description: 设计或评审 crash-triage 三份产物（L1 日报 / L2 周报 / 台账）的内容——该有哪些模块、指标、维度，哪些数据源给得出、哪些给不出。用于：报告缺内容、读者说看不懂、要加维度或指标、重排版面、判断某个想要的字段能不能做；或当用户提到 报告设计、内容审计、加维度、模块清单、看什么指标、报告缺什么 时。⛔ 不负责改指标算法与阈值（走 crash-metric-change）。

# crash-report-design

## 三份产物各回答一个问题

| 产物 | 频率 | 回答 | 版本口径 | 分析 |
|---|---|---|---|---|
| **L1 日报** | 每天 07:00 | 「**今天有没有变糟**」 | 版本号**最新 2 个** | ⛔ 不做 |
| **L2 周报** | 周一 05:30 | 「**这周该修什么**」 | 会话量 **top2 主力版本** | ✅ 崩溃段可出根因（标未复核）；⛔ 性能段不出 |
| **台账** | L2 独占 | 「**每个 issue 现在什么状态**」 | 跨版本，**刻意不过滤** | ⛔ 只收结论 |

⚠️ 日报与周报的版本集**常常不同**（新版刚放量时尤其），并排必须标注不可混比。

## 字段可用性（2026-08-24 实测，近 7 天）

动手设计前先看这张表；**要加表外的字段，先按 crash-report-analyst 的方法验覆盖率**。

| 字段 | Android | iOS | 判定 |
|---|---|---|---|
| `device.manufacturer/model` | ✅ | ✅ | ⚠️ Apple 机型标识符**自带逗号**（`iPad7,11`），解析必须走 CSV |
| `operating_system.display_version` | ✅ | ✅ | ✅ 唯一给率的维度（桶足够大） |
| `blame_frame.owner` + `library` | ✅ | ✅ | ⚠️ 两者**必须一起给** |
| `custom_keys.current_screen` | 200/221 | 1096/1097 | ✅ **崩溃发生在哪个页面**，目前完全未用。⚠️ 有事件取不到（Android 实测 19 条空）→ 渲染「未知」，⛔ 不要丢弃 |
| `custom_keys.mem_tier` | 211/221 | 1092/1097 | ✅ 内存档位（high/mid/low） |
| `custom_keys.app_foreground` | 200/221 | 1097/1097 | ✅ 前台崩 vs 后台崩，处置优先级完全不同。⚠️ **两端取值不同**：Android `true`/`false`，iOS `1`/`0`——不归一化会拆错 |
| `custom_keys.device_rom` | 211/221 | — | ✅ Android 厂商 ROM（18 种）；iOS 恒 `apple` 无信息 |
| `custom_keys.scene` / `step` | 113/221 | 1094/1097 | ✅ 自埋的崩溃场景与阶段 |
| `custom_keys.nserror-domain/code` | — | 1096/1097 | ✅ iOS 错误域，NON_FATAL 归类用 |
| `user.id` | **0/221** | **1060/1097** | ⚠️ **只有 iOS 有**——可给真实受影响用户数；⛔ Android 必须继续用「受影响安装」，两端不可并列成一列 |
| `installation_uuid` | ✅ | ✅ | ⚠️ 是**安装**不是用户；⛔ 与 sessions 的 `instance_id` **JOIN 不上** |
| `firebase_session_id` | ✅ | ✅ | ✅ 与 sessions 的 `session_id` 可 JOIN——crash-free 走这条 |
| `sessions.session_index` | 96% 为 0 | 同 | ⛔ **不是「第几次会话」**——8208/8516 的值是 0，字段在会话组内重置。⛔ 做不了新老用户拆分 |
| `sessions.first_session_id` | 96.4% 自指 | 同 | ⛔ 同上，不是「首次会话」标记 |
| `storage.free` / `memory.free` | ✅ | ✅ | ✅ 低存储/低内存关联 |
| `process_state` / `device_orientation` | ✅ | ✅ | ✅ |
| `variant_id` | ✅ | ✅ | ✅ issue 变体 |
| `remote_config_feature_rollouts` | 恒空 | 恒空 | ⛔ **灰度关联做不了** |

## ⛔ 两条会让整块设计落空的前提（2026-08-24 实测）

### iOS 几乎没有 FATAL——按致命口径下钻必是空表

```
iOS 60 天：FATAL 5 事件 / 4 issue   ·   NON_FATAL 1424 事件 / 5 issue
```

现有 `crash-issues.sql` 是 `is_fatal = TRUE`，`crash-dimensions.sql` / `crash-blame.sql` 是 `error_type IN ('FATAL','ANR')`——iOS 在这三份 SQL 下都只有个位数事件。

⛔ **iOS 侧的维度与 TOP N 下钻必须以 NON_FATAL（`issue_subtitle`）为主源**，否则新加的维度在 iOS 全是单行表，而「iOS 汇总段只有 1 行」与「iOS 很健康」在版面上长得一模一样。

### 前后台用 `process_state`，不用 `app_foreground`

| | iOS | Android |
|---|---|---|
| `process_state` 可判定 | 1088/1088 = **100%** | 200/221 = 90.5% |
| `app_foreground` 非空 | 100% | 90.5% |
| 两者 COALESCE | 100% | **99.5%** |

`process_state` 是一等字段、**双端同名同枚举**，用它就绕开了 `true/false` vs `1/0` 的归一化（那正是最容易写错的地方）。Android 的 21 条 `UNKNOWN_PROCESS_STATE` 里有 20 条 `app_foreground` 有值，故回落仍有价值。

⚠️ **这条拆分直接改写 iOS 的结论**：iOS 崩溃事件 **1073/1088 = 98.6% 发生在后台**（Android 反过来，173/221 是前台）。iOS 那上千条非致命不是「iOS 问题多」，是后台噪音——不拆开就会得出相反判断。

## 模块清单

### L1 日报（高频呈现，不做分析）

| # | 模块 | 回答 | 指标 | 维度 |
|---|---|---|---|---|
| 1 | 摘要行 | 要不要现在看 | 🔴/🟡 告警项 | — |
| 2 | 总体盘子 | 大盘多大 | 会话数 · 设备数 · crash-free（最新版 · 全版本并列） | 平台 |
| 3 | 三类事件 | 各类严重度 | FATAL 次数/率 · ANR 次数/率 · NON_FATAL 次数 | 平台 × 版本 |
| 4 | 影响面 | 影响谁、集中在哪 | 受影响安装 · 集中度 | 机型 / 系统版本 / **页面** / 内存档 |
| 5 | TOP 3 事件 | 先看哪三个 | 事件数 · 影响安装 · 集中度 | 每个再给 top 机型 / 系统版本 / 页面 |
| 6 | 时间分布 | 是否有尖峰 | 小时分布 | 平台 |
| 7 | 性能 | 体验有没有退 | 启动 P50/P95 · 慢帧 · 冻结 · 接口错误率 | 平台 × 版本 |
| 8 | 环比 | 比昨天/上周如何 | DoD / WoW | 同版本 |
| 9 | 口径 | 数字怎么来的 | 取数区间 · run_id | — |

### L2 周报（= 日报口径的周维度 + 分析）

在 L1 全部模块之上加：

| # | 模块 | 回答 | 内容 |
|---|---|---|---|
| 10 | 本周变化 | 这周发生了什么 | 新增 / 暴涨 / 消失 / **回归**（jq 确定性，不经模型） |
| 11 | 主力版本 | 承载用户的大头 | 会话 top2 版本的全套指标 |
| 12 | 归因分布 | 责任在谁 | `blame_frame.owner` + `library`（⚠️ 一起给） |
| 13 | 根因分析 | 为什么崩 | 每个 TOP issue：栈 · 复现路径 · 修复建议（⚠️ 标未经复核） |
| 14 | 性能趋势 | 在变好还是变坏 | WoW，⛔ 不出根因 |

### 台账（结论沉淀，四段式，顺序固定）

| 段 | 内容 | 关键列 |
|---|---|---|
| 1 | 项目常量 | 包名 / appId / 仓库 |
| 2 | 崩溃收口点登记 | 埋点位置 |
| 3 | **Issue 现状表**（FATAL / NON_FATAL 分两张） | 平台 · id · 标题 · 类型 · 首次纳入 · 处置状态 · **生命周期态** · 事件量 · 备注 |
| 4 | 变更时间线 | 按日期追加，⚠️ **append 不幂等，追加前必须查重** |

⛔ 性能不进台账（连续指标、无追踪 ID）。⛔ NON_FATAL 表**必须截断并标注**——iOS 上千条会把 FATAL 信号淹没。

## 排版铁律

1. **平台永远分列，不合并。** 两端的口径、量级、可用字段都不同（iOS 无 ANR、Android 无 user.id）。
2. **版本永远分行，不给跨版本合计。** 合计会把「刚放量的新版很糟」平均掉。
3. **维度嵌套顺序 = 平台 → 版本 → 维度。** 读者的动线是「先定位哪端哪版，再看细节」。
4. **卡片只放摘要 + 一张表**（`CELL_BREVITY=1` 短文案），完整内容留文档——长文案撑爆列宽会被截断。
5. **表格列名不能叫 `ios`/`android`**（CardKit 平台变体键），用 `c1`…`c4`。
6. **每个比率旁边标分母与窗口。**

## 建议加的内容（按优先级）

1. **页面维度**（`current_screen`）——覆盖率 90%+ 却完全未用。「崩在哪个页面」比「崩在哪个机型」可行动得多。
2. **前后台拆分**（`app_foreground`）——后台崩溃对用户无感，与前台崩溃混在一起会让优先级判断失真。
3. **TOP 3 事件的下钻卡片**：每个 issue 给「top 机型 / 系统版本 / 页面 / 内存档 + 集中度」，直接回答「谁受影响」。
4. **iOS 真实受影响用户数**（`user.id`，96.6%）——⚠️ 单独成列并标明 Android 无此数据，⛔ 不可与 Android 的「安装数」并成一列。
5. ~~新老用户拆分~~ ⛔ **做不了**（2026-08-24 实测推翻）：`session_index` 96% 为 0、`first_session_id` 96.4% 自指，两个字段都在会话组内重置，不是「自安装以来第几次」。
   ⚠️ 这条建议最初被标成 ✅ 是**只看了字段存在、没看分布**——正是本 skill 与 crash-report-analyst 都写明禁止的做法。留在这里当反面样本。
6. **复发率**（生命周期「回归」态占比）与**修复率**（`fix_commit` 命中占比）。⚠️ 修复率依赖 commit message 的 `crash:` 约定，实测两个仓库 120 天命中 0 条——**先落实约定，否则这个指标恒为 0**。

## 动手前

- 改**指标算法或阈值** → 走 `crash-metric-change`，不要在本 skill 里做。
- 加**维度或模块** → 先用 `crash-report-analyst` 验字段覆盖率（双端分别验），再开 openspec change。
- 验产物 → `crash-report-debug`（DRY_RUN / NO_DELIVER）。
