## D1 — 合并方向：数据层做主干，分析层做追加段

数据层周报持有三样分析层永远拿不到的东西：**取数区间双时区标注**、**run_id 与审计文件指针**、**口径注记**。这三样是「这些数字是怎么来的」的唯一记录，必须在文档顶部。分析层是对崩溃 issue 的解读，属于结论，放末尾。

反向（triage 在前、数据层作附录）被否：文档头部会失去取数区间与 run_id，跨周 diff 时无法确认两份报告的窗口是否等长。

## D2 — 只删 triage 的 h1，其余标题层级一律不动

⛔ **这是本 change 最容易踩的坑。**

`split-fix-list.py:16` 定位修复清单段用的是：

```python
FIX_HEADING_RE = re.compile(r'^##\s*[^\n]*修复清单')
```

严格匹配**二级**标题。把 triage 的 `## 四、修复清单` 降级成 `### 四、修复清单`，`split-fix-list.py` 会**静默失效**——它找不到段落就原样返回，退出码 0、无告警，修复清单从此不再按平台分组，而没有任何信号提示这件事发生了。

这与 CLAUDE.md 里「改名时别名处不报错只静默拿空集合」是同一类失效模式。

因此合并只做一件事：**丢弃 triage 的第一行 h1**（避免文档出现第二个 h1，飞书目录会把它渲染成并列的顶级条目），标题层级零改动。

代价：triage 内部的 `## 〇、执行完整性声明` 等段落与数据层的 `## 一、`…`## 六、` 同级平铺，中文序号会出现两套。**这是刻意接受的**——序号重排的收益是排版美观，风险是打断一条无告警的下游依赖，不划算。

## D3 — 分界段的标注

追加段标题固定为：

```
## 分析层 · 根因分析（模型产出，**未经人工复核**）
```

⚠️ **刻意不带中文序号**。初版写作「## 六、根因分析」，2026-08-24 含分析层的整跑实测撞号——当轮 triage 报告自己写出了 `## 六、修复清单`，同一份文档里出现两个「六、」。triage 内部的序号由模型每轮自拟、不可预测，插入的标题只要参与编号就迟早撞上。用「分析层 ·」既避开编号空间，又与仓库既有的「数据层 / 分析层」措辞一致。

「未经人工复核」在此处**再标一次**是刻意的冗余。spec `crash-perf-daily-weekly-report` 的「报告标注未经复核」要求卡片标注，triage 报告自身首行也有 callout 声明——但合并后 triage 的 callout 落在「六、」标题之后、正文之前，读者若从目录直接跳到某个根因小节会略过它。标题里带一次，跳转也躲不开。

## D4 — 缺分析的一周：行为零变化

`ANALYSIS_OK != 1` 时不追加任何内容，文档就是数据层五段，与当前完全一致。「五、口径」段末尾既有的「⚠️ 本周无深度分析 — 原因」注记保持不动——CLAUDE.md 硬约束：缺分析与无异常是两件事，必须可见。
