## Why

**周报每读 5 个字，有 2 个在说「别这样读」。**

2026-09-01 对 08-31 周报（`NIzedWRWCoAhOix10IVjfjxlpSS`）的实测：

```
总字符 9299 ┃ 其中 3712 字在 <callout> 免责块里 = 40%
           ┃ 16 个 callout ／ 54 行数据 ／ 28 个 ⛔⚠️ ／ 36 处「不可/不是/不得/禁止」
日报 17437 ┃ 9 个 callout ／ 213 行数据
```

每一条口径注解都有来历，都是踩过的坑，单独看没有一条该删。但累积效果是**读者读到的警告比数字多**，且没有优先级——「⛔ 分母为 0 显示无法计算」（读数须知）与「⛔ 不设会话数门槛」（给未来改代码的人看的设计备忘）在版面上一样重。

追根到一处结构性选择：**我们在用静态文档复刻 Firebase 控制台的下钻能力。**

Firebase 上，「看哪个版本」「看 FATAL 还是全部」「看几天」都是下拉框——口径不需要被理解，因为它可操作。我们发的是冻结文档，于是每一个口径选择都从「读者的一次点击」变成「作者替他做的决定」，读者要读懂数字就必须先逆向解码这个决定。40% 的篇幅就是这么来的。

代价可以量化。同一条 issue `62f88f39` 在产物里有四个都正确的数字：

| 出处 | 数字 | 口径 |
|---|---|---|
| 台账现状表 | 7 事件 | 全版本 · 7 天窗 · FATAL |
| 周报段四 TOP3 | 4 事件 / 4 安装 | 仅主力版本 · FATAL+ANR |
| 周报段三 归因表 | 2 事件 / 2 安装 | 仅 1.5.5 那一行 |
| 日报明细 | 1 事件 / 1 安装 | 仅 1.5.6 |

Firebase 上它只有一个数加一个下拉框。我们把下拉框的每个档位都印成一行，分散在三份文档里，再用注解解释它们为什么不同。

而**真正只有我们能给、Firebase 给不了的东西是另外四样**：跨轮次的「变化」、跨版本的 issue 生命周期与台账、崩溃/性能/放量并排、责任帧 owner 与 library 的组合读法。这四样恰恰不是篇幅大头。

## What Changes

- **段三（影响面维度）与段四（TOP3 下钻）由「静态复刻」改为「定位 + 直达」**：保留可定位对象（哪个机型/系统版本/页面集中）与集中度，**去掉逐维度的完整分布表**，每条 issue 给一个 Firebase 直达链接。读者要下钻就点过去，看到的是 Firebase 自己的口径——**于是「⛔ 不可与控制台对照」这一类注解整段失去存在理由**。
- **口径注解分层**：正文只保留「读这张表必须知道」的一行；「为什么这么设计」「改的时候注意什么」移到文末「口径与设计约束」一章。⛔ 一个字都不删，只换位置。
- **首屏只回答一个问题**：本周有没有新的坏事。一套口径，不解释。
- **段落级口径标注收敛为表头角标**：现在每段一个 callout 重复说明版本集与 error_type 集，改为在表头标注（如「主力版本 · FATAL+ANR」），注解只出现一次。

预期效果（估算，非承诺）：周报正文从 9300 字降到 4000 字量级，callout 从 16 个降到 3~4 个，信息量不减——减掉的是「解释我们和 Firebase 为什么不一样」。

## Non-goals

- **不删任何一条口径注解的内容**。只做分层与去重：正文留判读所需，其余移文末。⛔ 压缩时不得砍掉有记录的口径标注（样本量括注、两端窗口标注）——那条硬约束照旧。
- **不改任何指标算法、阈值或版本口径**。本 change 纯呈现层。版本集合的问题由 `crash-report-version-alignment` 处理。
- **不动分析层产出**。模型报告按 triage skill 自己的模板成文，脚本不改写其正文。
- **不改台账结构**。台账是「只存结论」的产物，不在本 change 覆盖面。
- **不删除段三段四本身**。去掉的是完整分布表，保留的是可定位对象与集中度——「只给可定位对象与取证方向，不出根因」这条既有要求不变，本 change 是它的进一步兑现。

## Capabilities

- `crash-perf-daily-weekly-report`（修改）：新增「口径注解分层」与「首屏单一问题」两条要求。
- `crash-perf-impact-summary`（修改）：新增「维度呈现优先直达而非复刻」要求。

## 待确认（实施前必须定）

⚠️ **本 change 会部分回退刚完成的 `crash-issue-drilldown`**（openspec/changes/crash-issue-drilldown，15 项任务已完成 14 项）。那个 change 的方向是把 per-issue 下钻**加进**周报；本 change 的方向是这类下钻**交给 Firebase，我们只给链接**。

两者不是实现冲突，是同一个问题的两种答案。**必须先定方向，本 change 才能写实施细节**：

| | 主张 | 代价 |
|---|---|---|
| 保留下钻（现状） | 读者不离开文档即可看到分布 | 每张表都要解释口径为何与控制台不同；篇幅与注解成正比增长 |
| 改直达（本案） | 篇幅与注解同时下降；口径差异问题消失 | 读者需要有 Firebase 访问权限；离线/群内快速浏览时信息变少 |
| 折中 | 保留段三维度表，只把段四 per-issue 下钻改直达 | 两种形态并存，读者需要理解「为什么这段能点那段不能」 |

⚠️ 建议在定方向前先确认一件事实：**报告的实际读者里有多少人有 Firebase 控制台权限**。若多数人没有，「改直达」等于把信息藏起来，本 change 的前提不成立。这个问题我无法从代码或数据中查证。
