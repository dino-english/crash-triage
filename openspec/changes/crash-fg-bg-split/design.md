## D1 — 用 `process_state`，不用 `app_foreground`

| 字段 | iOS 可判定 | Android 可判定 |
|---|---|---|
| `process_state`（一等字段） | 1088/1088 = **100%** | 200/221 = 90.5% |
| `app_foreground`（自埋 custom key） | 100% | 90.5% |
| **两者 COALESCE** | 100% | **220/221 = 99.5%**（实测未知 21 → 1） |

选 `process_state` 打头的理由不只是覆盖率——它**双端同名同枚举**（`FOREGROUND` / `BACKGROUND` / `UNKNOWN_PROCESS_STATE`），用它就绕开了自埋键的归一化。

⚠️ **`app_foreground` 两端取值不同**，这正是最容易写错的地方。方向经交叉验证（7d）：

```
iOS    ：BACKGROUND↔"0" = 1068 · FOREGROUND↔"1" = 14      （一致率 99.2%）
Android：FOREGROUND↔"true" = 162 · BACKGROUND↔"false" = 11
```

⛔ **不许凭直觉假设 `1` = 前台**——iOS 的 `1` 确实是前台，但这是**验出来的**不是猜出来的，而且 iOS 绝大多数事件是 `0`，只看样本首行会得到相反印象。

## D2 — 归一化表达式全仓只此一处

放在 `crash-error-types.sql` 的 `WITH e AS (...)` 里，**一个文件、一个表达式**。

⛔ 不复制到 `crash-rate.sql`，也不放渲染层。理由是失效模式 F1「同一目的两份实现，修了一份就以为修完了」——本仓库已因此把 1 个事件渲染成 11，且 lint 抓不到（`check-scripts` 第 4 项只检测同名函数）。

代价：FATAL 的前后台要从「错误类型」这份 SQL 里取，语义上略绕。**这个代价是刻意付的**——另一条路是让两份 SQL 各写一遍 CASE 表达式，那正是 F1。

## D3 — 未知单独成列，不并进后台

`0 前台` 与 `未知` 是两件事：前者是结论（确实没有前台事件），后者是缺数。合并会让「iOS 某批事件全是后台」与「这批事件取不到状态」长得一样。

Android 实测未知 1/221，iOS 0/1088——量很小，但正因为小，混进去更不会被发现。

## D4 — 摘要行只在「值得多说一句」时出现

条件：样本 ≥ `FGBG_MIN_EVENTS`（20）且后台占比 ≥ `FGBG_BG_NOTE_PCT`（80%）。

- **样本门槛**：3 次事件里 3 次后台不构成结论。
- **占比门槛**：50/50 的分布说明不了什么，写出来只是占版面。
- ⚠️ 两个阈值**不参与任何红黄绿判定**，只控制「要不要多说一句」。后台占比高不是告警——它是**降低**严重度的信息。

文案刻意写「用户无感」而**不写**「无需处理」：⛔ 后台崩溃会中断上传、推送与预加载，不等于可以不修。

## D5 — 为什么不给率

`firebase_sessions` 全字段实测：`instance_id` / `session_id` / `first_session_id` / `session_index` / `event_type` / 双时间戳 / 双开关 / `application.*` / `device.*` / `operating_system.*`。

**无 `process_state`、无 screen、无用户标识。** 前后台的会话分母不存在，这不是「暂时没做」而是数据源没有。⛔ 任何「前台崩溃率」的提议都要先回答分母从哪来。
