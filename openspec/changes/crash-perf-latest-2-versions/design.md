## D1 版本解析源表：sessions REALTIME

三张表都有版本维度，但**同一时刻各表的「最新版本」不同**（2026-08-17 实测）：sessions 已有 1.5.4（383 会话），crashlytics 完全没有 1.5.4 事件，performance 批量表只有 199 条 1.5.4。

选 `firebase_sessions` REALTIME 作为**唯一版本解析源**：它是「线上正在跑什么版本」的活源，其余两表是「这些版本出了什么事」。若各段各自解析，会出现崩溃段看 1.5.2/1.5.3、放量段看 1.5.4/1.5.3 的错位。

代价：最新版在性能/崩溃段可能 0 行。这是**真实状态**（新版刚放量、批量表滞后），用「该版本无数据」显式表达，不回退到旧版本凑数（回退等于偷偷改口径）。

## D2 版本粒度：display_version，不含 build

iOS 同一 `display_version` 下存在多个 build（实测 1.5.3 有 `1.5.3.24` 与 `1.5.3.0`，1.5.4 有 `.0/.5/.8/.9/.10`）。按 build 细分会让「最新 2 个」退化成「最新 2 个构建」（可能同属一个对外版本），对业务无意义。钉死 `display_version`；build 差异在同一版本内合并统计。

## D3 版本号排序用 `sort -V`，不在 SQL 里做

BigQuery 无原生版本号排序，SQL 内拆分数字段落既啰嗦又易错。沿用脚本既有做法（`topver()` 已在用 `sort -t, -k1,1 -V`），由 shell 排序。macOS BSD `sort -V` 已实测可用。

## D4 SQL 占位符 `{{VERSIONS}}`：值是 quoted list，谓词写在 SQL 文件里

字段路径两套（perf 顶层 `app_display_version`；crashlytics/sessions 嵌套 `application.display_version`），若让脚本拼整条谓词，脚本就要知道每个 SQL 文件对应哪张表的 schema——知识放错了地方。

约定：脚本只替换 `{{VERSIONS}}` → `"1.5.4"`（或 `"1.5.4","1.5.3"`），**谓词由 SQL 文件自己写**：

```sql
AND app_display_version IN ({{VERSIONS}})          -- perf 系
AND application.display_version IN ({{VERSIONS}})  -- crashlytics / sessions 系
```

保留 IN 列表形式（而非 `= '版本'`）是为 `CRASH_REPORT_VERSION_COUNT != 2` 时不用改 SQL。

## D5 逐版本取数，不做 GROUP BY version

两种实现：(a) 每版本各跑一次查询；(b) 一次查询 `GROUP BY version` 后在 shell 里按版本挑行。

选 (a)。理由：现有取数管线（`csv()` / `cut -f` / `jq '.[0]'`）全部假设「一次查询一个结果集」，改 (b) 要重写全部提取助手，diff 面积远大于多跑一次查询。代价是查询数翻倍（~30 → ~46），单次运行耗时上升约 1–2 分钟——日报 07:00 跑、L2 早 90 分钟，时间预算充足。

## D6 「该版本无数据」vs「数据未同步」的判定序

三态判定，顺序不可颠倒：

1. `table_exists()` 为假 → `表尚未同步`（既有语义，含瞬时错误按「存在」处理的重试逻辑不变）
2. 表存在但 `table_max()`（**不带版本过滤**）为空 → `⚠️ 数据未同步，最新截至 —`（既有语义）
3. 表有数据但该版本查询 0 行 → `— 该版本无数据`（**新增**）

第 2 步必须用不带版本过滤的探测，否则新版尚未产生数据会被误报成数据源故障，天天误告警。

## D7 版本间对比指示器

对比列 = 最新版值 − 上一版值，方向沿用仓库既有约定「数值变大 = 变差 = ↑」。着色：变差红、变好绿、持平灰、任一端缺数据显示 `—`（不猜）。

与既有 DoD/WoW 的分工：**对比列答「这版发得比上版好还是差」（卡片，一眼可见）；DoD/WoW 答「同一版本在恶化还是收敛」（文档，需要上下文）**。两者不同时出现在卡片同一单元格——那正是当前卡片读不动的原因之一。

## D8 阈值红绿灯继续作用于「最新版」

`traffic_light()` 阈值（崩溃率 1%、慢帧 50%、冻结 1%、启动 P95 2000ms、接口错误率 1%）判定对象改为**最新版的值**（上一版只展示不告警）：告警要指向「现在该不该拦发版」，上一版已成既定事实。阈值数值本次不动，但样本变小后波动加剧，需观察 1–2 周后复评（记在 tasks 验收项）。

小样本提示（`SAMPLE_SESSION_MIN`）判定对象同步改为版本级会话数——这与 `crash-perf-daily-monitoring` spec「MUST NOT 按版本细分会话数」直接冲突，本 change 的 spec 显式取代该断言（该 change 尚未归档，归档顺序见 proposal Impact）。

## D9 历史基准迁移：自愈式丢弃，不靠人工删文件

`state/metrics-history.jsonl` 旧行是全版本口径，新行是版本级。读取时按「行内有无 `versions` 键」判定格式：无则丢弃并打印 `⚠️ 丢弃 N 行旧口径历史（全版本 → 版本级），环比基准重建中`。

优于「让运维手动 rm」：运维步骤会被忘记，而忘记的后果是**静默混比**（今日版本级 vs 昨日全版本），恰恰是最危险的失败模式。写入侧同时按 `day` upsert（顺带修 `crash-perf-execution-audit-log` 已登记的同日两行问题）。

## D10 台账排版：拆表 + 折叠，不动内容

`reports/LEDGER.md` 是人工真相源，本次**只重排不改写结论**：单张 8 列宽表 → 「活跃 issue 表（5 列：Issue / 标题 / 状态 / 首次纳入 / 备注指针）」+ 每条 issue 的详情条目（长文本从单元格移到正文）+ `<details>` 折叠的历史归档区。飞书文档镜像同样受益（镜像是 markdown 直接 import）。

## D11 列集合 = 最新 2 版 ∪ 会话量 top2（上限 4 列）

「最新 2 个版本」回答「新版发得怎么样」，但当新版刚放量、大盘仍在旧版时，日报会**看不见承载绝大多数用户的那个版本**（实测 Android：1.5.3 有 901 会话、1.5.1 有 288，若某天 1.5.2 补上量，最新 2 版就会把 1.5.1 挤掉）。

规则：列集合 = 最新 N 版 ∪ 会话量 top2，按版本号新→旧排列，上限 4 列。列头带角标：`1.5.5 最新` / `1.5.3 主力`（同时满足则标 `最新·主力`）。当两个集合重合（当前 iOS/Android 均如此），列集合退化为 2 列，卡片形态与基础设计完全一致——**补列是异常态才出现的安全网，不是常态负担**。

成本控制：**天级单日值 / DoD/WoW / sparkline / 历史存储只跟踪最新 N 版**，补充列只出窗口值与版本间对比之外的裸值。理由是补充列的作用是「别把大盘看丢了」，不是「追踪它的日内走势」；全跟踪会让查询数从 ~46 涨到 ~72。

告警仍只由最新版触发（D8 不变）：补充列命中红档只着色不告警——它已是既定事实，拦不了发版。
