## MODIFIED Requirements

### Requirement: 产出显式标注分析层状态

周报与群卡片 MUST 显式标注本轮有无深度分析；无分析时 MUST 同时给出原因，并声明数据与台账不受影响。

有分析时，产出 MUST 标注**实际执行该分析的模型标识与端点归属**，MUST NOT 只写「模型产出」。

缺分析与无异常是两件完全不同的事。若不标注，读者会把「本周没有根因分析」读成「本周没有问题」——这是比缺失本身更严重的后果。

模型标识必须标注的理由：分析层的调用可能经由本机代理转发至第三方端点，请求的模型名与实际执行的模型名不必相同。2026-09-01 实测生产机：`ANTHROPIC_BASE_URL` 指向本机 `cc-switch`，上游是 `azure-foundry`，代理日志中 `request_model=claude-opus-4-8` 实际由 `gpt-5.6-terra` 执行，且 opus / sonnet / haiku / fable 四档全部映射到同一模型。而分析层的 prompt 与台账的证据分级（`✅钻取确认` / `⚠️聚合推断`）是按特定模型的行为调校的——读者若默认根因出自被请求的那个模型，「未经人工复核」这句标注就没有起到它该起的作用。

#### Scenario: 无分析时的标注

- **WHEN** 本轮未产出分析报告
- **THEN** 周报 MUST 含形如「⚠️ 本周无深度分析 — <原因>」的声明
- **AND** 群卡片的口径行 MUST 同样可见该声明（卡片读者多数不会点进文档）
- **AND** 声明 MUST 说明数据、台账与变化检测不受影响

#### Scenario: 有分析时的标注

- **WHEN** 本轮产出了分析报告
- **THEN** 产出 MUST 标注根因与修复方案未经人工复核、落地前须验证
- **AND** MUST 标注实际执行分析的模型标识与端点归属

#### Scenario: 模型标识取自环境声明

- **WHEN** 记录模型标识
- **THEN** MUST 取运行环境实际声明的端点与模型配置
- **AND** MUST 标明其为环境声明而非上游确认
- **AND** 理由：代理可将请求改写并转发至任意上游，脚本侧无法证实上游实际执行的模型

#### Scenario: 无法确定模型标识

- **WHEN** 环境未声明端点或模型配置，无法确定实际执行者
- **THEN** MUST 如实标注为无法确定
- **AND** MUST NOT 以请求时使用的模型名代替
- **AND** MUST NOT 表述为特定厂商的模型
