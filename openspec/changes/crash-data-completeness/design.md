## D1 完整性判据用「最新事件日的前一天」，不用分区元数据

**取 `LAST_COMPLETE_DAY = DATE(DATA_UNTIL) - 1`。**

备选是查 `INFORMATION_SCHEMA.PARTITIONS` 判断分区是否 finalize。**否决**：perf 表实测按**摄取时间**分区（`bq ls` 显示 `DAY` 无 field，crashlytics 才是 `DAY (field: event_timestamp)`），`partition_id` 与事件日不是一回事——2026-08-27 实测 perf IOS **根本没有 `20260826` 分区**，而按事件日却有 3988 行 08-26 数据。用分区元数据判事件日完整性会得出错误结论。

`DATE(DATA_UNTIL) - 1` 只依赖一条：表里存在 D+1 的事件 ⇒ D 已灌完。对批量与流式导出都成立，且 `DATA_UNTIL` 是现成的（`crash-daily.sh:547`，来自既有 `table_max()`）——**不额外查 BigQuery**，符合「数据口径」节记载的成本约束。

**已知代价**：D+1 只要有 1 条事件就判定 D 完整，理论上存在「D 尚未灌完、D+1 已有零星事件」的窗口。实测未见（灌数按时间顺序推进）；即便发生，退化后果等于今天的现状，不会更差。

## D2 窗口锚点换成 LCD，但 DATA_UNTIL 仍要显示

标注里**同时给**窗口与上游进度：

```
性能数据 2026-08-22 ~ 08-24（完整日）· 滞后 3 天 · 08-25 起未合并
                                                    ↑ DATA_UNTIL 的日期
```

只给窗口会丢掉上游进度——读者无法判断明天会不会好转，也看不出导出是否卡住（如 08-16 那种回填到 145h 的情况）。`crash-perf-data-staleness-guard` 要求「各段截止时间戳分别如实标注」，本 change **不放宽该要求**，只在其上再加窗口。

## D3 只让性能段分域，不动其余段——与「让新版本被看见」不冲突

「版本口径」节记载的取舍是：**刻意接受**低会话量新版占据报告，因为「一个内测包出现在线上数据里本身就是要看见的事」。

一刀切换列（整份报告都改成 1.5.4+1.5.3）会**违背这条原则**——1.5.5 将从报告里彻底消失。故否决。

**分域选版与该原则相容**：1.5.5 在崩溃段与放量段照常出现（`sessions_1d=36`、`crash_events_1d=0` 是真数据，且「新版发出去有没有崩」是发版当天最该看的一行），只有性能段——它在那里本来就没有任何数据可看——换成有数据的版本。**被看见的诉求由崩溃/放量段承担，可读性由性能段承担。**

同一节还写着「各表『最新版本』并不一致……**各段各自解析必然错位**」。既然错位是已认定的事实，与其让性能段显示一列空白，不如让它显示自己表里真实的最新 2 版。**本 change 是把已被记载的事实兑现到呈现层，不是推翻取舍。**

**代价**：同一份报告出现两套版本列，读者可能困惑。用表头显式标注化解（性能段标「性能数据可得的最新 2 版」）。

**退化方案**（若版面无法承受两套列）：保持 1.5.5+1.5.4，性能行走 C 的「尚无数据」态，另加第 3 列 1.5.3 专供性能。`MAX_VERSION_COLS` 已是 4，有空间。此方案改动更小但列语义更杂，**优先走分域**。

## D4 回溯上限 2 版

无上限回溯会在极端情况下翻到远古版本（如导出停摆一周），显示一个早已没人用的版本却看不出异常。上限 2 版 = 最多看 4 个候选；4 个都无数据即判定**数据源异常**，转既有「⚠️ 数据未同步」告警，不继续往下翻。

## D5 C 是第 3 态的细分，不是新的第 4 态

「缺数三态（顺序不可颠倒）」是既有硬约定：

1. `table_exists()` 为假 → `表未同步`
2. 表存在但 `table_max()`（不带版本过滤）为空 → `⚠️ 数据未同步`
3. 表有数据但该版本 0 行 → `— 该版本无数据`

C **只在第 3 态内部分叉**，判据是「该版本该指标的历史是否曾有值」，数据源是 `metrics-history.jsonl` / `weekly-metrics.jsonl`。**前两态的判据、顺序、文案一律不动**；第 2 态「必须用不带版本过滤的探测」这条也不受影响——C 发生在它之后。

⚠️ 命名上避免再叫「三态」，文档与代码注释统一称**「第 3 态细分」**或「历史值回填判定」，否则与既有缺数三态混淆。

## D6 判据必须用 null，不能用真值性判断

`start_p50_1d` 为 `null` 表示无样本；启动耗时不会是合法的 `0`。但**慢帧率 / 冻结率 / 接口错误率的 `0` 是合法且常见的**（2026-08-27 Android 1.5.4 冻结 0.0%）。

故 C 的判据 MUST 显式判 `null`，**MUST NOT** 用 `[ -z "$v" ]` 之类的真值性判断——那会把合法的 `0` 判成缺失，渲染出「沿用 08-25」而实际今天取到了 0。这是 bash 里极易踩的坑，`[ "$v" = "0" ]` 与 `[ -z "$v" ]` 必须分开写。

## D7 「本轮未取到」必须带日期

```
253ms（沿用 08-25，本轮未更新）
```

不带日期的「沿用旧值」在连续多轮取数失败时会一直显示同一个值而看不出已经僵住——`crash-fact-cache-freshness` 处理过的 `latest_event` 冻结正是这类问题（「台账『最近一次发生』停在历史峰值那天」）。**同一个坑不要在渲染层再踩一次。**

## D8 历史口径断裂：标记，不回填

A 生效后 `metrics-history.jsonl` 新行与已有旧行口径不同（含半天 vs 纯完整日）。三个选项：

1. 重算历史 —— 否决。原始数据仍在 BigQuery，但要重跑多天 × 双端 × 多版本查询，成本高；且旧报告已发出，改历史会让报告与历史对不上。
2. 清空重来 —— 否决。丢掉 WoW 基准。
3. **增 `window_mode` 字段（`legacy` / `complete_day`），跨口径比较时在报告上标注** —— 采纳。

切换后 7 天内的 WoW 会跨口径，该期间**必须带标注**，不能静默给数。这与「两套口径分离存储不可混比」（`crash-metric-change` skill 核心事实 2）是同一条纪律。

## D9 D 的时间改动与 A 必须同批上线

- A 单独上线：滞后 2 天 → 3 天，读者感知「变旧了」。
- D 单独上线：早 54 分钟的问题解决，但半天污染仍在。
- **合并上线**：滞后与现状持平，数据变干净。

故 tasks 里 D 与 A 同批验收，不拆两次发布。D 改的是 hermes cronjob（不在本仓库），需与脚本改动同时切换。
