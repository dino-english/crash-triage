## Why

`crash-perf-data-staleness-guard` 把性能窗口放宽到 3 天以**容忍** firebase_performance 约 2 天的批量滞后。窗口是宽了，但**没人问过尾部那一天只有 7 小时怎么办**——滞后被容忍了，不完整没有被处理。

### ① 半天数据占了「3d」样本的一半，并把 P95 抬高 12%

2026-08-27 跑批实测（iOS 1.5.4 `_app_start`，bq 实跑）：

| 口径 | 样本 | P50 | P95 |
|---|---|---|---|
| A 当前（`run−3d` → `DATA_UNTIL`，含半天） | 395 | 281ms | **1038ms** |
| B 最近 3 个完整天（08-22~08-24） | 288 | 276ms | **927ms** |
| C 仅尾部半天（08-25 00:00–06:59 UTC） | 192 | 281ms | 1044ms |

尾部 7 小时贡献了 **49% 的样本**（192/395），把 P95 抬高 **12%**。且它是固定时段切片——00:00–07:00 UTC = 东南亚/东亚的 07:00–14:00，**只有上午**，属系统性构成偏差，不是随机噪声。正在放量爬坡的版本受影响最大。

### ② 那半天不只是稀释窗口，它就是 DoD 表里的「今日」

2026-08-27 日报第四节 iOS 1.5.4：

```
| 启动 P95 | 1044ms | +6ms ↑ | +552ms ↑ |
| 慢帧（平台级） | 32.9% | +2.80pp ↑ | +30.90pp ↑ |
> 性能按最近可用日（2026-08-26 vs 2026-08-25）
```

`1044ms` 与上表 C 行**精确相等**——「今日」这一列是拿 7 小时的上午切片去和完整天做环比。慢帧 WoW **+30.90pp** 这种量级的信号，很可能整个是时段构成差异造出来的假象。**环比两边口径不同，差值无意义。**

这一条是本 change 的主要动机：①只是让绝对值偏高，②让环比失真——而环比是判断「新版有没有变差」的主要依据。

### ③ 性能段的列被没有性能数据的版本占据

`metrics-history.jsonl` 实录：

```
2026-08-25  1.5.4  196 会话  p50 261  slow 24.1
2026-08-25  1.5.3  283 会话  p50 302  slow 29.8   ← 有完整数据
2026-08-26  1.5.5    0 会话  p50 None slow None
2026-08-26  1.5.4  359 会话  p50 261  slow 24.1
```

1.5.5 自 08-26 出现至今，`start_p50_1d` 一次都没有过值（性能表里 `1.5.5` 零行，最新只到 1.5.4）。性能段两列中的一列长期为空。

**这不是 bug，是既有取舍的已知代价。** `docs/CLAUDE-架构与数据口径.md`「版本口径」明确记载：

> ⛔ **不设会话数门槛**（2026-08-22 起 `MIN_SESSIONS` 由 5 中和为 1）：门槛会把刚开始放量或已被叫停的新版静默剔除……而放量被叫停正是最该看见的事。
> ⚠️ 残余风险（刻意接受）：版本号更高的内测/灰度包哪怕只有 1 个会话也会成为「最新版」占据报告——**一个内测包出现在线上数据里本身就是要看见的事**。各表「最新版本」并不一致（性能批量表滞后 ~2 天、crashlytics 新版常为空），**各段各自解析必然错位**。

所以本 change **不推翻「让新版本被看见」这条原则**，只主张：让它在**有数据的段**被看见。见下方 What Changes B 与 design D3。

### ④ 跑批比数据落地早 54 分钟

`INFORMATION_SCHEMA.PARTITIONS` 实测 perf IOS 分区落地时刻：

```
20260825  08-26 23:54 UTC   47h
20260824  08-25 23:55 UTC   47h
20260823  08-26 00:44 UTC   72h
20260820  08-23 08:10 UTC   80h
20260816  08-22 01:54 UTC  145h   ← 回填
```

典型 47–52h（当天结束后约 24h），全距 45–169h。日报 07:00(+08) = **23:00 UTC** 跑，分区常在 **23:54 UTC** 落地——**系统性早 54 分钟**，白白多背一天滞后。2026-08-27 的 `health-daily.json` 记 `data_until: 2026-08-25 06:59 UTC`。

### ⑤ 「该版本无数据」态压着两种不同情况

既有缺数三态的第 3 态 `— 该版本无数据` 同时覆盖了：

- **该版本从来没有过数据**（1.5.5 的现状，属正常滞后）
- **历史有值、本轮没取到**（取数故障或导出退化）

两者处置完全不同，但渲染完全一样。`metrics-history.jsonl` / `weekly-metrics.jsonl` 里已存有判定所需的历史值，只是没被用于区分。

## What Changes

**A. 完整日窗口（L1 + L2）**

- 新增 `LAST_COMPLETE_DAY = DATE(DATA_UNTIL) - 1`（表里存在 D+1 的事件 ⇒ D 已灌完）。
- **性能段**窗口锚点由跑批时刻改为 `LCD`，取整日闭区间 `[LCD-(N-1), LCD]`。L1 N=3，L2 N=7。
- DoD 改为 `LCD` vs `LCD-1`，WoW 改为 `LCD` vs `LCD-7`——两边都是完整天。
- ⚠️ **不增加 BigQuery 查询**：`DATA_UNTIL` 已由既有 `table_max()` 取得（L1 复用、L2 已在 `crash-perf-latest-2-versions` 时新增），`LCD` 由 shell 从中算出。「起点由 shell 直接算、不额外查 BQ」这条成本约束不被破坏。
- 标注升级为「性能数据 08-22~08-24（完整日）· 滞后 3 天 · 08-25 起未合并」；**`DATA_UNTIL` 仍如实显示**，不放宽「各段截止时间戳分别标注」的既有要求。

**B. 性能段分域选版（仅 L1）**

- **崩溃段与放量段不动**：仍取最新 2 版，1.5.5 照常出现——「让新版本被看见」的原则完整保留。
- **性能段独立选版**：候选按版本号降序，逐个检查该版本在性能窗口内是否有值，凑满 2 个即停，**最多回溯 2 版**封顶；4 个候选皆无数据则转既有「⚠️ 数据未同步」告警。
- 性能段表头标注「性能数据可得的最新 2 版」，与其余段的版本列显式区分。
- 判据复用现成信号 `start_p50_1d == null`，不新增查询。

**C. 第 3 态细分：历史值回填判定（L1 + L2）**

⛔ **既有「缺数三态」的顺序与判据完全不变**（`表未同步` → `⚠️ 数据未同步` → `— 该版本无数据`）。本 change 只在**第 3 态内部**再分两种，不新增第 4 态、不调整前两态：

| 第 3 态的子情况 | 判据 | 渲染 |
|---|---|---|
| **尚无数据** | 历史中该版本该指标全 null | 「预计 08-28 到位」 |
| **本轮未取到** | 历史有值、本轮 null | 「253ms（沿用 08-25，本轮未更新）」 |

两侧皆有值且相等时属正常有值态，渲染「253ms 持平」，不进第 3 态。

**D. 跑批时间 07:00 → 08:30（+08）**

分区落地 23:54 UTC = 北京 07:54，08:30 跑可稳定看到前一完整日。与 A 组合后**新鲜度与现状持平、数据变干净**。

## Non-goals

- **不改崩溃段与放量段的窗口**。两者数据源新鲜度不同（crashlytics 当日可见、sessions 走 REALTIME 活表），完整日切分对它们无必要且平白损失新鲜度。本 change 只动性能段。
- **不给 L2 加分域选版**。周报按会话量 top2 选版（与日报刻意互补），0 会话的新版天然进不了 top2，**已免疫 ③**。L2 只受 A、C 影响。
- **不恢复 `MIN_SESSIONS` 门槛**。2026-08-22 将其中和为 1 是有实测依据的决定（Android 1.5.4 被叫停后从卡片上完全消失），本 change 不碰该常量，也不通过任何等价手段重新引入会话量门槛。B 的判据是**性能数据有无**，与会话量无关。
- **不重算历史**。`metrics-history.jsonl` 已按旧口径积累，A 生效后新旧不可直接连读；增 `window_mode` 标记，不回填、不重算。
- **不碰事实层缓存**。`crash-perf-issue-fact-cache` 的命中判定已由 `crash-fact-cache-freshness` 处理，与 C 不是同一层。
