## Why

事实层的**事件明细**在生产上几乎是空的，而且**结构上补不回来**。

2026-09-09 生产实测（新代码首个跑批，run_id `20260909-083002`）：

| | 数字 |
|---|---|
| 本轮 6 个 issue 的 `events` 数组长度 | `1 / 0 / 1 / 0 / 0 / 0` —— 合计 **2** |
| 同一批 issue 的窗口计数合计 | **29** |
| 模型侧统计行 | 命中 5 个（**跳过**）· 失败 1 个 |

「跳过」正是问题所在。抓取判定 `cache_verdict`（`bin/lib/core/cache.sh`）的入参只有
「强制重抓 / 文件是否存在 / 上次计数 / 本次计数」——**看不见 events 数组的长度**。
于是一条「`events_count_last_seen=14`、`events=[]`」的记录，只要线上计数不再上涨，
就**永远**判 `skip`，事件明细再也不会被抓。

`crash-fact-cache-deterministic-records` 让 shell 每轮无条件刷新观测字段，
把 `prev` 钉成本轮线上计数，于是「线上计数涨过旧值 → append」这条**理论上的自愈路径**
也关掉了（该 change 的 findings F-7）。⚠️ 公平地说那条路径实测从没生效过
（模型 25 轮里 20 轮没写、事件合计 6 vs 声称 55），准确表述是
「把理论上可能自愈变成了结构上不可能自愈」——但这正是必须现在修的理由。

**谁在吃亏**：L2 台账的「根因 / 版本流转」证据链。周报里那句
「✅钻取确认（采样 n=11/14）」靠的就是 `events` 里的历史事件；数组空了，
证据等级只能退成「⚠️聚合推断」，而读者看不出这是**数据没抓到**还是**真的推断不出**。

## What Changes

**让抓取判定看得见内容**：`cache_verdict` 增一个入参「已存事件条数」，
在「计数 > 0 且已存事件明显短缺」时返回 `append` 而不是 `skip`。

- **判据用「明显短缺」不是「不相等」**：`events` 是累积数组、计数是滚动窗口，
  两者本就不可比（`crash-fact-cache-deterministic-records` findings F-5）。
  攒久了 `已存 > 计数` 是正常的，⛔ 不能拿相等当判据。本 change 取
  「已存 == 0 且计数 > 0」这一个**保守判据**：它只覆盖「一条都没抓到」这种明确欠账，
  不去猜「抓了一部分」算不算够。
- **补抓有节流**：每轮最多补 N 个欠账 issue（默认 3，可配），⛔ 不一次性全放。
- `assert-fact-cache.sh` 的事件数对照行增一列「欠账 issue 数」，让补齐进度可见。

## Non-goals

- **不改 `events` 的合并语义**（沿用「已有记录原样保留、只 append」）。
- **不动观测字段的写入方**——那由 `crash-fact-cache-deterministic-records` 定案，本 change 不碰。
- **不追求「抓满」**：目标是让欠账**能收敛**，不是保证每个 issue 的事件数与窗口计数一致
  （那两个量本来就不可比）。
- **不修模型自陈「权限被拒」**——根因至今不可判定（缺工具级日志，F45 ③）。
  ⚠️ 本 change 只保证「模型愿意抓的时候，判定不再拦着它」。

## Capabilities

### Modified Capabilities

- `crash-perf-issue-fact-cache`：抓取判定 MUST 考虑已存事件条数；
  「计数为正而一条事件都没有」MUST NOT 被判为命中跳过。

## Impact

| 文件 | 变更 |
|---|---|
| `bin/lib/core/cache.sh` | `cache_verdict` 增第 5 个入参「已存事件条数」；⚠️ 纯函数，不读文件 |
| `bin/fetch-snapshot-bq.sh` · `bin/fetch-snapshot.sh` | 调用处传入 `(.events // []) | length`；补抓节流 |
| `bin/test/run.sh` | 现有 `cache_verdict` 用例需补第 5 个入参（⚠️ 调用点会全部报错，正好当清单用） |
| `bin/test/assert-fact-cache.sh` | 事件数对照行增「欠账 N 个」 |

**风险**：落地首轮会让全部欠账记录排队补抓。生产实测欠账 4/6，全仓约 24 个文件——
按默认节流 3 个/轮，约一周收敛完，MCP 调用量增幅可控。
⛔ **不得为了「快点补完」把节流关掉**：那会在一轮里放出几十次 `list_events`。
