## Context

动机与证据见 [proposal.md](proposal.md) 的 Why。这里只记约束。

**今天的结论存储就是表格本身。** `crash-weekly.sh:419-424` 用 awk 从本地台账的 `<!-- LEDGER:ISSUES:BEGIN/END -->` 之间抽出上一版表格 → `render-ledger.sh:54-71` 从中解析出 `id → {first_seen, disposition, note}` → 与本轮机器数据合并重渲。整条链路没有任何独立于表格的持久化。

**两张表的取数语义不同**，这是所有设计选择的分水岭：

| | Issue 现状表 | NON_FATAL 现状表 |
| --- | --- | --- |
| 取数 | 全量（`crash-anr-issues.sql` 注释：「返回全量，末尾 LIMIT 只是安全上界」） | 按受影响安装取头部 |
| 行的寿命 | 常驻 | 滚动，会掉榜 |
| 人工结论列 | 有（首次纳入 / 处置状态 / 备注） | 无 |
| 渲染函数 | `build_rows()`（FATAL + ANR 共用） | `nf_rows()` |

**在途冲突**：`crash-ledger-anr-tracking`（17/22）正在改 `build_rows()` 与 Issue 现状表，剩余任务是部署日人工动作与未验项。本 change 必须绕开它。

## Goals / Non-Goals

**Goals:**

- 人工结论的存活不再依赖「本轮是否被呈现」
- 一份存储同时可服务全部现状表与周报正文，键空间跨 `error_type` 统一
- 结论与机器判定字段在来源上可区分，互不覆盖

**Non-Goals:**

- 本轮不迁移 `build_rows()` 的结论来源（避开在途冲突，见 Context）
- 不做结论的版本历史与审计链
- 不改任何表的入选判据

## Decisions

### D1：独立存储，而不是给 NON_FATAL 表加两列

**决定**：新增 `$STATE/ledger/dispositions.json`，键 `issue_id`，渲染期 join。

**为什么不加列**：加列是无效方案。NON_FATAL 表是滚动榜单，而结论的唯一存续途径是「被解析出来又写回去」——行掉榜即从表中消失，下一轮解析读不到，结论静默蒸发；回榜时是白纸。加列只会让这个丢失过程看起来像「本来就没填」。

**考虑过的替代**：

- *照抄 ANR 的「受影响安装 ≥ 阈值」判据换掉 TopN* ——ANR 过阈值后只有 2 条，能全量常驻，所以那条路对 ANR 成立。NON_FATAL 是千条级（iOS 14 天 1020 条），任何阈值都要么放进太多淹没可读性、要么仍然滚动。⛔ 不可移植。
- *把结论写进 Firebase issue 的 note* ——note 已在人工使用（本轮四条的判读线索正来自 note），但它不可被跑批稳定读取、无结构、且与台账渲染无联系。作为人的备忘有效，作为渲染数据源不可行。

### D2：存储是人工资产，跑批只读

**决定**：跑批对该文件只读；结论字段的任何写入都由人完成。跑批前后文件逐字节一致。

**为什么**：`crash-perf-fix-status-reconcile` 已有「对账只更新机器可判定的列，MUST NOT 覆盖结论性判断」。但现行实现里 `render-ledger.sh:142-143` 在反扫命中时会把 note 覆写成 `commit + subject`——**实现与该 spec 相悖**。把结论挪进只读存储，从机制上消除这种覆写，而不是靠调用纪律。

**代价**：结论更新只能人工进行，没有自动回填。这是刻意的——`crash-ledger-anr-tracking` 的 D4 冷启动同样把「人工订正首次纳入日期」列为任务，本项目已接受此模式。

### D3：NON_FATAL 不纳入 fixmap 反扫

**决定**：反扫继续只作用于 Issue 现状表。

**为什么**：反扫的价值取决于标识约定的遵守率，而实测遵守率不足以支撑自动判定——`847a280c`（修复 `359fadbc`，线上已验证生效）的 message 两种格式都没有，`git log --grep` 完全查不到；`21ef358b` 则合规。若对 NON_FATAL 开启反扫，`359fadbc` 会被渲染成「无修复提交」，与「已验证生效」的人工结论直接矛盾，且机器结论会压过人工结论。

⚠️ 这不等于「NON_FATAL 无需跟踪修复状态」——它由人工结论承载。spec 里把这点写死，避免下次有人把留白读成疏漏。

### D4：周报呈现结论，日报不呈现

**决定**：周报 iOS NON_FATAL 段 join 同一存储并标明「人工结论」；日报不动。

**为什么**：`crash-perf-daily-weekly-report` 的「L1 与 L2 的职责边界」写明 L1 MUST NOT 产出分析、结论或台账。但该 requirement 只说了「产出」，没说「呈现」——本 change 把这个留白补上：L2 可呈现已沉淀结论，L1 不可。理由是日报是当期数据视图，混入既往沉淀的结论会让读者无法分辨判断的时效来源。

### D5：存储不可得时降级，但损坏必须报错

**决定**：文件不存在 → 结论列留空 + 标注不可得 + 跑批继续；文件存在但解析失败 → **报错中止，且不得以空内容覆写**。

**为什么要分开**：这两种情况后果不同。前者是首次启用的正常状态；后者若静默当作空存储，下一次人工写入会基于空文件，**等于永久丢掉全部结论**。这与台账 `block_replace` 定位失败必须报错中止、不得退化为 `overwrite` 是同一条纪律。

### D6：冷启动用本轮四条结论建库

**决定**：首次落地时把 2026-09-23 复核的四条结论写入存储，作为首批数据。

**为什么**：它们既是本 change 的动机证据，也是唯一现成的验证样本——能立刻检验「掉榜后回榜结论仍在」这条最关键的行为。`baa93993`（sk_unknown 哨兵，判为设计内、不需修复）一并入库，它代表「结论 = 无需修复」这个容易被空白掩盖的状态。

## Risks / Trade-offs

- **结论存储丢失（`git clean -xfd` / 换机 / `$STATE` 未备份）** → 它是不可重算的人工资产，spec 已要求纳入与 `last-snapshot.json` 同级的备份范围；部署任务须显式验证备份覆盖到它。
- **`nf_rows()` 增列导致飞书表格排版崩坏** → 列宽只能实发验证（项目既有教训 F29/F30）。部署前须实发私聊并 `docs +fetch` 读回核对，不以本地渲染为准。
- **新增入参跨进程未 `export`** → `REPOS_ROOT` 踩过同样的坑且不报错。`check-scripts.sh` 须覆盖新参数的传递路径。
- **与 `crash-ledger-anr-tracking` 抢改同一文件** → 本 change 只碰 `nf_rows()` 与其调用点，不进 `build_rows()`。⚠️ 若 anr-tracking 在本 change 落地前修改了 `render-ledger.sh` 的入参签名，须以它为准 rebase。
- **人工结论长期不更新而线上已变** → 结论呈现必须标明它是人工沉淀、非当期推导（已写入 spec），读者据此判断时效。本 change 不做过期提醒。

## Migration Plan

1. 建 `dispositions.json`，写入 D6 的五条结论（四条复核 + 一条哨兵判定）
2. `render-ledger.sh` 的 `nf_rows()` 增 join 与两列；`crash-weekly.sh` 传参
3. `check-scripts.sh` 十项跑通（递归扫 `bin/**/*.sh`）
4. `NO_DELIVER` 整跑，核对台账本地产物的两列
5. 实发到私聊，`docs +fetch` 读回核对列宽与排版
6. 周报正文 NON_FATAL 段接入同一存储
7. 部署日人工动作：台账飞书文档 NON_FATAL 表标题下的静态说明补两列解释

**回滚**：移除 join、恢复 `nf_rows()` 原样即可，`dispositions.json` 保留不删——回滚后结论不呈现但不丢失。
