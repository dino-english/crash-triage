## Context

现行卡片版式定稿于 2026-08-22（口径文档「卡片：单表、列 = 平台 × 版本」），回答「各指标是多少」；本 change 要它回答「谁今天要动什么」。数据层、阈值数字、修复四态判定都不动，改的是**分档判定 + 呈现**。

2026-10-11 实测的约束（全部是本 design 的前提）：

| 约束 | 实测 |
| --- | --- |
| `{tag:"table"}` 不能进 `collapsible_panel` | 飞书拒发 `ErrCode 200621 ... not supported tag: table` |
| table 单元格不渲染链接 | 既有实测（spec「issue 级条目提供外部下钻入口」） |
| **markdown 表格语法**在 markdown 块内：渲染为表格、**链接可点**、可进折叠面板 | 用户在客户端点过；⚠️ `messages-mget` 读回时链接被压平，读回不能证明可点性 |
| `column_set` 色底（`red-50` / `orange-50` / `grey-50`）、`button`、`collapsible_panel`、header `text_tag_list`、`chart` 均被接受 | 样稿 B / C / D / W2 实发，`messages-mget` 读回组件齐全 |

## Goals / Non-Goals

**Goals**：卡片首屏只回答「有没有要开发动手的」；每条紧急项自带「为什么」与直达入口；健康度两端分判、只高亮异常；红灯附「是哪部分拖的」。

**Non-Goals**：见 proposal。

## Decisions

### D1 日报分档是确定性规则，判定对象 = 报告版本集

报告版本集 = 最新 2 版 ∪ 告警判定版本（小样本回退结果）。issue 的「7 天台数」= 报告版本集内的受影响安装（FATAL + ANR，与「集中在哪」节同口径）。

| 档 | 条件（任一） |
| --- | --- |
| 🚨 | ① 修复状态 = **修了仍在**，且 7 天台数 > 0 ⟵ `new_build_events` 是累计量，必须叠加近期条件<br>② 未修（无修复映射或状态未知），生命周期 ∈ {新增, 暴涨, 回归}，7 天台数 ≥ `TIER_NEW_MIN`（Q2，建议 2）<br>③ 未修，生命周期 = 长期，7 天台数 ≥ `TIER_LONG_MIN`（Q2，建议 5）<br>④ 判定版本崩溃率 / ANR 率红档（既有 `red_line()` 判据；crash-free 仍不单独告警——被崩溃率覆盖）<br>⑤ 性能版本退化（Q3） |
| ⏳ | 修复状态 = 已修未发版 且 `release_check == ok` 且 issue OPEN（与现 L1 计数同一判定），按 7 天台数降序 |
| 👀 | 其余有信号的项：未修且低于阈值；性能红/黄档（非退化）；已发版待验（只给计数） |

- **一个 issue 只进一档**，优先级 🚨 > ⏳ > 👀。
- ⚠️ 发版判定不可得（`release_check != ok`）时，①与⏳都不判，沿用现有「⚠️ 修复发版判定不可得（N 条）」注记——不得退回只比时间。
- ⚠️ L1 不呈现**人工处置结论**（spec「L1 与 L2 的职责边界」）。⏳ 行展示的修复提交标题是**反扫得到的机器事实**，不是人工结论；周报的「P0」标签 ⛔ 不得出现在日报。

### D2 周报分档由分析层契约驱动，契约失效回落 D1

分析层（`fetch-snapshot.sh` full）新增产物 `$OUT_DIR/priorities.json`：

```json
[{"issue_id":"<32位hex>","platform":"ios|android","priority":"P0|P1|P2","action":"≤40 字","why":"≤40 字"}]
```

脚本侧校验（jq，纯函数）：数组；`issue_id` 匹配 `^[0-9a-f]{32}$` **且出现在 `snapshot.json`**（防编造）；`priority` 枚举；字段长度截断不报错。

| 情况 | 🚨 来源 | 卡片注记 |
| --- | --- | --- |
| 文件合规 | P0/P1（P2 → 👀） | 「模型分析 · 未经人工复核」 |
| 缺失 / 非法 / 校验后为空但快照非空 | 回落 D1 规则（周口径数据） | 「⚠️ 分析层优先级不可用（原因）——以下为规则判定」 |

- ⛔ **`priorities.json` 不进成功判据**（`fetch-snapshot.sh:320-323` 与 `crash-weekly.sh` 的 `report.md` 判据保持两端一致）——缺它只降级，不让整轮失败。
- ⚠️ prompt 没有语法检查、模型未必照办——**唯一可靠检查是产物断言**（同 `FACT_CACHE_POLICY` 的教训）：校验函数夹具 + 整跑后断言。
- 「为什么不解析修复清单段」：写法每周不同（见 Context），正则只会静默漏条。

### D3 判灯按平台分判；慢帧 / 冻结改平台整体 3d 值（Q1）

- 每个健康度数字独立走 `traffic_light()`，⛔ 不再一行一灯。
- 慢帧 / 冻结的**判灯值** = 平台整体 3d（`AVG(screen_info.slow_frame_ratio|frozen_frame_ratio)`，与 `daily-perf-1d.sql` 同算法、换 3d 完整日窗口）。最差页仍取、仍在文档呈现，卡片上作括注「（最差页 X 87.8%）」——⛔ 括注不着红（它不是判灯值）。
- 影响（按 10-11 数据）：Android 慢帧 🔴→🟡（43.6%）、冻结 🔴→🟡（0.51%）；iOS 不变。阈值数字不动。
- ⚠️ 现 `metrics-history.jsonl` 的 1d 平台值与新 3d 值**分开存**，字段名带窗口后缀，⛔ 不混。

### D4 健康度面板取代卡片单表

两列 `column_set`（iOS | Android），每列：判定版本 + 设备/天；crash-free、崩溃率、启动 P95、慢帧、冻结、接口错误率（Android 加 ANR）；紧凑 DoD/WoW 规则不变（spec「核心指标紧凑环比」）。

- **最新版必须可见**（版本口径「让新版本被看见」）：判定版本 ≠ 最新版时，列底加一行「最新版 X · N 设备 · ⚠️ 样本小」。
- **全版本 crash-free 并列**（spec「卡片并列呈现最新版与全版本」）：面板下一行灰字。
- 摘要行三条既有规则原样迁移：必须标版本；无值不判灯；ANR 单端（iOS 不补占位）。
- 底部一行灰字：三段窗口与滞后天数（替代原口径说明块；完整口径留文档）。

### D5 红灯下钻：亮红才出，卡片最多 2 张图

| 红灯 | 维度 | 图 | 样本闸门 |
| --- | --- | --- | --- |
| 启动 P95 | 系统版本分桶（Android：≥13 / 12 / ≤11；iOS 分桶待 T2.4 实测） | 横向条形 + 阈值参考线 | 桶 n < 20 不给 P95（与现 P95 闸门同） |
| 慢帧 / 冻结 | 页面 top3（平台整体值红时） | 横向条形 | 沿用 `perf-screens` 现有 |
| 接口错误率 | 接口 top3 | 横向条形 | 沿用 `perf-network` 现有 |
| 崩溃率 | issue top | 横向条形（周报样稿 W2） | — |

- 图下必须有**一句结论**（哪部分拖的、占比）与**一句历史**（来自 `perf-history.jsonl` / `metrics-history.jsonl`，判定「新问题 / 在改善 / 在恶化」）——读者不必读图。
- ⛔ 不按机型下钻（Context：碎）。
- ⚠️ **深色模式**：样稿写死了 hex 色值，违反 spec「保留项·深色风格主题自适应」。实现改用 `color_theme`；参考线若无主题自适应色，退化为图下文字「红线 2000ms」（T6.3 实发验证后定）。

### D6 卡片组件选型

| 内容 | 组件 | 理由 |
| --- | --- | --- |
| 🚨 每条 / 周报 P0 | `column_set` 色底块（`red-50`）+ `button` | 需一句「为什么」+ 一键控制台；table 截断且无链接 |
| 次要列表 | `collapsible_panel`（默认收起）内 **markdown 表格** | 对齐成列 + 链接可点；table 进不了面板 |
| 健康度 | 两列 `column_set`（`grey-50`） | 两端分判 |
| 标题 | header `template` 随最高档（🚨 red / ⏳ orange / 无 green），`text_tag_list` 三档计数 | 群列表预览即见 |

### D7 文档

- **日报**：头部取数区间不动 → 「一、今日要点」（三档，DocxXML callout 红/橙/灰）→ 二、版本对照（灯按平台分判）→ 三、明细（issue 表加「分档」列）→ 附录（维度、性能明细、非致命、放量、环比、口径）。⛔ 任何既有口径注解不删，只按 spec「口径注解分层呈现」挪位。
- **周报**：头部（取数区间 / run_id / 口径注记，spec 要求在头部）→ 「本周必修」（来自 `priorities.json`，标未经复核；回落时标规则判定）→ 修复进度 → 本周变化（已关闭 / 消失折叠成计数 + 列表）→ 数据层其余段落 → 分析层段落**原样追加**（⛔ 不改其标题层级，`split-fix-list.py` 依赖二级标题）。
- 周报卡片的 commit 只取 subject 首行（现 `_fix_rows` 把正文整段拼入）。

### 实施中的调整（与上文 Decisions 不同处）

- **7 天台数 = 报告版本集内 FATAL 受影响安装**（`crash-issues.sql` 的 `users`，与明细表同源），不是 D1 草稿写的 FATAL + ANR——ANR 无 issue 级行，ANR 超标走指标级规则 ④。
- **文档三档高亮框底色**：🚨 `light-red` / ⏳ `light-yellow` / 👀 `light-blue`（设计稿写的灰色未用）——DocxXML 颜色名在 lark-cli 包内无清单，只用仓库已实际渲染过的颜色名，避免整份文档建不出来。
- **下钻图结论句按数据成句**：10-11 Android 1.8.2 拖慢 P95 的是 Android 14 / 12 / 11 / 10（API 34 的 P95 2330ms 也超红线），不是样稿手写的「11 及以下」。
- **摘要行（文档）灯按平台分判**：`red_line` / `yellow_line` 只列出各自超阈值的那一端；`_alert_body` / `alert_missing` 随之删除。
- **共享常量上移**：`CRASH_RATE_RED/YELLOW`、`TIER_NEW_MIN/LONG_MIN` 从 `crash-daily.sh` 顶部移到 `bin/lib/common.sh`——周报的红灯下钻与回落分档也要判它们，两个进程各写一份必然漂移。
- **周报卡片的图收敛为两类**：红灯下钻（主力版本崩溃率红档 → 按 issue 拆，只画最差的一个版本）+ 启动 P95 趋势（Q4）。「三类事件构成」「崩溃页面 TOP5」移出卡片：前者的数字在主力版本表里，后者在文档「三、影响面分布」。
- **P95 趋势图的样本闸门**：`perf-history.jsonl` 新增字段 `n`（`_app_start` 样本数）；有 `n` 的行按 `PERF_P95_SAMPLE_MIN` 过滤，旧行（无 `n`）去掉该版本首次出现那一周——版本首周样本最少，09-28 Android 1.8.1 首周 7784ms 正是这种点。
- **周报回落规则的生命周期**取本周变化检测的桶（新增 / 回归 / 暴涨），`tier_classify` 因此支持「📈暴涨」与新增、回归同一门槛。周报回落时 ⏳ 归「🔧 修复进度」段，不另起一档。
- **性能退化（规则 ⑤）加会话门槛**（2026-10-12 生产首轮监控发现）：两版日会话都要 ≥ `SAMPLE_SESSION_MIN`(213) 才比（`cmp_prev_ver_of`），下钻图的「对比上一版」同一门槛。首轮 Android 1.8.1 正在退场（日会话 30 vs 1.8.2 804），慢帧 30.1%（前一窗口 46%）、接口错误率 0.4%（13/2814）被比出两条误报 🚨。帧数闸门挡不住——991 帧早过 20，问题是剩下那批用户不代表大盘。夹具 `fn-perf-regress-gate.sh` 用当日生产数值。
- **下钻图条数上限 8**：按版本号降序截 6 会正好切掉最老、最慢的那一桶（10-11 DRY RUN：Android 10 P95 5787ms 被截掉）。

## Risks / Trade-offs

- **阈值拍得不准 → 🚨 天天空或天天满**：T1 用生产历史 run 回测分档分布，再定 Q2。
- **周报模型不遵守契约**：D2 回落 + 显式注记；首轮整跑后断言 `priorities.json` 合规。
- **紧急档变少被读成「变好了」**：标题与 🚨 段在空时写「今日无需开发处理」并给出 👀 计数，不留白。
- **改判灯值后 Android 慢帧 / 冻结从红变黄**：是口径修正不是改善——首轮卡片底部注明「慢帧 / 冻结判灯改为平台整体值（原为最差页）」，保留一周。
- **长任务**：日报 3011 行，卡片构建与文档渲染两处定义点（F29/F30/F35）——每个定义点都要实发 + 读回验证。
