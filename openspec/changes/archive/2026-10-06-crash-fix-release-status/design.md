## Context

修复状态由 `scan-fix-commits.sh:141-143` 判定：取事实层里该 issue 最晚事件时间，晚于修复提交 → 「修了仍在」，否则 → 「已修待验」。判据只有时间，**看不见事件发生在哪个包上**。

L1 与 L2 各自跑一次反扫（`crash-daily.sh:1402`、`crash-weekly.sh:222`），产出两份独立 fixmap。L1 用它数「已修待验 且 OPEN」报成「🔴 代码已修但未发版」（`crash-daily.sh:1408-1419`）——文案说发版，判据与发版无关。L2 用它渲染卡片 `_fix_rows` / `_chg_rows`、台账「处置状态」列与变更时间线。

2026-10-06 实测的数据约束（全部是本 design 的前提）：

| 约束 | 实测 |
| --- | --- |
| crashlytics REALTIME 只留 30 天 | 两端最早 09-06；批量表 07-17 起且仍在更新（10-05） |
| sessions 无长期表 | 批量表 08-11 停更，REALTIME 09-06 起 ⇒ 08-11~09-06 的 build 首现不可得 |
| iOS 内部包极密集 | 1.8.0.x 内部包隔几小时一个，1–6 台设备，性能采集**全关**；上架包 1.7.1.2 2790/2790 台全开 |

## Goals / Non-Goals

**Goals**：四态判定（修了仍在 / 已发版待验〔可带「旧包仍崩 N 次」备注〕/ 已修未发版 / 状态未知）；L1 告警按真「未发版」计数；两端同一套状态名。

**Non-Goals**：见 proposal。另：不修 `render-ledger.sh` 上一版表格查找键不匹配（链接写法 vs 短 id）——另起修复，见「已知相关缺陷」。

## Decisions

### D1 判据是「事件所在的包是否含修复」，不是时间

一个 issue 在修复提交之后的事件按「所在 build 是否含修复」二分：

- 含修复的包上有事件 → **修了仍在**
- 否则，若「含修复的包已上线」→ **已发版待验**；不含修复的包上仍有 N 次事件时加备注「旧包仍崩 N 次」
- 否则 → **已修未发版**
- 拿不到 build 信息（查询失败）→ 保留时间规则的结果，标注「发版判定不可得」（见 D6）

*为什么「旧包仍崩」不单独成态*：处置方式与「已发版待验」相同（等用户升级），只是提示量级；多一态就多一个图例、多一处渲染分支（用户 2026-10-06 选定）。

### D2 「含修复的包」与「已上线」按端用不同判据

| | iOS | Android |
| --- | --- | --- |
| 含修复的包 | 修复提交之后**首次出现**、且性能采集设备数 > 0 的 build | 版本号 ≥ `fixed_in_version` 的 build |
| 已上线 | 存在上面这样的 build | `release_ref` 非空（提交在 `origin/main` 或任一 `V*` tag 中） |
| `fixed_in_version` | 不用 | 最早包含提交的 `V*` tag 的版本号；仅在 main 无 tag 时为 null → 退回 iOS 式判据（首现晚于提交的 build） |

**iOS 为什么不用 tag**：缺 v1.8.1 / v1.8.2，且修复提交多为 cherry-pick 进发版分支、hash 变了（4/4 不在任何 tag 祖先链上）。

**iOS 为什么排除内部包**：内部 adhoc 包隔几小时一个，且不一定出自含修复的分支。把它们算作「含修复的包」，一次内测崩溃就会判成「修了仍在」——2026-09-23 复核 `c3184f91` 正是这种情况（1.8.0 的 10 次全来自内测包、走另一条代码路径）。内部包上的事件计入「旧包 / 内部包」N，**呈现但不改判**。

**Android 为什么用 main / tag 而不是设备数**：用户决定（2026-10-06）。tag 已在 15 条上验证。build 首现推断有一类必错：1.7.1 在 62f88f39 修复的**同一天**上线，但出自不含修复的分支——只比时间分不出来，tag 能（它说要到 V1.8.0）。

**Android 版本号比较**：在 jq 里拆成数字数组比较（`split(".") | map(tonumber)`），⛔ 不在 SQL 里比（口径文档 :128 既有做法是脚本侧 `sort -V`），⛔ 不从 versionCode 反推版本号（182010 → 1.8.2 的编码依赖 minor/patch < 10，且末 3 位是 CI 序号）。

### D3 事件取 crashlytics 批量表 ∪ REALTIME，按 `event_id` 去重

只查 REALTIME（30 天）会漏掉修复之后、30 天以前的事件：实测 `a34175e5` `ce481263`（修复 08-19）在 REALTIME 里 0 次，批量表里 1 / 7 次。

### D4 build 首现取四张表的最早时间，并接受 08-11~09-06 的空洞

`first_seen(build) = MIN(event_timestamp)` over sessions REALTIME ∪ sessions 批量表 ∪ crashlytics 批量表 ∪ crashlytics REALTIME。

空洞的后果是**偏保守**：那段时间首现、且没崩过的 build，首现会被推迟到 09-06。实测影响：Android 1.5.4 / 1.5.5 落在空洞里，判据把首个发版包认成 1.5.6——「已发版」结论不变（tag 说 1.5.4）。iOS 侧同理，只可能把「已上线」推迟，不会提前。

⛔ 不为空洞加特判：唯一的修补是找回 sessions 的那段数据，不存在。

### D5 L1 反扫前 fetch 业务仓库

Android 的「已上线」读 `origin/main` 与 tag，而 L1 从不 fetch（只有 L2 周一 fetch，`crash-weekly.sh:128`）。不 fetch 的后果：周二合进 main 的修复，L1 要到下周一才不再报「未发版」——**每日告警会持续误报 6 天**。

照抄 L2 的同一条命令（`fetch --all --tags --prune`，不 checkout / reset）。⚠️ fetch 失败不中断 L1，但 MUST 在卡片标注「仓库未同步，发版判定可能滞后」——不得静默用旧 refs 出结论。

### D6 新子脚本失败时的降级必须可见

`fix-release-status.sh` 依赖 bq，可能失败。失败时：

- 输出原 fixmap（时间规则的状态），每条加 `release_check: "unavailable"`
- 渲染处在状态后加「（发版判定不可得）」
- L1 告警**不计数**（宁可少报「未发版」也不把时间规则的结果当发版判定报出去——这正是本 change 要消除的错）
- 退出码非零，调用方 `|| RC=$?` 捕获后照常往下走（与 `fetch-issue-states.py` 同构）

⛔ 不得把失败静默降级成两态：那会让读者以为发版判定照常生效。

### D7 判定是纯函数，SQL 只取数

`fix-release-builds.sql` 只输出原始行：`(issue_id, build, display_version, first_seen, perf_on_devs, events_after_commit)`，外加一份 build 清单 `(build, display_version, first_seen, perf_on_devs)`。四态判定写在 `bin/lib/` 的 jq 函数里，夹具直接喂 JSON 测，不碰 bq（遵循 `crash-perf-functional-core` 的分层）。

SQL 的 fixmap 输入经占位符注入为 `UNNEST([STRUCT(...)])`，⛔ 只替换值（口径文档 :144）。issue_id / commit 都是十六进制，注入前校验 `^[0-9a-f]+$`，不合规的条目跳过并记日志。

### D8 图标沿用 L1 图例已有的两个

L1 索引页图例（`crash-daily.sh:2676-2680`）早就写了「🛠️ 代码已修·未发版」「📦 已发版·观察中」，只是从没有代码产出。本 change 让它们成真：

| 状态 | 图标 |
| --- | --- |
| 修了仍在 | ⚠️ |
| 已发版待验 | 📦 |
| 已修未发版 | 🛠️ |
| 状态未知 | ❔ |

`md2docx.py` 已有 🛠️（橙）/ 📦（蓝）/ ⚠️（橙）的上色规则，无需改。⚠️ 现「🛠️ 代码已修待验」的 🛠️ 语义变了（从「没再崩」变成「未发版」），图例与卡片文案须同轮改齐。

## Risks / Trade-offs

- **iOS 上架包判据依赖性能采集开关**：若某次上架包误关采集，该版会被当作未上线 → 修复显示「已修未发版」。可见、偏保守；口径文档已记录该开关「上架全开、adhoc 全关，30 天双向干净」。
- **iOS TestFlight 包**：开采集、设备少（实测 1.7.0.15：1/1 台）——会被当作「已上线」。影响是「已发版待验」略早出现，不会把「修了仍在」说成别的。接受。
- **Android 热更新不打 tag**：同版本号热更新包若含修复但没打 tag、也没进 main，会一直判「已修未发版」。依赖团队打 tag，用户已知悉并选择「暂时」用 main / tag。
- **状态文案变化会让台账整表 `block_replace` 一次**：指纹按列名算（`deliver.sh:536-578`），部署后首轮必然重写，属预期。
- **L1 每天多两次 fetch 与 2–4 条查询**：fetch 秒级；查询扫四张表，需实测耗时与扫描量后写进 tasks 验收。
