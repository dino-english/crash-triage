## Context

动机与生产数据见 [proposal.md](proposal.md)。这里记实现约束。

**实施期修正（2026-09-09）**：提案写的是「调用处传入 `(.events|length)`」，
实际排查后发现**两条路径的判定不在同一个地方**：

| 路径 | 判定在哪 | 抓取成本 |
|---|---|---|
| `fetch-snapshot-bq.sh`（bq） | `cache_verdict`，确定性 shell | **零**——bq 路径本来就拿不到事件明细，`append` 是空操作 |
| `fetch-snapshot.sh`（模型） | prompt 的「判定一」，自然语言 | 一次 `crashlytics_list_events`，**这才是真钱** |

所以「让判定看得见内容」在两条路径上是两件不同的事，节流只对模型路径有意义。

## Decisions

### D1 · 欠账清单由 shell 算，抓取交给模型

⛔ **不在 prompt 里让模型自己判断「数组是不是空的」**。它已经被证明会跳过读文件这一步
（2026-09-08/09 连续两轮自陈「权限阻断」却仍报「命中 N 个（跳过）」）。
改为：`fetch-snapshot.sh` 在组装 prompt **之前**扫一遍 `$ISSUES_DIR`，
算出「计数 > 0 且 `events` 为空」的 id 清单，取前 N 个**显式写进 prompt**：
「以下 issue 的事实层缺事件明细，本轮对它们全量抓取，忽略计数判定」。

这与本仓库既定的分工一致——**能确定性算出来的不交给模型**，模型只干它擅长的抓取。
⚠️ 也因此节流天然落在 shell 手里，不依赖模型「自觉少抓」。

### D2 · `cache_verdict` 仍要加第 5 个入参

bq 路径的 `append` 虽是空操作，判定语义仍必须正确——它产出的
`FETCH_NEW/APPEND/SKIP` 计数会进跑批日志，是人判断「事实层在不在工作」的依据。
⛔ 让它继续把欠账记录报成「跳过」，等于日志在说谎。

判定顺序（⚠️ 顺序不可换）：强制重抓 → 文件不存在 → **欠账** → 计数上涨 → 跳过。

### D3 · 判据只取「已存 == 0 且计数 > 0」

⛔ 不做「短缺比例」。`events` 是累积数组、计数是滚动窗口，两者不可比
（上个 change 的 findings F-5，实测开发机 110 vs 29 是正常态）。
「一条都没有」是唯一无歧义的欠账信号。

### D4 · 节流默认 3，且**先算清单再截断**

`CRASH_REPORT_BACKFILL_LIMIT`（默认 3）。清单按 id 排序后取前 N——
⚠️ **不随机、不按计数排序**：每轮取同一批直到它们被补上，
才能让「欠账数逐轮下降」成为可观测的收敛信号（tasks 4.3 的验收判据靠它）。

## Risks / Trade-offs

- **模型可能仍旧不抓**：本 change 只保证「判定不再拦着它」，抓不抓仍取决于模型。
  ⚠️ 这正是 tasks 4.3 要求连续 3 轮观察欠账数的原因——⛔ 不得以「代码路径对」结案。
- **首轮生产欠账 18 个**（2026-09-09 实测，24 个文件）：按 3/轮约 6 轮补完，
  且只有出现在当轮快照里的 issue 才会被处理，实际会更慢。⛔ 不得为图快关掉节流。
