# 实施期发现

## F-0 · ⛔⛔ 「事件已出窗抓不到」是**我判错的**——7 天只是默认值，能查 90 天

⚠️ **本节推翻 F-1 的一半结论，F-1 原文保留在下方以留痕。**

`crashlytics_list_events` 的 `intervalStartTime` 文档原文：
「**Must be within the last 90 days. Defaults to 7 days ago**」。
7 天是**默认值**，不是能力边界——显式传区间就能查 90 天内的任何事件。

**裸调 MCP 实测**（不经模型，`npx firebase-tools mcp --only crashlytics` + JSON-RPC）：
`87073ca8`（`latest_event` 2026-08-17，我标成「抓不到」）把窗口放宽到 60 天后
**完整返回事件**——`eventTime 2026-08-17T13:06:24Z`，device / memory / 堆栈字段一应俱全。

所以：

| 我当时的结论 | 实际 |
|---|---|
| 13 条已出窗、抓不到 | **13 条现在就能补**，只是没人把窗口放开 |
| `11e188d1` 空手而归 = 抓不到 | 模型用了**默认 7 天窗**；欠账记录的事件多半在 7 天之外 |
| 按 7 天窗剔除候选 = 修复 | ⛔ 反而把**本可补**的 13 条永久排除，比它修的饥饿更糟 |

**订正后的做法**：
- 判「抓不到」的分界是 **API 保留期 89 天**（取 89 不取 90，边界留余量），不是取数窗口；
- 补抓时 prompt **必须要求显式传 `intervalStartTime` / `intervalEndTime`**，
  ⛔ 不传就会空手而归、看起来像「抓不到」，其实是没去要。

⚠️ **这条错误的成因值得单独记**：我用「一个数据点 + 一个推断」下了结论
（`11e188d1` 抓空 + 推断 7 天窗是硬边界），而验证它只需要一次裸 MCP 调用。
**手上有直接测量的手段却先去推断，这是本次系列改动里代价最高的一次判断失误。**

## F-1 · ⛔ 节流按 id 排序会被「抓不到的记录」永久占位（2026-09-10 生产首轮发现）

⚠️ **本节的「抓不到」判据已被 F-0 推翻**——饥饿现象与修法（先筛选再排序）仍成立，
但「哪些算抓不到」从 7 天窗改成了 89 天保留期。原文保留：

**首轮结果是好的**：欠账 18 → 15，已存事件合计 6 → 17，模型统计行
「未命中 3 个（全量抓取）」——注入 prompt 的清单确实驱动了抓取（那 3 个 id
**不在本轮 topIssues 快照里**，模型不会自发去碰它们，这是机制生效的硬证据）。
清单里 3 个补上 2 个：`1c2dd231` 0→1、`20559a5e` 0→1。

⛔ **但没补上的那个暴露了设计缺陷**。`11e188d1`：计数 5、`latest_event` 是
**2026-08-29**、`source:"bigquery"`。它的事件早已滑出 7 天窗，`list_events`
查不到任何东西——**这条记录永远补不上**。

而节流是「按 id 排序取前 3」（design D4，理由是「每轮取同一批直到补上，
欠账数才能成为可观测的收敛信号」）。⛔ 这个理由在「补不上」的记录面前反过来了：
它会**每轮占住一个名额，直到天荒地老**。

**量化（2026-09-10 生产 15 条欠账）**：

| | 数量 | id |
|---|---|---|
| 窗口内、**可补** | **2** | `63db031f`（09-06）· `e87dae39`（09-05） |
| 已出窗、**抓不到** | **13** | `11e188d1` `26335e5d` `2a800b33` `30805a61` `3769bd8d` `424473ed` `470ed3ef` `85c581ed` `87073ca8` `a34175e5` `a7af5911` `ce481263` `fa48b2eb` |

按 id 排序，前三名 `11e188d1` `26335e5d` `2a800b33` **全部不可补**。也就是说
**从下一轮起，补抓会一次都不再成功**，而两个真正可补的 `63db031f` / `e87dae39`
永远排不到号——⚠️ 今天能补上 2 个纯属侥幸：那两个 id 恰好排在第 2、3 位。

**修法**：候选清单先剔除「`latest_event` 早于抓取窗口」的记录，再排序；
被剔除的单独报「不可补 N 个（事件已出窗）」。⛔ 不能只是改排序——
不可补的记录仍会混在「欠账」这个数里，让 tasks 4.3 的收敛判据永远不达标。

⚠️ 「出窗即抓不到」目前是 **1 例实测 + 机制推断**（`11e188d1` 本轮被写过但事件数仍 0）。
修法本身不依赖这个结论成立：把它们从**候选**里剔除只影响名额分配，
真要验证得等某条出窗记录在后续轮次仍补不上。

## F-2 · 「欠账」这个数把两类记录混在一起

`欠账 = 计数 > 0 且 events 为空` 同时包含「还没抓」与「抓不到」。
前者会收敛，后者不会。⛔ 用一个混合数当收敛判据（tasks 4.3）**永远不会达标**，
而看数的人会以为补抓坏了。断言的输出要把两者分开报。

## F-3 · 真正的根因有两个，都在 `--allowedTools` 与 prompt 里，且都是一次裸 MCP 调用就能测出来的

2026-09-10 当天用裸 MCP（`tools/list` / `resources/list` / 工具描述）测出来的：

1. **模型不是在撒谎**。`crashlytics_get_report` 的描述原文要求
   「must read the Reports Guide **using the `firebase_read_resources` tool** before calling」，
   而 `--allowedTools` 里没有这个工具——它回报的「读取 Guide 的权限未获授权」**字面属实**。
   ⚠️ 记忆 `model-misreports-io-error-as-denied` 因此已订正：那半个月的「模型爱撒谎」是误判。
2. **`list_events` 的 `pageSize` 默认是 1**。prompt 从没传过它，所以事实层每个 issue
   永远只存 1 条事件。同一批 24 个 issue：不传共抓 24 条，传 `pageSize=50` 抓 **185 条**。

**存量修复（一次性，非流水线）**：裸 MCP + 88 天窗 + `pageSize=50`，只 append 不改写已有记录，
写回前备份到 `$STATE/backup/pre-backfill-20260910`。结果：事件 **6 → 185**、
待补 **15 → 0**、不可补 0、非法 JSON 0、断言通过。

**下游兑现（这才是这批数据存在的理由）**：

| 周报 | ✅ 钻取确认 | ⚠️ 聚合推断 |
|---|---|---|
| 2026-09-07（补齐前） | **0 处** | **12 处** |
| 2026-09-10（补齐后） | **4 处** | **0 处** |

⚠️ 遗留：`62f88f39` 有 8 条早期退化格式条目（只有 `eventId` + `raw_mcp_output`，无 `eventTime`），
API 已取不回对应事件，⛔ 保留不删——它们仍是「该事件存在过」的证据。
`scan-fix-commits.sh` 读 `.events[].eventTime` 时会少算这 8 条，影响面仅限该 issue 的时间线。
