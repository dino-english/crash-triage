## D1 — 给分数不给百分比

基准实测只有 **14 个 key**。1 个回归 = 7.1%、2 个 = 14.3%——百分比在这个分母上是伪精度，且周与周之间的跳动会被读成趋势。

分数形态 `2 / 14` 自带分母，符合「任何比率都要能说出分母」这条既有约束。

## D2 — 三态必须可区分，⛔ 基准未建立时不显示 0

| 状态 | 渲染 |
|---|---|
| 基准未建立 | `本轮建立基准，复发率下轮起可用` |
| 已建立、无回归 | `0 / 14（无 issue 回归）` |
| 已建立、有回归 | `N / 14（N 个 issue 在上一轮窗口内无事件，本轮重新出现）` |

⛔ 基准未建立时显示 `0 / 0` 或 `0%` 会让「没有回归」与「还没法算」长得一样。

⚠️ **`SEEN_WAS_ESTABLISHED` 必须在 `render-ledger.sh` 之前判**——跑批收尾会把基准覆盖成本轮值，之后再判永远是「已建立」。这与既有约束「基准提升必须在渲染之后」是同一条时序。

## D3 — 数已渲染的表，不重算判定

三态判定在 `render-ledger.sh` 里已经实现。复发数直接 `grep` 现状表的状态列。

⛔ 在 crash-weekly.sh 里重算一遍必然与表格漂移——失效模式 F4（同一个值多来源）刚在本仓库造成过历史日期被覆盖。

⚠️ `grep -c … || echo 0` **不能用**：零匹配时 grep 既输出 `0` 又返回 1，两边都执行会得到 `"0\n0"`，后续整数比较直接报错（失效模式 F21，本 change 实施时踩到）。

## D4 — 已知边界

⚠️ 台账取数带 `LIMIT 20`。issue 总数逼近 20 时，掉出榜单再回来会被误计为回归。实测 Android FATAL 7d 唯一 issue 数 **13 < 20**，暂未咬合——但这是个会随崩溃数增长而触发的隐患，触发时复发数会虚高。
