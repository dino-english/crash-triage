## Why

**三份产物描述同一批 issue，但读者无法确认哪两行说的是同一条崩溃。**

起因是 2026-09-01 的一次人工比对：拿一份「崩溃认领」文案去核 08-31 周报，核不上。逐条查完发现**认领是对的**——它的四条数字逐字来自 08-31 日报，BigQuery 复算全部吻合：

| 认领文案 | 08-31 日报 | BigQuery 实测（08-24~08-31 整日窗） |
|---|---|---|
| iOS `2a800b33` 1 次 / 1 人 | 日报 iOS 1.5.4 段 `1 / 1` | 1 事件 / 1 安装，`iPhone9,3` · 15.8.8 |
| Android `11e188d1` 5 次 / 1 人 / 4 会话 | 日报 Android 1.5.6 段 `5 / 1` | 5 事件 / 1 安装 / 4 会话 |
| Android `62f88f39` 1 次 / 1 人 | 日报 Android 1.5.6 段 `1 / 1` | 1 事件 / 1 安装 |
| 补充 `63db031f` 1 起 | 日报 Android 1.5.6 段 `1 / 1` | 1 事件 / 1 安装 |

核不上的是**周报**，而且第一次比对时连「同一条 issue」都没认出来——`11e188d1` 在认领里叫「Media3 初始化 NoSuchMethodError」（异常类型），在周报段一叫 `AudioPlaybackService.ensureMediaSession`（责任帧），**段一不带 issue id，只能靠标题猜，于是猜错了**。

三个可定位的缺口：

**1. 周报段一（变化摘要）不带 issue id。** `crash-weekly.sh:765-767` 只输出 `.title` 与 `.events`。它是周报里唯一覆盖全版本的一段，也是唯一会报告「变化」的一段——最需要被交叉核对的地方恰恰无键可核。实测危害：`11e188d1` 打印「📈 暴涨 · 13 事件」，而这 13 个事件是 1.5.4 占 8、1.5.6 占 5，读者看到的是一个跨版本合计数，无从知道新版占了多少。

**2. 周报段一没有「回归」态，回归被渲染成「新增」。** `crash-weekly.sh:265` 的定义是：

```
new: [ $n[] | select($om[.id] == null) ]     # 只跟上一周快照比
```

一条「以前有过、上周没有、这周回来了」的 issue 与一条全新 issue 落进同一个桶。而台账用 `issue-seen.json` 的 90 天基准能区分三态。同一轮跑批因此可以自相矛盾——实测 2026-08-31：`2a800b33` 在日报是「长期」、在台账与周报是「🆕新增」。

spec `crash-perf-issue-lifecycle` 已经要求 issue 明细与台账现状表覆盖三态，**但周报的变化摘要不在其覆盖面内**，属规格空白而非实现违规。

**3. 标识形态四种并存。** 同一条崩溃在产物里有四个名字：责任帧标题、人写的异常描述、8 位短 id、32 位完整 id。分析层产出的报告用 32 位（`### 62f88f3900a1313c994871bf51c65f81`），数据层用 8 位——`crash-weekly-report-composition` 归档后两者会出现在同一份文档里。

**4. 台账图例把「消失」与「关闭」写成一格。** 图例写「✅已消失/已关闭」，而周报正文自己的口径注解写着「『消失』是**窗口内无事件**，⛔ 不等于『已修复』」。两者矛盾，且**「关闭」这一态根本取不到**：实测 BigQuery Crashlytics 导出的 schema 里与 issue 相关的字段只有

```
issue_id   issue_title   issue_subtitle
```

没有任何 state / closed / regressed 字段。要拿 OPEN/CLOSED 只能回 MCP `topIssues`，而那条通路只返回 OPEN（关闭即从列表消失），正是 `crash-source-bigquery-migration` 当初迁走的原因，且 2026-08-06 有过误关线上 issue 的事故。**做不到的事必须登记成做不到，不能留一个图例让读者以为它在工作。**

## What Changes

- **周报段一每条变化带 8 位 issue id 与版本分布**：`🆕 新增 [<8位>] <标题> · <总事件> 事件（1.5.6 5 · 1.5.4 8）`。版本分布让「跨版本合计」不再伪装成单版本数字。
- **周报段一补「🔁 回归」态**：判据改用与台账同一份 `issue-seen.json` 基准（90 天，取基准中最大 `last`），与 `crash-perf-issue-lifecycle` 既有三态定义对齐。⛔ 不新建第三份基准。
- **台账变更时间线条目带 8 位 id**。
- **id 形态统一为 8 位短 id + 一条 Firebase 直达链接**；分析层追加段内的 32 位 id 保持原样不改写（模型产出不动，见 Non-goals）。
- **台账图例拆开**：`✅已消失（窗口内无事件，≠ 已修复）`，删去「/已关闭」。
- **登记「issue 开关状态不可得」**：写进 `crash-source-bigquery-migration`，附实测 schema 证据，避免下次有人按「字段应该有」去找。

## Non-goals

- **不改主力版本判据**。周报三段主体在描述已退役版本（实测 08-31：1.5.6 承载 855 会话 / 93%，而周报主力版本是 1.5.4 的 20 会话与 1.5.5 的 46 会话）——这是真问题，但动的是口径，风险等级不同，走独立 change 并经 `crash-metric-change` 校验。本 change 只做呈现层，**零口径改动**。
- **不砍掉段三段四的维度与下钻**。「用直达链接替代静态复刻」属内容设计取舍，且会部分回退刚完成的 `crash-issue-drilldown`，需先定方向，走独立 change。
- **不统一 L1 与 L2 的生命周期基准**。两套基准的分离有明确理由（L1 带版本过滤、L2 不带，见 `crash-perf-issue-lifecycle`「L2 生命周期基准独立于 L1」）。本 change 只要求**当两份产物对同一 issue 给出不同生命周期标签时，各自标明自己的基准口径**，不合并基准。
- **不改写分析层产出的 id 形态**。模型报告按 triage skill 自己的模板成文，脚本改写其正文会与 `crash-weekly-report-composition`「标题层级零改动」的约束同源地脆弱。
- **不引入 MCP 取 issue 开关状态**。只登记不可得。

## Capabilities

- `crash-perf-issue-lifecycle`（修改）：新增「周报变化摘要 MUST 区分回归与新增」「同一 issue 在不同产物出现不同生命周期标签时 MUST 标明基准口径」两条要求。
- `crash-perf-daily-weekly-report`（修改）：新增「issue 级条目 MUST 可被唯一标识」要求，覆盖日报明细、周报变化摘要与下钻、台账两张表与时间线。
- `crash-perf-ledger-ownership`（修改）：时间线条目 MUST 带 issue 标识；图例 MUST NOT 把「消失」与「关闭」并列为同一态。
- `crash-source-bigquery-migration`（修改）：新增「issue 开关状态不可得」登记要求。
- `crash-perf-data-analysis-split`（修改）：「产出显式标注分析层状态」扩展为同时要求标注实际执行分析的模型标识与端点归属。
