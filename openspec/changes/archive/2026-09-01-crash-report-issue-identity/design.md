# 设计：issue 标识与生命周期对齐

## D1 · 为什么是 8 位短 id 而不是 32 位

三份产物已有的 id 呈现全是 8 位（`crash-daily.sh:1752` 的 `${fid:0:8}`、`render-ledger.sh:78` 的 `.id[0:8]`、周报段四下钻）。改成 32 位要动三处已稳定的渲染，且 32 位在卡片与表格里会撑爆列宽（`CELL_BREVITY` 那条约束的同一类问题）。

8 位的碰撞风险已有既定处置：`scan-fix-commits.sh` 对「8 位短 id 撞到多个 issue」的做法是**不自动更新、标为待人工确认**。本 change 沿用该判据，不新造一套。

⚠️ **分析层追加段里的 32 位 id 不改写**（Non-goals）。同一份文档里两种长度并存是刻意接受的：改写模型正文属于对 triage 产出的结构性干预，与 `crash-weekly-report-composition` D2「标题层级零改动」同源——脚本对模型文本做正则改写，改不中时静默失效。代价是读者在分析段看到长 id，缓解手段是数据层每条都给 Firebase 直达链接，链接里本来就是 32 位。

## D2 · 回归态复用台账基准，不新建第三份

周报段一现在只跟**上一周快照**（`last-snapshot.json`）比，所以判不出回归。台账走的是 `issue-seen.json`（90 天，取基准中最大 `last`），已经能判三态。

选择复用而不是给段一新建基准，理由有三：

1. 同一轮跑批里两段用不同基准，正是当前「台账标 🔁回归、周报标 🆕新增」这类矛盾的来源；
2. `issue-seen.json` 的保留期、清理、「上一轮取最大 `last`」三条规则都已在 spec 里定死并踩过坑，复制一份等于把三个坑重开一次；
3. 基线提升的时序约束（MUST 在 `render-ledger.sh` 之后）已经存在，段一读取只是多一个读者，不改写入时序。

⛔ **读取点必须在基线提升之前**。`issue-seen.json` 在本轮末会被提升为「全部 issue 的 `last` = 今天」，提升后再读会让每条都判成「长期」——与 `render-ledger.sh` 踩过的是同一个坑，只是方向相反（那边是三态永远只渲染「遗留」）。

## D3 · 版本分布放在事件数之后，不新起一列

段一是项目符号列表不是表格，加列无从谈起。形态定为：

```
- 🆕 新增 [11e188d1] com.…AudioPlaybackService.ensureMediaSession · 13 事件（1.5.4 8 · 1.5.6 5）
```

⚠️ **版本分布只在跨版本时出现**：单一版本时括注退化成噪音。判据是「该 issue 在窗口内的 distinct 版本数 > 1」。

⛔ **括号一律先条件赋值再拼接**，禁 `${var:+（...）}`——全角括号会被 bash 并进变量名（CLAUDE.md 常驻约束，`check-scripts.sh` 第二项会拦）。

## D4 · Firebase 直达链接的构造

链接形态（两个 app id 已在台账「项目常量」段登记）：

```
https://console.firebase.google.com/v1/appid/project/dino-english-497507/crashlytics/app/<APP_ID>/issues/<32位 issue id>
```

⚠️ **32 位 id 必须来自数据本身**，不能由 8 位短 id 拼回去。取数层拿到的就是完整 id，只在渲染时截断——所以链接与显示文本各取所需，不需要反查。

⛔ **链接只加在文档，不加进卡片**。卡片单元格是 `lark_md`，一条 URL 会把列宽撑爆，与「⚠️ 数据未同步（截至…）」被截断是同一个失效模式。

## D5 · 图例：消失 ≠ 关闭 ≠ 已修复

三个词现在混用：

| 词 | 真实含义 | 数据来源 |
|---|---|---|
| 消失 | 滚动窗口内无事件 | BigQuery，可得 |
| 已修复 | 代码已改并发版 | commit 反扫，**当前失效**（见下） |
| 已关闭 | Firebase 控制台上 issue 状态为 CLOSED | **不可得** |

图例改为 `✅已消失（窗口内无事件，≠ 已修复）`，删去「/已关闭」。

⚠️ 「已修复」那一列当前也是死的：实测 `git log --all --grep='\[crash:' --since='30 days'` 在 iOS 仓库零命中——commit `29a20dc5` 写的是 `Crashlytics issue: <32位>` 而非约定的 `[crash:<8位>]`。**本 change 不修它**（属独立问题，改正则还是改约定需要与 iOS 侧确认），但图例注记要如实反映：处置状态列可能因约定未被遵守而停留在上一轮。

## D6 · 验收无法靠 DRY_RUN

段一的渲染在 `CHANGES_MD` 生成阶段，DRY_RUN 打完卡片预览就 `exit 0`，跑不到文档渲染。验收必须用 `CRASH_REPORT_NO_DELIVER=1`。

⚠️ **L2 的基线提升在 NO_DELIVER 闸门之前**，「跑两次对比产物」在 L2 不成立——测试前先备份 `last-snapshot.json` 与 `issue-seen.json`（`baseline.sh` 的快照回滚协议已覆盖，但手工跑要自己备）。

⚠️ 回归态无法用活数据验证（需要构造「曾有、上轮无、本轮有」的基准）。用夹具跑：手工构造 `issue-seen.json` 与两份快照，断言三态各出现一次。函数级测试 MUST 跑在 `bin/test/harness.sh` 的生产 shell 设置下。

## D7 · 段一同时进卡片与文档，链接只能进文档

⚠️ **`CHANGES_MD` 是单一变量，被卡片（`crash-weekly.sh:1115` 的 markdown 块）与文档（`:1057`）共用。**
往它里面加 Firebase 链接，链接会**同时出现在群卡片里**——一屏十几条变化每条挂一个 console URL，
版面立刻不能看。

⛔ **不要为此复制出「卡片版 CHANGES_MD」与「文档版 CHANGES_MD」两份**。那正是 F35 的形状：
卡片表格的列集合有两个定义点，改一处就让预览与实发不一致。

做法：`sec()` 增一个「是否带链接」的参数，卡片与文档各调一次同一个函数。**一个定义点，两次调用**。

⚠️ 8 位 id 与版本分布两者都进卡片——它们正是卡片读者最需要、而现在完全没有的信息
（卡片上「暴涨 13 事件」同样看不出新版占了几个）。⚠️ 但卡片版面**只有真发一张才验得出**，
DRY RUN 与 markdown 预览都验不出（盲区④），验收时必须单发 `$STATE/publish/card.json` 到开发机 `ou_` 私聊。
