## 待定的岔路：YAML 怎么解析（⛔ 需要人定，不要替我选）

`crashlytics_list_events` 的返回**是 YAML 文本不是 JSON**（实测片段）：

```yaml
- name: |
    projects/465344775452/apps/…/events/6AC744EF…_2264847276362233513
  eventTime: |
    '2026-09-17T07:24:09Z'
  issue: >
    id: 227fc097cbbaec56fa4c016c7739209c
  device: |
    manufacturer: OnePlus
```

MCP 的 `inputSchema` 里**没有输出格式参数**（实测 `tools/list`），所以 YAML 躲不掉。
而生产机两个 python 都没有 PyYAML。三条路：

| 方案 | 代价 | 风险 |
| --- | --- | --- |
| **A. 装 PyYAML**（`setup.sh` 加一步） | 本仓库首次引入 python 三方依赖 | 换机/重装多一个失败点；⚠️ 与「bash + bq + jq」的既有形态不一致 |
| **B. 手写极小解析器** | 零依赖，贴合现有形态 | ⛔ 解析的是**别人的输出格式**，上游一改就静默错——而事实层错了没人看得见 |
| **C. 只存原始文本块** | 最省 | 丢结构，台账「✅钻取确认」的采样计数做不了 |

⚠️ **我的倾向是 A**：B 的失败模式正是本仓库最贵的那一类（静默、无检测、
事实层没人日常核对）。但 A 动装机脚本，且与仓库既有的「零三方依赖」形态冲突，
⛔ 这个取舍该由人拍板。

**2026-09-18 已拍板：选 A。** ⚠️ 随之而来的要求：缺 PyYAML MUST 在装机阶段
（`setup.sh` / `check-scripts.sh`）就暴露，⛔ MUST NOT 留到跑批时才发现——
那正是本 change 要消灭的那类静默降级。

## 为什么不是「让模型分页取到能内联为止」

内联与否取决于**结果字节数**不是条数——312KB 那次是 6 个 issue，单个 issue 的堆栈
就可能过阈值。⚠️ 调 `pageSize` 是在赌一个我们观测不到、且上游可改的阈值：
赌输的表现是事实层静默少几条，与现状同级别。⛔ 不作为主方案。
