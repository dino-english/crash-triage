## Why

**起点是一个看起来很有说服力的观察，实测后被自己推翻了大半——本节保留完整推翻过程，因为「为什么不做」比「做了什么」更值得记住。**

### 最初的观察（2026-09-01 实测 08-31 周报）

```
总字符 9299 ┃ 其中 3712 字在提示块里 = 40%
           ┃ 16 个提示块 ／ 54 行数据 ／ 28 个 ⛔⚠️ ／ 36 处「不可/不是/不得/禁止」
日报 17437 ┃ 9 个提示块 ／ 213 行数据
```

结论当时下得很快：读者读到的警告比数字多，根因是**我们在用静态文档复刻 Firebase 控制台的下钻能力**——控制台上口径是下拉框、不需要被理解，而冻结文档里每个口径选择都变成读者必须逆向解码的编辑决定。同一条 issue `62f88f39` 在产物里有四个都正确的数字（台账 7 / 段四 4 / 段三 2 / 日报 1），控制台上它只有一个数加一个筛选控件。

预期：把段三段四改成「定位 + 直达」，周报能从 9300 字降到 4000 字量级。

### 实测推翻了两条

**① 29%（去重后的当前值）里的绝大多数是真正的判读须知，不是冗余。**

逐条按「这条信息的读者是谁」四层归类（判读须知 / 对照警告 / 设计备忘 / 历史教训）后，39 行提示块里**能移走的只有 1 行**（run_id 与审计路径，属排障信息）、**能去重的只有 1 处**（段四重复了段三已说过的 owner 读法）。其余如「`—` 表示该桶会话数不足」「crash-free 是下界估计」「ANR 率不可对照 Play 门槛」「页面维度没有分母」「占比分母是 issue 自己的事件数」——**不知道就会读错数字**。

它们不是排版问题，是这份报告口径复杂度的代价。

**② 「改直达」的前提不成立：多数读者没有控制台权限。**

```
Firebase 项目 IAM 唯一 user 数        38
周报投递群成员                        15 人 + 4 bot
群成员中能在 IAM 里匹配到的（宽松拼音匹配） 5 / 15
```

⚠️ 拼音匹配是启发式（IAM 是个人 gmail、飞书是企业身份，无可靠关联键），但方向足够清楚：**约三分之二的读者点不开链接**。改直达对他们等于把信息藏起来。design 里预留的「折中方案」（只把段四 per-issue 下钻改直达）对这批人有同样问题。

**③ 实施后的实测降幅：0.1 个百分点。**

```
改前  总 11744 字符 ┃ 提示块 3378（28.8%）┃ 提示行 39
改后  总 11740 字符 ┃ 提示块 3365（28.7%）┃ 提示行 39
```

## What Changes

范围已按实测收缩到两处**结构性**改动（⛔ 不删任何注解内容，只换位置与去重）：

- **排障信息下沉**：`run_id` 与审计路径从文档开头移到文末口径章，并标注「排障用，非判读须知」。原先它与「取数区间」并列在首屏，权重被读成同一级。
  ⚠️ **只加在文档侧**——`NOTE_MD` 被卡片与群消息逐字节共用，改它本身会把审计路径塞进卡片（F37 的形状，实施时差点再犯一次，被代码里前人留的警告拦住）。
- **段四去重**：owner 的完整读法在段三「归因」注解里已写过一遍，段四改为交叉引用 + 保留本段特有的「未经人工复核」。

保留的 spec 要求：**口径注解分层呈现**、**首屏只回答单一问题**、**issue 级条目提供外部下钻入口**（后者已由 `crash-report-issue-identity` 交付——id 本身即控制台链接，有权限的能点、没权限的照读表格，两边都不损失）。

## Non-goals

- ⛔ **不砍段三段四的维度与下钻**（原方案的核心，已被 ② 推翻）。对应的 spec 要求「维度呈现优先直达而非静态复刻」**已撤回**，不进 `crash-perf-impact-summary`。
- ⛔ **不删任何一条口径注解的内容**。分层只换位置。样本量括注、窗口两端标注、单位与分母说明照旧留在正文。
- ⛔ **不改任何指标算法、阈值或版本口径**。纯呈现层。
- ⛔ **不动分析层产出**。

## 后续（不在本 change 内）

唯一还有量级收益的方向是**降低口径本身的复杂度**——统一三份产物的版本集与 error_type 集，让「本节口径 = FATAL+ANR，与主力版本表不可相加」这类注解从根上不必存在。那是重新设计报告口径，不是排版问题，⛔ 不应塞进本 change。
