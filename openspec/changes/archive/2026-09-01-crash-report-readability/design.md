# 设计：报告可读性

## D1 · 诊断的量化依据

对 08-31 周报（`NIzedWRWCoAhOix10IVjfjxlpSS`）与 08-31 日报（`DQwzdOfqOoAtDmxCFU7j3AIPpVg`）原文实测：

| | 周报 | 日报 |
|---|---|---|
| 总字符 | 9299 | 17437 |
| callout 内字符 | 3712（40%） | — |
| callout 块数 | 16 | 9 |
| 表格数据行 | 54 | 213 |
| ⛔ / ⚠️ 记号 | 28 | — |

日报的比例健康得多（213 行数据 / 9 个 callout），**问题集中在周报**。原因是周报的数据密度低而口径复杂度高：同样一段影响面分布，日报按版本分列直接给，周报要同时说明版本集、error_type 集、分母缺失三件事。

⚠️ 这组数字是 2026-09-01 一次性测量，不是持续指标。实施后应重测同一组数字作为验收依据，⛔ 但不要把「字符数下降」本身当成目标——目标是注解与数据的比例，不是短。

## D2 · 分层的判据：这条注解在回答谁的问题

| 层 | 判据 | 去处 |
|---|---|---|
| 判读须知 | 不知道就会读错这张表的数字 | 正文，随表 |
| 对照警告 | 防止与外部口径（控制台/商店门槛）误对照 | 正文，随表；**若该维度改直达则删除** |
| 设计备忘 | 解释为什么这么设计、改的时候注意什么 | 文末口径章 |
| 历史教训 | 记录踩过的坑 | 文末口径章，或只留在 docs/ |

⛔ **判据不是「长短」也不是「重要性」**，是「这条信息的读者是谁」。「⚠️ 分母为 0 显示无法计算」短且属判读须知，留；「⛔ 不设会话数门槛，因为门槛会静默剔除刚放量的新版」长且属设计备忘，移。

⚠️ 有一类必须留在正文且不得压缩：**样本量括注、窗口两端标注、单位与分母说明**。这条是既有硬约束（「压缩时不得砍掉有记录的口径标注」），本 change 不碰。

## D3 · 直达链接消灭的是哪一类注解

改直达后自动失去存在理由的，只有**唯一作用是解释「我们和控制台为什么不一样」**的那些。例如：

- 「⛔ 不可与 Firebase 控制台首屏的用户口径对照」——若 crash-free 仍在报告里给，这条**必须保留**（它对照的是我们自己的数字）。
- 「本节口径 = FATAL + ANR，与主力版本表的崩溃列不可直接相加对照」——这是**内部两段之间**的对照警告，改直达也不会消失。

⚠️ **不要指望直达能消掉大部分注解**。实测 16 个 callout 里，纯外部对照类只有少数几个。篇幅的主要下降来自 D2 的分层移位，不是 D3。**这一点必须在验收时如实核对，不能事后把「没降那么多」说成成功。**

## D4 · 与 `crash-issue-drilldown` 的方向冲突

`crash-issue-drilldown`（15 项任务完成 14 项）刚把 per-issue 下钻加进周报段四；本 change 主张这类下钻交给 Firebase。

⛔ **这不是可以靠实现技巧调和的冲突，必须先定方向**（proposal「待确认」表三选一）。在方向定案前，本 change 的 tasks 只能写到「分层」这一半，段三段四的处置不得开工。

## D5 · 前提假设及其证伪方式

「改直达」的前提是**读者有 Firebase 控制台权限**。若多数读者没有，改直达等于把信息藏起来。

⚠️ 这个前提**无法从代码或数据中查证**，必须问人。⛔ 不得默认成立。证伪方式：报告投递的飞书群 `oc_655033f1f85fa04f9eac25d56f056cf9` 的成员里，有 Firebase 项目 `dino-english-497507` 访问权限的比例。

若前提不成立，可退到折中方案：保留段三维度表，只把段四 per-issue 下钻改直达（per-issue 下钻恰恰是控制台最擅长、我们复刻成本最高的部分）。

## D6 · 验收

- **文档结构验收**：重测 D1 那组数字。⛔ 不把字符数当目标，看的是 callout 内字符占比。
- **内容不丢失验收**：改动前后的口径注解**逐条清点**，断言每条都仍存在（位置可变）。⚠️ 这一步必须逐条比对，不能靠总字数推断。
- ⚠️ 卡片列宽只有真发一张才验得出——单发 `$STATE/publish/card.json` 到开发机 `ou_` 私聊。
- ⚠️ 验产物用 `CRASH_REPORT_NO_DELIVER=1`（DRY_RUN 打完卡片预览就 exit 0，跑不到文档渲染）。
- ⚠️ L2 基线提升在 NO_DELIVER 闸门之前，测试前先备份 `last-snapshot.json` 与 `issue-seen.json`。
