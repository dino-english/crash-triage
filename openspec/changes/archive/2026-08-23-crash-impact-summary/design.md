## Context

动机与实测数据见 [proposal.md](proposal.md)。

**可用字段**（`bq show --schema` 实测，Crashlytics 表约 110 字段，现有 SQL 用 6 个）：`device.manufacturer` / `device.model` / `device.architecture` / `operating_system.display_version` / `operating_system.name` / `event_timestamp` / `installation_uuid` / `process_state` / `memory.free` / `storage.free` / `blame_frame.library` / `remote_config_feature_rollouts`。

**版面约束**：卡片是 CardKit v2 的 table 组件——**无行级、无单元格级背景色**，只有文字色。汇总段若堆三块 × top5 = 15 行，卡片不可读。文档（DocxXML）没有这个限制。

**既有结构**：日报现为「一、结论 / 二、版本对照 / 三、明细 / 四、环比与口径」。「结论」当前只有版本间 delta 的几条 bullet。

## Goals / Non-Goals

**Goals:**

- 让「今天要不要立刻介入」这个判断，在汇总段内就能做出。
- 把「9 次崩溃 / 1 台设备」与「14 次崩溃 / 7 台设备」在版面上区分开。

**Non-Goals**（proposal 已列，此处只加设计级边界）：

- **不做维度交叉**。机型 × OS × 时段属于排查工具，不属于日报。
- **不存维度历史**。`metrics-history.jsonl` 存的是可做趋势的标量；「机型 top5」不是标量，存进去只会让文件膨胀且无人查询。

## Decisions

### D0：已定的排版决策（2026-08-22，由使用方拍板）

| 决策 | 结论 |
|---|---|
| 机型 / OS / 时段三维度是否按版本拆 | **按版本拆**（全拆，非只最新版） |
| 汇总段是否进卡片 | **不进**，纯文档段 |
| 页面样本量是否提到版本对照表 | **提到**（见 D7） |
| 接口错误率是否指名最差接口 | **指名**（见 D7） |

**「按版本拆 + 不进卡片」是一对自洽的选择**：拆开后是 2 端 × 版本数 × 3 维度 × top N 行，只有文档容得下。卡片不承载汇总段，因而不受行数影响。

⚠️ **但文档里的可读性仍需处理**：2 端 × 2 版本 × 3 维度 × 5 行 = 60 行连续表格，读者会略过。缓解见 D1a。

### D1a：按版本拆之后的可读性处理

拆开不等于全部平铺。三条约束：

1. **每个维度每版本只取 top 3**（不是 5）。拆版本后条目数翻倍，top N 必须同步收紧，否则总行数翻倍。
2. **维度块按平台分组、版本并列**，不是「平台 × 版本」四段各自重复三张表。同一维度的两个版本并排呈现，读者能直接看出「新版是不是引入了新机型问题」——这正是按版本拆的**唯一价值**，平铺成四段就丢掉了。
3. **无差异不展开**：某维度在两个版本间的 top 3 完全一致时，合并呈现并标注「两版一致」。稳态下这会是常态，能把 60 行压回 20 行左右。

**否决「四段平铺」**：那只是把数据倒出来，读者要自己做版本间比对——而那正是我们该替他做的。

### D1：汇总段只回答三个问题，每个问题一小块

**选择**：影响多少人 / 集中在哪 / 什么时候。三块，各自独立可读。

**否决「把所有可用维度都加上」**：表里还有 `process_state`（前后台）、`memory.free`（内存水位）、`architecture`、`remote_config_feature_rollouts`（灰度关联）。每一个都有价值，**但汇总段的价值来自能被一眼读完**。加满会让它退化成数据倾倒——读者反而看不出重点，与本 change 的目的相反。

其余维度留待需要时按需加入，或进入专门的排查工具。**`remote_config_feature_rollouts`（能直接回答「是不是某个 flag 灰出去导致的」）价值最高，列为最优先的后续候选。**

### D2：集中度 = 事件数 / 受影响安装数

**选择**：直接给比值，不做归一化或分档。

实测的说服力：`Google Pixel 8 Pro 9 事件 / 1 安装 = 9.0` vs `OPPO CPH2591 14 / 7 = 2.0`。前者按事件数排第二，实际只影响一个人。**当前明细表只有事件数一列，这两者长得一模一样。**

**标记阈值用「相对该端均值」而非固定值**：不同 app、不同端的基线集中度差异大，固定阈值（如「>5 即标记」）在一个端准、在另一个端就误报。用相对量则自适应。

**否决「用集中度替代事件数」**：两个数都要，它们回答不同问题。事件数 = 问题发生的频度，安装数 = 影响的广度，比值 = 两者的关系。只给比值会丢掉规模信息。

### D3：排序口径改为受影响安装数

明细表当前按事件数 `ORDER BY events DESC`，改为按 `COUNT(DISTINCT installation_uuid) DESC`。

**这是一个会改变读者行为的改动**，不是显示细节：排在第一位的 issue 会被当成最该修的。按事件数排，单设备反复触发的问题会长期霸占头部。

**保留事件数列**，不隐藏——读者需要自己判断的空间，尤其在两个 issue 影响人数相同时。

### D4：时间分布——峰值 + 聚集检测，两件不同的事

**峰值**：按小时分桶取 top，回答「什么时候最容易出」。实测 14:00 与 21:00 各 19 事件——对教育类 App 与上课/晚间时段吻合。这是常态信息。

**聚集**：短时间窗内的事件堆叠，回答「是不是发生了一次事故」。均匀摊在两周里的 19 次与挤在 10 分钟里的 19 次是完全不同的故障形态——后者通常对应一次发版、一次配置推送或一次后端异常，**是可以立刻行动的信号**。

**两者必须分开呈现**：峰值时段是常态分布的描述，聚集是异常事件的提示。合并成一个「峰值」会让常态被读成事故。

**判定方式留给实施**（spec 只约束「能区分均匀与聚集」）：最简单的可行做法是比较最密集时间窗的事件占比与均匀分布的期望占比。**不要引入统计检验**——样本量小（双端两周合计两百余事件），任何显著性检验都会给出不可靠的结论，而这里只需要一个粗糙但稳健的提示。

### D5：汇总段完全不进卡片（已拍板）

原设计是「卡片放两块、文档放三块」。**使用方决定汇总段不进卡片**——卡片另有精简方案（独立的卡片改版 change 承载），汇总段是纯文档能力。

这消除了 CardKit v2 无行级样式带来的全部版面风险，也让 D1 的「按版本拆」得以成立：不受卡片行数约束。

文档中汇总段位于「一、汇总」，卡片经既有 `__DETAIL_URL__` 指向文档。

### D6：汇总段不给结论，与性能段同一约束

汇总段 MAY 说「事件集中于 Android 16」，MUST NOT 说「原因是 Android 16 的适配问题」。

维度聚合只能显示相关性——Android 16 事件多，可能只是因为用它的人多（实测 51 事件 / 44 安装，集中度 1.16，分布很广，看起来更像"用户多"而非"适配差"）。**没有分母就没有结论**：要判断是否适配问题，需要「该 OS 版本的崩溃率」而非「该 OS 版本的崩溃数」。

**是否补 OS 维度的分母**（`firebase_sessions` 是否含 OS 版本字段）**未核实**，列入 tasks。若可得，则维度表可给率而非绝对数，结论力大幅提升；若不可得，则必须在版面上标明「绝对数，未除以装机量，不代表该机型/系统更易崩溃」——否则读者必然做出错误推断。

这是本 change 最容易出错的一处：**给出机型排行而不给分母，等于在暗示一个数据不支持的结论。**

## Risks / Trade-offs

| 风险 | 缓解 |
|---|---|
| ~~机型 / OS 排行无分母~~ **已解决**：sessions 表实测含 `device.model` / `operating_system.display_version`，维度表直接给率 | 残余风险变为「有了率就以为有了根因」→ D6 的 MUST NOT 依然成立 |
| **汇总段过载，反而不如现状** | D1：只三块，每块 top N；卡片只两块 |
| **排序口径改变让读者以为数据变了** | 上线首期在明细表标注「已改为按影响安装数排序」 |
| **聚集检测误报**（小样本下随机波动被当成事故） | D4：用粗糙稳健的占比比较，不引入统计检验；提示措辞用「存在时间聚集」而非「发生了事故」 |
| **汇总段滑向分析** | D6 与既有性能段硬约束一致；spec 已写入 MUST NOT |
| **卡片版面溢出** | D5：卡片两块封顶，实测渲染后确认行数 |

**接受的取舍**：不做维度交叉、不做灰度关联（`remote_config_feature_rollouts`）、不做内存水位。这些都有价值，但塞进日报会毁掉汇总段的可读性。它们属于排查工具或后续 change。

## Open Questions

无。原 Open Question（`firebase_sessions` 是否含 OS / 机型字段）**已于 2026-08-22 实测确认可得**：该表含 `device.model` / `device.manufacturer` / `operating_system.display_version`。

因此**维度表给「率」而非绝对数**——分母来自 sessions 表的同维度会话数。D6 的风险随之大幅降低：「Android 16 事件多」不再可能被读成「Android 16 适配差」，因为呈现的直接就是该系统版本的崩溃率。

⚠️ 但 D6 的「不得断言根因」约束**依然成立**：给了率也只是相关性更强的相关性。某机型崩溃率高，可能是该机型用户集中在某个网络环境、某个功能路径，仍需钻取确认。

### D6a：两个维度的率可靠性完全不同（2026-08-22 实测后新增）

实测 Android 1.5.3 近 7 天：

| 维度 | 桶大小 | 率是否可靠 | 呈现 |
|---|---|---|---|
| **系统版本** | 2657 / 1221 / 715 会话 | ✅ 可靠 | **给率** |
| **机型** | 最大 75 会话 | ❌ 不可靠 | **给绝对数 + 影响安装 + 集中度** |

**加分母确实反转了结论**——系统版本维度上，Android 16 有 16 事件（绝对数最多）但率只有 **0.60%**（2657 会话），而 Android 14 有 23 事件、率 **3.22%**（715 会话）。只看绝对数会把最健康的版本当成头号问题。这验证了 D6。

**但机型维度加不了分母**：Android 机型碎片化到该版本最大的桶只有 75 个会话。实测门槛设 50 只剩 1 行、设 100 一行不剩——维度整个消失；设 20 留下的 `OPPO CPH2591 26.09%`（46 会话）统计上毫无意义。

**因此机型维度不给率**，给绝对数 + 影响安装数 + 集中度，并显式标注「未除以装机量，不代表该机型更易崩」。

**过滤放渲染层不放 SQL**：SQL 里过滤掉就连影响面也看不见了，而影响面（users）恰恰是机型维度唯一可靠的信息。渲染层只把率列换成「样本不足」，行本身保留。
