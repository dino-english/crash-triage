## D1 — Android 渲染 `— 不上报`，不是 0，也不是空

三种填法各自会被读成什么：

| 填法 | 被读成 |
|---|---|
| `0` | 「Android 没人受影响」——**与事实相反**（实测同窗口 20 个受影响安装） |
| 留空 | 「渲染坏了」 |
| **`— 不上报`** | 「该端没有这个数据」✅ |

⚠️ 后缀必须与 iOS ANR 的 `— 无此概念` **区分**：那里是「系统层没有这个概念」，这里是「客户端没上报这个字段」。前者不会变，后者加个 `setUserId` 就有了。用同一个后缀会让人以为 Android 也永远不可能有。

判定放渲染层（`该列恒 0 且事件数 > 0` → 判为不上报），⛔ 不在 SQL 里按平台分叉——分叉会让两端跑不同的查询，口径漂移无从察觉。

## D2 — ⛔ 与「受影响安装」不可相加或相减

实测 iOS 近 7 天：126 安装 / 119 用户，但 **119 个 user.id 对应 130 组 (用户, 安装) 配对**，单用户最多跨 3 个安装；前台子集里出现过 **6 安装 / 7 用户**——用户数反而多于安装数。

`126 − 119 = 7 个匿名用户` 这种算法是错的。两者是**交叉的两套群体，互不包含**。标注必须写在表格旁边，⛔ 写在 design 里不算。

## D3 — `NULLIF(user.id, '')` 不可省

覆盖率是按「非 NULL **且非空串**」实测的。只判 NULL 会把空串当成一个有效用户计入去重，虚增 1。
