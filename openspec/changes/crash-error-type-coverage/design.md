## Context

动机与实测数据见 [proposal.md](proposal.md)。这里只记实现约束。

**`error_type` 的实测取值**（近 14 天，`bq query` 直取）：

| 平台 | FATAL | ANR | NON_FATAL |
|---|---|---|---|
| Android | 105（`is_fatal=true`） | 93（`is_fatal=false`） | 131（`is_fatal=false`） |
| iOS | 4（`is_fatal=true`） | **该行不存在** | 1020（`is_fatal=false`） |

`is_fatal` 与 `error_type` 不是同一个维度：`is_fatal=TRUE` ⟺ `error_type='FATAL'`，而 ANR 与 NON_FATAL 的 `is_fatal` 均为假。**现有 `WHERE is_fatal = TRUE` 等价于 `error_type='FATAL'`**，只是写法掩盖了它排除了什么。

**iOS 没有 ANR 行，不是数据缺失**：iOS 系统层无 ANR 概念（Android 的 ANR 由 system_server 判定主线程无响应后产生）。iOS 的近似物是 watchdog 终止（`0x8badf00d`），Firebase Crashlytics 不将其单列为 `error_type`。真正对应的诊断在 MetricKit（`MXHangDiagnostic`）与 Xcode Organizer 的 Hang Rate，**均不在本流水线的数据源内**。

## Goals / Non-Goals

**Goals:**

- 让 ANR 与 NON_FATAL 从「被 SQL 静默排除」变为「有数字、有阈值、有告警」。
- 双端不对称被显式表达，而不是靠空格。
- 既有崩溃三行的口径与历史序列**一字不动**。

**Non-Goals**（proposal 已列，此处只加设计级边界）：

- **不合并三类 error_type 到一个"稳定性总分"**。三者的分母、可比性、责任人都不同，合成一个数会同时丢掉三者的可行动性。
- **不在本 change 接 MetricKit**。那是客户端埋点工程，不是报表流水线。

## Decisions

### D1：新增两个 SQL，不改现有崩溃 SQL 的过滤条件

`crash-issues.sql` / `crash-issues-all.sql` 的 `WHERE is_fatal = TRUE` **保持原样**，只更新注释。新增 `crash-anr.sql` 与 `crash-nonfatal.sql`。

**否决「一条 SQL 带 `error_type` 分组，一次取全」**：崩溃三行的历史序列（`metrics-history.jsonl`）按 FATAL 口径积累了 90 天，任何改动现有查询的做法都要面对"这一天的数字和昨天不可比"。分开取数则历史零风险。多两次查询的成本可忽略（现有单版本查询 3s 内返回）。

**注释必须改**：现注释写「与 topIssues 的 FATAL 过滤一致」——**这个理由已经失效**（topIssues 已不是数据源）。留着它会让下一个人以为过滤是为了兼容旧接口，而不是"这里刻意只要 FATAL，其它类型另有 SQL"。

### D2：ANR 率的分母用会话数，与 Play Console 口径的差异必须标注

**选择**：ANR 率 = ANR 事件数 / 会话数，与既有崩溃率同分母。

**否决「对齐 Play Console 口径」**（用户感知 ANR 率 = 至少经历一次用户感知 ANR 的日活用户 / 日活用户）：
- 「用户感知」是 Play 侧的判定（前台且用户可见），BigQuery 导出没有等价字段；
- 日活分母需要 `firebase_sessions` 的用户级去重，与现有会话级分母是两套口径，会让 ANR 率与崩溃率无法并排阅读。

**但差异必须写在报告上**。实测 0.743% / 0.794% 与 Play 的 0.47% 门槛在同一数量级，读者极易直接比对得出"超标了"的结论——**可能对，也可能不对，我们的数据回答不了**。不标注就是让报告替读者做一个它做不了的判断。

措辞方向：标明分母是会话数、窗口天数，并写明「与 Play Console 的用户感知 ANR 率（日活分母）口径不同，不可直接对照门槛判定」。

### D3：iOS 的 ANR 位置——显式说明，不留空不填零

三种填法，只有一种对：

| 填法 | 读者的结论 | 对不对 |
|---|---|---|
| 留空 / `—` | 「数据没取到」 | ❌ 数据取到了，是这类事件不存在 |
| `0` | 「iOS 没有卡死问题」 | ❌ 有，只是叫别的名字、在别处 |
| 「无此概念，见冻结率」 | 「去看冻结率」 | ✅ |

这与 `crash-daily.sh:1197` 那行文案犯的是同一个错误的两面：那行**用静态断言掩盖了有数据**，留空会**用空白掩盖了数据在别处**。

指向的近似信号是**冻结率与慢帧**——它们已经在日报里（`frozen` / `slow_worst` 两行），只是从没有人把它们和 Android ANR 摆在一起类比过。这个指向是零成本的，只是文案。

### D4：ANR 阈值取 0.47%，但标为"参考 Play 门槛，口径不同"

红线 `ANR_RATE_RED=0.47`、黄线 `ANR_RATE_YELLOW=0.24`（红线的一半，与既有指标「黄线约为红线一半」的习惯一致：崩溃率 1.0/0.5、接口错误率 1.0/0.5、冻结率 1.0/0.5）。

**取 0.47 不是因为我们的口径与 Play 相同**（D2 已说明不同），而是因为**没有更好的锚**，且宁可偏严。阈值常量的注释必须写明这一点，避免下一个人以为这是对齐后的数值。

**预告**：实测主力版本 0.743% / 0.794%，上线首日**必然触发红档告警**。这是正确行为——问题一直存在，只是不可见。但必须提前告知，否则会被当成流水线故障排查（这套系统已经有过「把被信号杀掉当成故障告警」的先例）。

### D5：NON_FATAL 的两端数字不可比，标注是硬要求

iOS 1020 vs Android 131，差 7.8 倍。这**几乎肯定不是** iOS 异常更多，而是两端 `recordError` / `recordException` 的收口点覆盖范围不同——非致命异常完全由客户端主动上报，覆盖多少全看埋了多少。

所以并列呈现时**必须标注不可比**。这与「日报三段版本口径不可混比」是同一类约束，措辞可沿用既有风格。

删掉 `crash-daily.sh:1197` 那行时，**不能顺手把"不可比"这个信息也删掉**——那行文案里唯一还成立的部分就是「两端数字暂不可比」。保留这个语义，去掉已失实的「线上仍为零上报」。

### D6：ANR 进摘要行，只 Android 一端（已拍板）

摘要行（卡片顶部的 🔴/🟡 行）纳入 ANR，**只呈现 Android**。iOS 不给占位值、不给括注——它不是「无数据」，是这类事件不存在，占位会与既有的「无数据降级成括注」语义冲突。

⚠️ 实测 0.743% / 0.794% 高于 0.47% 红线，**ANR 会天天占据摘要行第一位直到修下去**。这是预期效果（该指标本就长期超标且不可见），但意味着摘要行的「突发感知」作用会被一条常态项稀释。若两周后仍在，建议把 ANR 从摘要行降级为表格着色——**列为上线后的复盘项，不在本 change 内预判**。

### D7：NON_FATAL 进台账，但必须截断（已拍板，推翻原 Non-goal）

使用方决定 NON_FATAL 进 L2 台账。原 Non-goal 作废。

**实现约束（不可省）**：台账的「Issue 现状表」**拆为两张**——FATAL 现状表保持原样，NON_FATAL 现状表**按受影响安装数取 top N**（建议 N=10）并在表下标注「共 M 条，按影响面取前 N」。

**为什么必须截断**：iOS NON_FATAL 近 14 天 1020 条。台账是给人做处置判断的定点替换文档，全量写入会让 FATAL 的十几条淹没在一千条里，台账随即失去用途。截断不是打折执行决策，是让决策可用。

**为什么拆两张表而非加「类型」列**：单表混排时排序口径无法统一——FATAL 按影响面排、NON_FATAL 按影响面排会让两类交错，读者无法一眼看出「有几个致命问题」。两张表各自排序，语义清晰。

**同步机制不变**：仍走 `sync_ledger()` 的 `block_replace` 定点替换，新增一次标题定位（「NON_FATAL 现状表」）。⚠️ 标题定位必须取**最后一个**匹配（正文里可能出现同名文字的引用块，2026-08-20 踩过）。

## Risks / Trade-offs

| 风险 | 缓解 |
|---|---|
| **ANR 上线首日触发红档告警被当成故障** | D4：实施前预告；告警文案里写明「首次纳入统计」 |
| **读者拿 0.74% 直接对照 Play 的 0.47% 判定超标** | D2：报告上标注口径差异。这是本 change 最容易被忽略、后果最实际的一条 |
| **iOS NON_FATAL 1020 被读成「iOS 异常比 Android 多 7.8 倍」** | D5：并列处标注收口点覆盖差异 |
| **NON_FATAL 全量写台账淹没 FATAL 信号** | D7：拆两张表 + top N 截断 + 显式标注截断量。**不截断则台账直接不可用** |
| **ANR 常态超标长期霸占摘要行，稀释突发感知** | D6：预期效果；上线两周后复盘是否降级为表格着色 |
| **删 1197 行文案时连「不可比」一起删掉** | D5 已点名；tasks 中作为独立检查项 |
| **新增两次 SQL 查询拖慢跑批** | 现有单版本查询 3s 内返回，新增 2 次×版本数；`bqq` 已有 180s 超时护栏兜底 |
| **`metrics-history.jsonl` 旧行无 ANR 字段导致读取报错** | 读取端按「无该键 = 无数据」处理，与现有 `versions` 键缺失的处理方式一致（不回填、不丢弃整行） |

**接受的取舍**：ANR 率与 Play 门槛口径不同，因此本 change **不能回答「我们是否达到商店质量门槛」**。它只能回答「ANR 有多少、在哪个版本、趋势如何」。要回答前者需要用户级分母与「用户感知」判定，属于另一个 change。

## Migration Plan

无数据迁移。新增字段进 `metrics-history.jsonl` 后，旧行缺该键属正常。

**回滚**：`git revert`。新增 SQL 文件成为无人调用的孤儿，无害。

## Open Questions

- **ANR / NON_FATAL 是否应进 L2 台账**？台账当前追踪 FATAL issue 的跨版本生命周期。ANR 有 `issue_id`，技术上可追踪；NON_FATAL 数量级大（iOS 1020），全量进台账会稀释信噪比。**本 change 只做呈现，不进台账**——这个问题不影响本 change 的规格与任务拆分，留待台账口径单独讨论。
