# 实施中发现

## F1 ⚠️ D3 警告的那个 bug 真的踩了——文档被卡片形态覆盖

design D3 写着「`ROW_DEFS` 必须拆成 `_CARD` / `_DOC`，**这是最容易漏的一处**，
漏了会把文档也一起砍到 6 行」。

实施时我拆了 `ROW_DEFS`，也把 `xml_table` 指向了 `_DOC`，**但漏了 markdown 文档**：
`md_table()` 原先同时服务卡片回退视图与文档的「二、版本对照」段，我把它改成卡片形态后，
**文档的版本对照段变成了 6 行 × 平台列**，并且 iOS / Android 两节渲染出完全相同的表。

发现方式：验收时 grep 文档里的 `会话数 1d`，**结果是 0 次**。

**修法**：拆成两个函数——`md_table_doc()`（全量行 × 版本列，文档用）与 `md_table()`（卡片回退视图）。
两者不能合并，卡片敢砍到 6 行的前提正是文档保持完备。

**教训**：`ROW_DEFS` 有 4 个调用点（`build_table` / `md_table` / `verdict_line` / `xml_table`），
design 里只点了 3 个。拆共享常量时要先 `grep -n` 数清调用点，不能凭记忆。

## F2 卡片从 18 行压到 6 行

|---|---|---|

## F4 ⛔ `ios` / `android` 是 CardKit v2 的保留列名——真发一张才发现

首次真实投递直接失败：

```
code 230099: table rows name is invalid;
ErrorValue: row idx:1, invalid name:harmony
```

列名与行键完全匹配（`metric` / `ios` / `android`），`jq empty` 通过、结构检查通过。
问题在**列名本身**：CardKit v2 把 `ios` / `android` 当成**元素的平台变体键**
（`ios` / `android` / `pc` / **`harmony`**），于是把数据行解析成平台变体对象，
抱怨缺了 `harmony` 这一支。

**修法**：列名改为 `col_ios` / `col_and`。

**这条最值得记的不是 bug 本身，是它怎么被发现的**：
- `jq empty` ✅ 通过
- 3 列 6 行结构检查 ✅ 通过
- 元素顺序、字节数 ✅ 正常
- **只有真发一张才炸**

design 把「先实测渲染」列为 task 1 是对的。我原本想用结构性验证代替它——那样会把一张
永远发不出去的卡片交付上线，而卡片是这条流水线**唯一的高频出口**。

修复后重发成功：`✅ 卡片已发送（idempotency-key=20260822-155447）`。

## F5 ⚠️ 交付的卡片与使用方确认的草图有四处出入（我的疏漏）

对着草图逐行核对才发现：

| 草图承诺 | 首次交付 | 性质 |
|---|---|---|
| `崩溃 20 次 / 10 人` | `1 类 2 次` | 少了受影响人数 |
| `ANR 48 次 0.74%` | `0.00% (0/35)` | 少了事件数 |
| `慢帧最差页 94.0% (1203)` | 无样本量 | **决策 D5 未实现** |
| 接口错误率指名最差接口 | 未做 | **决策 D7 未实现** |

D5 / D7 是使用方明确拍板的决策，我记进了 artifact 却没落进任何一个 change 的 tasks——
**决策与任务之间断了链**。已全部补上（`crash_brief` / `anr_brief` 两个卡片专用行键；
`slow_worst` 附样本量；`net_err` 附最差接口）。

**教训**：拍板的决策必须当场落成 task，否则「记在文档里」等于没记。

## F6 ⚠️ iOS 的「卡死信号」原本是个悬空指针

iOS 那格写「— 无此概念（见冻结率）」，**而冻结率在 6 行精简时被砍掉了**——
指针指向一个卡片上不存在的行。而且那格对 iOS 是**零信息量的占位文字**。

更根本的问题：既然 iOS 有对应信号（冻结帧率，>700ms 单帧，用户直接可感知的卡死），
**这一行就该装它**，而不是指向别处。

改为语义行「卡死信号」，双端各用自己的原生指标：
- Android：`49 次 0.76%（7d）` —— ANR
- iOS：`冻结帧 X%（3d·最差页）` —— 冻结帧率

⚠️ 两端指标不同、窗口也不同（7d vs 3d），单元格内各自标注窗口，口径注声明**不可比**。

## F7 影响集中行原本取错了版本

原实现固定取最新版。实测 Android 1.5.4 刚放量只有 2 个事件 → 这行只出得来 **1 个机型**。
改为取**该端事件最多的版本**：现在出 `Android 1.5.3：OPPO CPH2591 5 人 · TECNO KL4 2 人 · vivo V2026 2 人`。

## F8 表头加设备数后长度翻倍，压成紧凑形式

使用方要「top2 个别版本使用人数」。设备数才回答「多少人在用」（会话数会被同一人反复启动放大）。

展开写成 `1.5.4(28 会话·14 设备)→1.5.3(1243 会话·877 设备)` 会让表头长到在手机上必然截断——
**表头是最吃宽度的地方**。改为 `1.5.4(28/14)→1.5.3(1243/877)`，含义写进口径注。

## F9 ⚠️ 平台分列**隐藏了主力版本的真实数字**——这是 D1 当初没看到的代价

使用方提议「上下两个版本分开 column」，实现出来对比才发现：**这不只是版面清晰度问题。**

| 指标 | 平台分列（只显示最新版 + delta） | 版本分列（两版并排） |
|---|---|---|
| Android 崩溃 | `2 次 / 1 人 -22 ↓` | `1.5.4: 2 次/1 人` · **`1.5.3: 24 次/14 人`** |
| Android 卡死信号 | `0 次 0.00%` | `1.5.4: 0 次` · **`1.5.3: 49 次 0.74%`** |
| iOS 非致命 | `0 次 / 0 人 -647 ↓` | `1.5.4: 0` · **`1.5.3: 647 次/79 人`** |

平台分列的格子里只有**最新版**的值，主力版本的数字要从 delta 反推。而新版刚放量时最新版
样本极小（1.5.4 只有 5 个会话），于是**卡片上唯一可见的数字全是没有统计意义的那个**。

**最要紧的是**：`crash-error-type-coverage` findings F1 记录的「ANR 0.76% 超标却不告警」，
在平台分列下卡片上**连数字都看不到**（只显示 1.5.4 的 0.00%）；版本分列下 `1.5.3: 49 次 0.74%`
直接呈现——**版面选择部分补偿了告警口径的缺陷**。

单元格也确实清爽了：`99.65% (23/6615)` vs `94.29%(1.5.4) · 99.30%（全版本）⚠️样本小 -5.36pp ↓`。

**代价**：列数 3 → 5，窄屏宽度未验证；全版本 crash-free 在表里无归属列，移到下方 markdown 行；
对比值不再单列（四个版本并排，变化横向读得出来）。

**当前状态**：两种布局都可用，`CRASH_REPORT_CARD_LAYOUT=version-cols` 切换，默认仍是平台分列。
两版都已发到私聊供目视对比，**选哪个由使用方定**。

⚠️ design D1 当初否决版本分列的理由是「手机上 5 列必然压缩或换行」——**那是未经验证的假设**，
而且只考虑了宽度，没考虑到平台分列会让主力版本的数字消失。

## F10 版本分列定稿，平台分列已删除

手机端实测通过，`CRASH_REPORT_CARD_LAYOUT` 开关与平台分列的全部代码
（`card_header` / `card_cell` / 平台分列的 `build_card_table` / `ROW_DEFS_CARD` / `crash_free_pair` 分支）
已删除——两套布局并存是技术债，不该长期保留。

markdown 回退视图 `md_table()` 同步改为版本分列形态，并开启 `CELL_BREVITY`（它是卡片的回退视图，
应与卡片一致，而不是与文档一致）。

**删除后验证**：文档的版本对照段仍是 13 行 × 版本列，完整缺数文案仍有 10 处——
卡片瘦身没有波及文档。
