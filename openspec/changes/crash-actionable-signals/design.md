## Context

动机与实测数据见 [proposal.md](proposal.md)。这里只记方案要点。

**实测归因分布**（Android 近 7 天，FATAL+ANR，201 事件基数下的 7 天切片）：
`SYSTEM` 47/30 · `SYSTEM(libutils.so)` 30/23 · `DEVELOPER` 23/18 · `THIRD_PARTY` 11/9 · 未归因 6/6。

**实测灰度关联不可用**：近 30 天 201 个事件中 `ARRAY_LENGTH(remote_config_feature_rollouts) > 0` 的有 **0 个**。

## Goals / Non-Goals

**Goals**：让「该谁接 / 是不是新的 / 哪个系统版本 / 整体健不健康」四个问题在卡片上有答案。

**Non-Goals**：见 proposal。设计级补充——**不引入 owner 的中文意译歧义**：
`DEVELOPER` / `THIRD_PARTY` / `SYSTEM` 渲染成「自家 / 三方 / 系统」，但口径注必须写明
它标识的是**责任帧属于谁**，不是「谁触发了崩溃」。

## Decisions

### D1：归因方与库必须一起给

只给 owner 会丢掉「是哪个库」，只给 library 会丢掉「是谁的代码」。实测最有信息量的一行恰恰是
`SYSTEM + com.prime.dino.english`（47 事件）——**归因方是系统，被归因的库却是自家包名**，
说明是系统帧被自家代码调用。任何一列单独看都会得出错误结论。

**否决「只给 owner 三分类」**：那正好丢掉上面这个反例，而它是这个维度最需要被看见的形态。

### D2：生命周期基准换用 BigQuery issue id，并扩为带日期的滚动集合

现结构 `daily-snapshot.json` 的 `ios_ids` / `android_ids` 来自 MCP，而 MCP 抓取长期失败——
**两个数组现在都是空的，L1 的新增判定实际是死的**。

改用与崩溃统计同源的 BigQuery issue id（`$TMP/issues-<plat>-<ver>.json` 已有）。

结构从「id 数组」扩为 `issue_seen: {"<id>": "<末次出现日期>"}`：
- **新增** = id 不在 `issue_seen` 里
- **回归** = 在里面，但末次出现日期早于上一轮
- **长期** = 末次出现日期就是上一轮

**否决「只存昨天的 id 集合」**：那样只能判新增，判不了回归——而回归（修复失效 / 场景重现）
与全新问题的处置方式完全不同，正是最该被单独标出的那一类。

**保留期 90 天**，与 `metrics-history.jsonl` 一致。超期清理，之后再出现按新增处理——
隔了三个月的一次重现，更接近新问题而非回归。

### D3：首轮只建基线，不标新增

旧结构（无 `issue_seen` 键）→ 本轮只写基线、不标任何 issue。
沿用 L2 `last-snapshot.json` 的既定做法：首轮把每个 issue 都标成新增会刷满整屏，
且与「新增」这个词要传达的信息相反——它应当表示变化，而首轮没有变化可言。

### D4：卡片两个 crash-free 并列，不是替换

最新版那个回答「新版发得怎么样」，全版本那个回答「整体健不健康」。
实测最新版 `94.29% (2/35)` 与全版本 `99.28%` 差 5pp，而前者基于 35 个会话——**没有统计意义**。

**否决「用全版本替换最新版」**：新版放量期正是最需要盯的窗口，去掉它就看不见新版异常了。
**否决「只在小样本时才显示全版本」**：条件显示会让读者不知道平时那个数是什么口径。两个都常驻。

### D5：系统版本行只给率最高的那个，且只在率可靠时出

系统版本维度的会话桶足够大（实测 2657 / 1221 / 715），率可靠。
设备型号维度不可靠（最大桶 75 会话），故设备行**只给人数不给率**——两行的判读价值不同，不能合并。

卡片只给**率最高的那一个**系统版本：完整分布在汇总段，卡片是简报。

## Risks / Trade-offs

| 风险 | 缓解 |
|---|---|
| **`daily-snapshot.json` 结构变更导致首轮刷屏** | D3：无 `issue_seen` 键时只建基线；实施后首轮实测确认无「新增」标记 |
| **`owner=SYSTEM` 被读成「不是我们的问题」** | spec 已写 MUST NOT；口径注写明它标识责任帧归属而非触发者；D1 的 `SYSTEM + 自家包名` 反例进注释 |
| **卡片再加两行（系统版本 + 全版本 crash-free）又变长** | 系统版本并入影响集中那块（markdown 行，不占表格行）；全版本 crash-free 与最新版**同格并列**，不新增行 |
| **归因取数增加查询次数** | 每端每版本一次，与维度查询同批；仅对最新 N 版取，与既有成本控制一致 |
| **回归判定在跑批漏跑一天后误判** | 漏跑一天会让所有 issue 的「上一轮」变成前天 → 全部判为回归。**以基准里的最大日期为「上一轮」**，而不是「昨天」 |

## Migration Plan

`daily-snapshot.json` 结构扩展，无需迁移：旧键保留，新增 `issue_seen`。首轮建立基线。

**回滚**：`git revert`。`issue_seen` 键成为无人读取的冗余字段。
