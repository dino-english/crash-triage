## D1 · ANR 进同一张现状表，不另起一张

`render-ledger.sh` 的行生成里 `type: "FATAL"` 是**硬编码常量**，而表头早就有「类型」列——
这列本来就是为多类型留的扩展点，不是新概念。

⛔ **与 NON_FATAL 分表的理由在 ANR 身上不成立**。那条理由是量级：
iOS 非致命 14 天 1020 条，混排会把十几条 FATAL 淹掉。而 ANR 过阈值后今天只有 2 条，
且处置方式与 FATAL 相同（都要有人修）。⇒ 同表 + 类型列区分。

⚠️ 若某天过阈值的 ANR 多到淹没 FATAL（经验界：超过 FATAL 行数），再拆表不迟——
**那时才有证据**，现在拆是投机。

## D2 · 阈值放在渲染层，不放在 SQL

SQL 取回 ANR 全量（`LIMIT 50` 只做安全上界），过滤与计数都在 jq 里做。

- **为什么不在 SQL 里 `HAVING users >= N`**：那样「未入选有几条」就取不到了，
  而「未呈现的数量必须标注、不静默丢弃」是台账既有纪律（NON_FATAL 表同款）。
  在 SQL 里筛就得再查一次总数——多一次 bq 调用换一个本来就在手里的数字。
- ⚠️ **`LIMIT 50` 被打满时要看得出来**：返回 50 行即视为可能截断，注解改为「≥50 条」。
  今天实测 34 条，留 16 行余量。

## D3 · ⛔ 只给过阈值的 ANR 建事实层记录

事实层「一次抓取永久保留、不参与清理」。32 条单设备 ANR 大多是一次性的，
为它们建档 = 让事实层无限膨胀，而膨胀的代价是**每轮 `fetch-issue-states.py` 都要逐个
调一次 MCP**（今天 32 个文件已经是整跑里最慢的一段之一）。

⇒ 入选台账才进事实层。⚠️ 代价写清楚：一个 ANR 从 1 台涨到 2 台时才建档，
它的「首次纳入」是**越过阈值那天**，不是第一次发生那天。这与 FATAL 的语义不同，
表下注解必须说明。

## D4 · 冷启动：首轮 ANR 全部标「🆕新增」

生命周期基准 `issue-seen.json` 里没有任何 ANR id ⇒ 落地后第一轮全部判「🆕新增」，
「首次纳入」= 当天。⛔ **这是冷启动残留不是事实**——`4d05f9e7` 至少从 1.5.6 起就在发生。

⇒ 落地后第一轮必须**人工订正首次纳入日期**（同 2026-08-31 生命周期基准冷启动那次）。
⚠️ 不要试图从 BigQuery 回填「真正的首次发生」：事件表只有 89 天保留期，
回填出来的日期同样是个下界，却长得像事实。

## D5 · 边界：进现状表与时间线状态变更，不进变化检测

| 通路 | ANR 进不进 | 为什么 |
| --- | --- | --- |
| 现状表（处置跟踪） | ✅ 进 | 本 change 的目的 |
| 时间线 · 处置状态变更 | ✅ 自动进 | 那段按 id 遍历 fixmap，不分平台键 |
| `DIFF` 新增/回归/消失/暴涨 | ❌ 不进 | 按平台键遍历顶层 FATAL 数组，接它要动卡片变化行与复发率 |
| 复发率 / 卡片变化行 | ❌ 不进 | 同上 |

⚠️ 这个边界必须写进表下注解，否则读者会以为「ANR 没出现在时间线新增里 = 没有新 ANR」。

## D6 · iOS 不分叉

同一份 SQL 双端共用，iOS 自然跑出 0 行（数据源不产出 iOS 的 ANR）——
⛔ 不在 SQL 里按平台写 if，与 `crash-rate.sql` 的 `affected_users`（Android 恒 0）同一条纪律。
渲染层不出空表，靠表下注解说明「ANR 仅 Android，iOS 系统层无此概念」。
