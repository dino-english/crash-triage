## D1. 注记放仓库，不放 `$STATE`

**选择**：`notes/version-notes.tsv`，随代码进版本控制。

**理由**：`$STATE` 装的是运行数据与**机器相关**配置（`local.env` 的群 ID、开关、`path.env` 探测缓存）。
注记不是配置而是**内容**——要 review、要两台机器一致、要和产生它的那次业务改动同批提交。
放 `$STATE` 会变成开发机与生产机各一份、且不进版本控制，写了等于没写。

⚠️ 与 `local.env` 的边界要在文件头写明，否则后人会把它当配置塞进 `$STATE`。

## D2. 渲染在摘要区，⛔ 不进表格单元格

**选择**：作为摘要区的独立 markdown 元素输出（实测卡片结构为
`markdown / hr / markdown / markdown / hr / table`）。

**理由**：进表格会同时踩中本仓库两个已知失效模式——

1. **列宽只有真发一张才验得出**（DRY RUN 与 markdown 预览都验不出截断），而注记是长文案，
   必然撑爆列宽；
2. **卡片表格的列集合有两个定义点**（`build_card_table` 出 JSON、`md_table` 出预览与日报 md），
   改一处会让预览与实发不一致（F35）。

放摘要区两条都不触发：不改列集合、不受单元格宽度约束。

## D3. 命中当前报告的版本集，不是「所有版本」

**选择**：按「平台 + 版本」精确匹配**该份报告正在呈现的版本集**。

⚠️ **L1 用最新 2 个版本、L2 用会话量 top2 主力版本，两者常常不同**（新版刚放量时尤其）。
因此同一条注记完全可能只出现在其中一份报告里——**这是正确行为，不是缺陷**。
不写明的话，以后必被当成 bug 来「修」成两边都出，那会让日报出现它并未呈现的版本的注记。

多条命中按版本降序，上限 3 条；超出截断并标注实际条数（与 NON_FATAL 现状表的截断纪律一致）。

## D4. 不自动抑制判定

**选择**：注记只增加一句话，⛔ 不改「✅ 变好 / ⚠️ 变差」的判定逻辑。

**理由**：自动抑制需要阈值（跌多少算「可疑」），而阈值本身要有依据；更要命的是它会把**真改善**
一起吞掉——修好一个真崩溃导致的下降与移除噪音导致的下降，在数据上完全同形，数据侧区分不了。
注记是人写的、有落款、可追责，判断权交给读者。

这也是本 change 归 `crash-report-design` 而不是 `crash-metric-change` 的分界：**不改任何数字**。
