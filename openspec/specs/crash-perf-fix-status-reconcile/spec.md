# crash-perf-fix-status-reconcile Specification

## Purpose

定义修复状态的自动对账机制：通过约定的 commit message 标记，在跑批时反扫业务仓库的提交历史，自动更新台账中各 issue 的处置状态，无需在业务仓库安装任何钩子。

## Requirements

### Requirement: commit message 携带崩溃标识

修复某崩溃 issue 的提交，其 message MUST 包含该 issue 的短标识，格式为方括号包裹的 `crash:` 前缀加 8 位十六进制标识。

#### Scenario: 提交带合规标记

- **WHEN** 提交 message 含 `[crash:<8位十六进制>]`
- **THEN** 该提交被识别为对应 issue 的修复提交

#### Scenario: 提交无标记

- **WHEN** 提交 message 不含该标记
- **THEN** 该提交不参与修复状态对账
- **AND** 不产生告警

### Requirement: 反扫在跑批期进行，不侵入业务仓库

修复状态对账 MUST 在流水线自身的跑批过程中完成， MUST NOT 在业务仓库安装提交钩子或写入任何文件。

#### Scenario: 跑批执行对账

- **WHEN** 跑批链路运行到修复状态对账步骤
- **THEN** 以只读方式扫描两个业务仓库的提交历史
- **AND** 业务仓库的工作区与提交历史不被修改

#### Scenario: 业务仓库不可读

- **WHEN** 某个业务仓库无法读取提交历史
- **THEN** 对账跳过该平台并在产出中显式标明
- **AND** 另一平台的对账照常进行

### Requirement: 对账幂等且可补漏

对账 MUST 在固定回溯窗口内重复扫描，同一提交多次扫到不产生重复记录，漏过一轮的提交在下一轮仍可被捕获。

#### Scenario: 同一提交被多轮扫到

- **WHEN** 某修复提交在连续多轮跑批中都落在回溯窗口内
- **THEN** 台账中该 issue 只记录一次修复提交
- **AND** 重复扫描不改变台账内容

#### Scenario: 上一轮跑批失败

- **WHEN** 上一轮跑批未执行对账
- **AND** 该窗口内存在修复提交
- **THEN** 本轮对账仍能识别该提交

### Requirement: 对账只更新机器可判定的列

对账 MUST 只改写由代码提交事实与线上事件事实推导出的字段， MUST NOT 覆盖结论性判断。

识别到修复提交后，状态 MUST 取下列四者之一，且判定 MUST 以「修复提交之后的事件发生在哪个包上」为准， MUST NOT 只比较事件时间与提交时间：

| 状态 | 含义 |
| --- | --- |
| 修了仍在 | 含修复的包上仍有新事件 |
| 已发版待验 | 含修复的包已上线，且其上无新事件 |
| 已修未发版 | 尚无含修复的包上线 |
| 状态未知 | 事件证据不可得 |

#### Scenario: 识别到修复提交

- **WHEN** 某 issue 被识别出修复提交
- **THEN** 其处置状态更新为上述四者之一并记录提交标识
- **AND** 该行的既有结论性备注保持不变

#### Scenario: issue 线上仍在发生

- **WHEN** 某 issue 已有修复提交
- **AND** 修复提交之后，含修复的包上有新事件
- **THEN** 状态标注为「修了仍在」
- **AND** 不擅自判定为已修复

#### Scenario: 新事件全部来自不含修复的包

- **WHEN** 某 issue 已有修复提交
- **AND** 修复提交之后的新事件全部发生在不含修复的包上
- **THEN** MUST NOT 标注为「修了仍在」
- **AND** 若含修复的包已上线，标注为「已发版待验」并附「旧包仍崩 N 次」
- **AND** 若含修复的包尚未上线，标注为「已修未发版」
- **AND** 理由：2026-10-06 生产实测 19 条映射中 6 条属此类却被报成「修了仍在」，其中 5 条修复已随新版发出、新包上 0 次

#### Scenario: 修复尚未发版且无新事件

- **WHEN** 某 issue 已有修复提交
- **AND** 修复提交之后无新事件
- **AND** 尚无含修复的包上线
- **THEN** 标注为「已修未发版」
- **AND** MUST NOT 标注为「已发版待验」——没有新事件不代表修复已触达用户

#### Scenario: 事件证据不可得

- **WHEN** 无法取得该 issue 在修复提交之后的事件信息
- **THEN** 标注为「状态未知」
- **AND** MUST NOT 默认为「已发版待验」或「已修未发版」

### Requirement: 标识匹配须避免误判

短标识匹配 MUST 限定在约定格式内， MUST NOT 因提交 message 中出现相似字符串而误判。

#### Scenario: message 含相似但非标记的字符串

- **WHEN** 提交 message 含 8 位十六进制但不在 `[crash:...]` 格式内
- **THEN** 不被识别为修复提交

#### Scenario: 短标识对应多个 issue

- **WHEN** 某 8 位短标识在当前 issue 集合中匹配到多于一个
- **THEN** 不自动更新任何一个
- **AND** 在产出中标明该歧义待人工确认

### Requirement: 修复提交在两端都必须被呈现，但 null 的含义按端区分

反查到的修复提交 MUST 在两端都渲染出来，MUST NOT 对任一端写死为不可判定。

⚠️ 但「找不到」的含义按端不同，MUST 区别呈现：
- 提交约定为**硬规则**的一端：找不到 ⇒ 可判定为未修复
- 提交约定为**自发采用、非强制**的一端：找不到只意味着「提交信息里没找到」，
  ⛔ MUST NOT 渲染为「未修复」——那是过度断言

#### Scenario: 反查到修复提交

- **WHEN** 某 issue 在业务仓库的提交信息中被引用
- **THEN** 两端都 MUST 显示该提交标识

#### Scenario: 未反查到，且该端约定为硬规则

- **WHEN** 未找到引用，且该端的提交约定是强制的
- **THEN** MAY 判定并显示为未修复

#### Scenario: 未反查到，且该端约定非强制

- **WHEN** 未找到引用，且该端的提交约定是自发采用的
- **THEN** MUST 显示为不可判定，并在说明中讲清「不等于未修复」

#### Scenario: 「某端未采用该约定」这类结论的复核

- **WHEN** 需要判断某端是否采用了提交约定
- **THEN** MUST 在**跑批实际读取的那份仓库**上复核，MUST NOT 依据开发机的本地副本
- **AND** MUST 使用与反扫器一致的匹配规则——2026-09-05 实测：用收窄的正则在落后的本地副本上
  复核，会得出与事实相反的结论

#### Scenario: 反查结果不得在渲染处被丢弃

- **WHEN** 反扫器已产出某端的修复提交映射
- **THEN** 所有消费该结果的渲染处 MUST 呈现它，MUST NOT 因平台而整段跳过
- **AND** ⚠️ 「已修未发版」与「已发版待验」是最容易被遗忘的状态，MUST 出现在卡片可见处

#### Scenario: 修复状态的数据源不得是当周快照

- **WHEN** 渲染修复状态
- **THEN** MUST 以反扫器产物（fixmap）为源，MUST NOT 以当周崩溃快照为源
- **AND** 理由是定义性的，不是实现偏好：issue 一旦修好、窗口内不再产生事件就**掉出快照**，
  而那**正是「已发版待验」的含义**——以快照为源，只有「修了但仍在崩」的才可能被渲染，
  恰好把最该顶到卡片上的那一类全部过滤掉
- **AND** 2026-09-07 生产实测：同一轮跑批，台账时间线 2 条、卡片 0 条（快照里 `fix_commit != null` 计数为 0）

#### Scenario: 两态不得被写死成一态

- **WHEN** 反扫器已判定状态
- **THEN** 渲染处 MUST 逐态显式映射并原样采用该判定，MUST NOT 写死其中一态，MUST NOT 以兜底分支把未列出的状态归入某一态
- **AND** ⚠️ 把其余状态一律归为「修了仍在」会把「已修未发版」「已发版待验」说成修复无效，处置方式完全不同

### Requirement: 对账范围须对每张现状表有确定答案

修复状态反扫的适用范围 MUST 对台账中每一张现状表显式给出答案，MUST NOT 留白。本轮确定：Issue 现状表纳入对账；NON_FATAL 现状表 **不纳入**。

不纳入的理由 MUST 记录在案，且 MUST NOT 被理解为「NON_FATAL 无需跟踪修复状态」——其修复状态由人工结论承载。

#### Scenario: 反扫命中某 NON_FATAL issue 的标识

- **WHEN** 某提交 message 携带的标识对应一个 NON_FATAL issue
- **THEN** 不改写该 issue 在 NON_FATAL 现状表中的任何列
- **AND** MUST NOT 覆盖其人工结论

#### Scenario: 人工结论与反扫结果并存

- **WHEN** 某 issue 同时存在人工结论与可识别的修复提交
- **THEN** 人工结论 MUST 保持不变
- **AND** 机器可判定字段与人工结论 MUST 在呈现上可区分来源

### Requirement: 不遵守标识约定的修复提交须可被识别为对账盲区

对账依赖提交 message 中的约定标识。未携带标识的修复提交 MUST NOT 被当作「该 issue 未修复」的证据。

理由：2026-09-23 实测 `847a280c`（修复 `359fadbc`，已验证线上生效）的 message 既无 `[crash:<8位id>]` 也无 32 位标识，按 `git log --grep` 完全查不到；而 `21ef358b` 携带 32 位标识可被识别。若把「查不到」读成「未修复」，会得出与线上事实相反的结论。

#### Scenario: 修复提交未携带标识

- **WHEN** 某 issue 的实际修复提交未携带约定标识
- **THEN** 其修复状态停留在上一轮，标注为「对账未覆盖」
- **AND** MUST NOT 标注为「未修复」

#### Scenario: 人工已确认修复但对账无记录

- **WHEN** 人工结论已判定某 issue 修复生效，而对账未识别到修复提交
- **THEN** 以人工结论为准呈现
- **AND** MUST NOT 因对账无记录而推翻人工结论

### Requirement: 「含修复的包」与「已上线」须按端可得的信号判定

判定 MUST 只使用该端确实可得、且已实测可信的信号；某端缺少可靠信号时 MUST 采用保守判据（宁可推迟「已上线」，不可提前），MUST NOT 以会话量或设备数门槛区分内部包与上架包。

iOS：含修复的包 = 修复提交之后首次出现、且为上架包（开启性能采集）的 build；已上线 = 存在这样的 build。
Android：已上线 = 修复提交已进入主干或任一发版标签；含修复的包 = 版本号不低于最早包含该提交的发版标签的 build。

#### Scenario: iOS 内部测试包上的事件

- **WHEN** 修复提交之后，某 iOS issue 的新事件只出现在内部测试包上
- **THEN** MUST NOT 据此标注「修了仍在」
- **AND** 这些事件 MUST 计入「旧包 / 内部包」次数并呈现

#### Scenario: Android 与修复同日上线、但不含修复的版本

- **WHEN** 某 Android 版本在修复提交之后首次出现，但最早包含该修复的发版标签是更高的版本
- **THEN** 该版本上的事件 MUST 计为不含修复的包上的事件
- **AND** 理由：2026-10-06 实测 `62f88f39` 修复与 1.7.1 同日，1.7.1 不含修复（标签显示要到 1.8.0）

#### Scenario: Android 修复已进主干但尚无发版标签

- **WHEN** 某 Android 修复提交已进入主干，但没有任何发版标签包含它
- **THEN** 判为已上线
- **AND** 含修复的包退回为「修复提交之后首次出现的 build」

#### Scenario: 早于构建首现数据可得范围的修复

- **WHEN** 某 build 的首次出现时间落在数据缺口内而不可得
- **THEN** 以可得的最早时间为准，接受「已上线」被推迟的偏差
- **AND** MUST NOT 因此把「已上线」提前

### Requirement: 发版判定不可得时须显式标注

发版判定依赖线上事件与构建数据，取数失败时 MUST 在所有呈现处显式标注「发版判定不可得」，MUST NOT 静默退回只比时间的判定而不加说明。

#### Scenario: 取数失败

- **WHEN** 本轮无法取得构建与事件数据
- **THEN** 修复状态沿用只比时间的结果，并在每处呈现标注「发版判定不可得」
- **AND** 依赖「已修未发版」计数的告警 MUST NOT 计入这些条目

#### Scenario: 业务仓库未能同步

- **WHEN** 本轮未能同步业务仓库，判定基于上次同步的提交与标签
- **THEN** MUST 标注「仓库未同步，发版判定可能滞后」
