# crash-perf-issue-lifecycle Specification

## Purpose
让每个崩溃 issue 在报告中带上生命周期状态——新出现、曾消失又回来、持续存在——使读者无需比对历史即可判断哪些需要立刻关注。

## Requirements

### Requirement: issue 生命周期标记

崩溃 issue 明细 MUST 为每个 issue 标注其生命周期状态：本轮首次出现、曾出现过但上一轮未出现（回归）、以及连续出现（长期）。

判定基准 MUST 来自与崩溃统计**同一数据源**的 issue 标识集合，MUST NOT 依赖另一条独立且可能失效的采集通路。

#### Scenario: 首次出现的 issue

- **WHEN** 某 issue 的标识从未在历史基准中出现
- **THEN** 标注为新增

#### Scenario: 曾消失又出现的 issue

- **WHEN** 某 issue 曾出现在历史基准中，但上一轮未出现，本轮又出现
- **THEN** 标注为回归
- **AND** 该状态与「新增」区分呈现——回归意味着修复失效或场景重现，与全新问题的处置方式不同

#### Scenario: 连续出现的 issue

- **WHEN** 某 issue 上一轮与本轮都出现
- **THEN** 标注为长期存在

### Requirement: 首轮建立基线不标新增

当历史基准不存在或不含生命周期所需结构时，本轮 MUST 只建立基线，MUST NOT 将全部 issue 标注为新增。

理由：首轮把每个 issue 都标成新增会刷满整屏，且与「新增」这个词要传达的信息相反——它应当表示变化，而首轮没有变化可言。

#### Scenario: 基准缺失或结构陈旧

- **WHEN** 历史基准文件不存在，或不含生命周期所需的结构
- **THEN** 本轮建立基线并照常呈现 issue 明细
- **AND** 不标注任何 issue 为新增或回归

### Requirement: 基准保留期有界

生命周期基准 MUST 有明确的保留期，超出保留期的 issue 标识 MUST 被清理。

理由：基准是「见过哪些 issue」的集合，不设上界会无限增长；且过于久远的一次出现，再次出现时更接近新问题而非回归。

#### Scenario: 基准中存在超期条目

- **WHEN** 某 issue 标识的末次出现时间超出保留期
- **THEN** 该标识从基准中清理
- **AND** 该 issue 若再次出现，按新增处理

### Requirement: 台账现状表标注生命周期三态

崩溃台账的 Issue 现状表 MUST 为每行标注生命周期状态，取值 MUST 覆盖三态：本轮首次出现、连续出现、以及曾出现过但上一轮未出现（回归）。

仅有「新增 / 遗留」两态 MUST NOT 视为满足本要求——回归与连续出现在处置上是两件事：回归意味着修复失效或场景重现。

#### Scenario: issue 消失后再次出现

- **WHEN** 某 issue 曾进入过台账基准，上一轮未出现，本轮又出现
- **THEN** 现状表标注为回归
- **AND** 其「首次纳入」MUST 取基准中记录的最早日期，MUST NOT 记为本轮日期

#### Scenario: 基准为空

- **WHEN** 生命周期基准不存在或为空
- **THEN** 本轮只建立基准，MUST NOT 标注任何 issue 为新增或回归

### Requirement: L2 生命周期基准独立于 L1

L2 台账的生命周期基准 MUST 独立维护，MUST NOT 复用 L1 日报的基准。

理由：两条链路的取数口径不同——L1 带版本过滤（只看最新 N 个版本），L2 刻意不带（台账跨版本追踪）。老版本上仍在发生的 issue 从不进入 L1 基准，复用会使其每轮被误判为新增。

#### Scenario: issue 只存在于非最新版本

- **WHEN** 某 issue 只在最新版本之外的版本上发生
- **THEN** 其在台账中的生命周期判定 MUST 基于 L2 自有基准
- **AND** MUST NOT 因未出现在 L1 基准中而被标注为新增

### Requirement: 生命周期基准保留期有界且「上一轮」按基准推断

基准 MUST 有明确保留期，超期条目 MUST 清理。判定「上一轮」MUST 取基准中记录的最大日期，MUST NOT 假设为固定的前一周期。

理由：跑批漏跑时，按固定周期推断会把全部 issue 误判为回归。

#### Scenario: 漏跑一轮后恢复

- **WHEN** 某轮跑批未执行，下一轮正常执行
- **THEN** 连续出现的 issue 仍判定为连续出现，MUST NOT 因周期跳空而被标注为回归

### Requirement: 周报变化摘要区分回归与新增

周报的变化摘要 MUST 区分「本轮首次出现」与「曾出现过、上一轮未出现、本轮又出现」两种情形，MUST NOT 将后者渲染为新增。

判定基准 MUST 与台账现状表使用**同一份**生命周期基准，MUST NOT 为变化摘要另建第三份基准。

理由：变化摘要此前只与上一轮快照比对，「不在上一轮快照中」既包含全新 issue 也包含回归 issue，两者落入同一桶。而台账用 90 天基准可区分三态——于是同一轮跑批可对同一 issue 给出矛盾标签。实测 2026-08-31：`2a800b33` 在日报标注为「长期」，在台账与周报变化摘要标注为「新增」。

#### Scenario: issue 曾消失又出现

- **WHEN** 某 issue 存在于生命周期基准中，上一轮未出现，本轮出现
- **THEN** 变化摘要标注为回归
- **AND** MUST NOT 计入新增

#### Scenario: 基准读取时序

- **WHEN** 变化摘要读取生命周期基准
- **THEN** 读取 MUST 发生在本轮基准提升之前
- **AND** 理由：提升后基准中每个 issue 的末次出现日期均为本轮日期，此时判定的结果恒为「长期」

#### Scenario: 基线轮

- **WHEN** 本轮为基线轮
- **THEN** 变化摘要 MUST NOT 标注任何 issue 为新增或回归

### Requirement: 生命周期标签差异必须标明基准口径

当同一 issue 在不同产物中出现不同的生命周期标签时，各产物 MUST 标明自身判定所依据的基准口径。

理由：L1 与 L2 的基准刻意分离（L1 带版本过滤、L2 不带），标签不一致是设计的必然结果而非缺陷。但读者看到同一条 issue 一处写「长期」、一处写「新增」时，无从判断这是口径差异还是数据错误。

#### Scenario: 读者对照两份产物

- **WHEN** 日报与台账对同一 issue 给出不同生命周期标签
- **THEN** 两份产物 MUST 各自注明其基准的版本过滤口径与保留期
- **AND** MUST NOT 通过合并基准来消除差异
