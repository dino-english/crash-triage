# crash-perf-ledger-ownership Specification

## Purpose

定义崩溃台账（LEDGER）的产出方、渲染结构与飞书同步方式，并划定 L1 移除台账职责后的边界。台账是崩溃处置结论的唯一沉淀载体，由 L2 全权产出。

## Requirements

### Requirement: 台账由 L2 独占产出

台账的生成与同步 MUST 只发生在 L2 周报链路。L1 日报链路 MUST NOT 读取、渲染、投递或镜像台账。

#### Scenario: L1 跑批完成后不产生台账产物

- **WHEN** L1 日报链路完整跑完并成功投递
- **THEN** 投递清单中不含任何台账文档
- **AND** 飞书台账文档的修订版本号不变

#### Scenario: L2 跑批产出台账

- **WHEN** L2 周报链路完整跑完
- **THEN** 本地台账源被更新
- **AND** 飞书台账文档被同步

### Requirement: 台账采用四段式结构

台账 MUST 包含四个段落，顺序固定：项目常量、崩溃收口点登记、Issue 现状表、变更时间线。

#### Scenario: 首次生成台账

- **WHEN** 本地台账源不存在
- **THEN** 生成含全部四段的台账
- **AND** Issue 现状表以本轮取到的线上 issue 建立基线
- **AND** 不迁移任何历史台账内容

#### Scenario: 后续更新台账

- **WHEN** 本地台账源已存在
- **THEN** 保留项目常量与收口点登记两段的既有内容
- **AND** 只更新 Issue 现状表与变更时间线

### Requirement: Issue 现状表为双端单表

Issue 现状表是一张表，iOS 与 Android 的条目共存于其中，通过「平台」列区分。 MUST NOT 按平台拆成多张表或多份文档。

#### Scenario: 双端均有 issue

- **WHEN** 本轮取到 iOS 与 Android 的 issue
- **THEN** 两端条目出现在同一张表中
- **AND** 每行标明所属平台

#### Scenario: 单端无 issue

- **WHEN** 某一端本轮无 issue
- **THEN** 表中仅出现另一端的条目
- **AND** 不因此拆表或省略平台列

### Requirement: 现状表定点更新，时间线只追加

同步台账到飞书时，Issue 现状表 MUST 定点替换，变更时间线 MUST 追加。任何情况下 MUST NOT 整份覆盖文档。

#### Scenario: 同步已有台账文档

- **WHEN** 飞书台账文档已存在且含既有时间线
- **THEN** 现状表被替换为最新内容
- **AND** 既有时间线条目全部保留
- **AND** 本轮变更作为新条目追加在时间线末尾

#### Scenario: 首次同步到既有飞书文档

- **WHEN** 飞书台账文档尚未含四段结构
- **THEN** 四段结构以追加方式写入文档
- **AND** 文档中既有内容一字不改地保留
- **AND** 不使用整份覆盖建立结构

#### Scenario: 定点替换无法定位目标

- **WHEN** 现状表的定位标识失效
- **THEN** 同步失败并明确报错
- **AND** 不退化为整份覆盖

### Requirement: 时间线条目挂周报链接

台账变更时间线的每条记录 MUST 挂载产出该变化的那一轮周报链接，**并 MUST 携带该 issue 的标识**。

理由（追加）：时间线是台账里唯一按时间排列的部分，也是回溯「这条崩溃什么时候第一次出现」的入口。只有标题时，标题措辞随取数源变化即断链。

#### Scenario: 追加时间线条目

- **WHEN** 本轮周报已成功投递并取得文档 URL
- **THEN** 新增的时间线条目包含该周报链接
- **AND** 该条目 MUST 同时包含 issue 标识与变化类型

#### Scenario: 周报未投递成功

- **WHEN** 周报文档投递失败
- **THEN** 不追加时间线条目
- **AND** 台账保持上一轮状态

#### Scenario: 去重判据受标识影响

- **WHEN** 时间线条目的正文因加入 issue 标识而变化
- **THEN** 首轮同步 MUST 确认既有条目不会因正文变化而被判为不重复并重复追加
- **AND** 理由：去重判据是「去掉周报链接后缀的正文」，正文格式变更会使其对历史条目失效

### Requirement: 台账同步失败不影响周报投递

台账同步是周报投递之后的独立步骤，其失败 MUST NOT 改变周报链路的成败判定。

#### Scenario: 周报成功但台账同步失败

- **WHEN** 周报文档与卡片均已投递成功
- **AND** 台账同步步骤失败
- **THEN** 本轮周报仍判定为成功
- **AND** 失败原因被记录，可单独重跑台账同步

### Requirement: 台账图例不得把「消失」与「关闭」并列为同一态

台账图例 MUST 分别定义「消失」与「已修复」，MUST NOT 将「已关闭」列为可呈现的状态。

「消失」的含义 MUST 明确为**滚动窗口内无事件**，并显式标注其不等于已修复。

理由：图例此前写作「✅已消失/已关闭」，把三件事压成一格——「窗口内无事件」（可得）、「代码已改并发版」（依赖 commit 反扫）、「Firebase 控制台 issue 状态为 CLOSED」（不可得）。而周报正文的口径注解自己写明「『消失』是窗口内无事件，不等于已修复」，两处矛盾。

#### Scenario: issue 在窗口内无事件

- **WHEN** 某 issue 本轮窗口内无事件
- **THEN** 标注为消失，并注明其含义为窗口内无事件
- **AND** MUST NOT 表述为已修复或已关闭

#### Scenario: 处置状态列依赖的约定未被遵守

- **WHEN** 修复提交未采用约定的 issue 标记格式
- **THEN** 处置状态列停留在上一轮取值
- **AND** 图例 MUST 注明该列依赖提交约定，未被遵守时不更新
- **AND** MUST NOT 将其渲染为「未修复」
