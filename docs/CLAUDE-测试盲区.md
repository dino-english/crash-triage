# 测试盲区：为什么「测过了」还会在跑批时炸

> 2026-08-24 复盘。当天我在一条链路上连续引入 7 个 bug，**每一个改动前都做了函数级测试**，
> 却仍有 5 个要等到跑批（5–15 分钟）甚至由使用方读产物才发现。
> ⛔ 结论不是「测得不够仔细」——是**测试方法有结构性盲区**，再仔细也堵不上。
> ⚠️ 2026-09-15 补了第五条：**查了数据也会错**——那次不是没测，是测了还错了四次，且都是同一个形状。

## 二、七个结构性盲区

### 盲区① 抽函数出来测 = 把「顺序」测没了

典型夹具：

```bash
{ echo '常量=值'; sed -n '/^my_fn() {/,/^}/p' script.sh; echo 'my_fn 参数'; } | bash
```

⛔ 这把函数从它在文件里的位置**摘了出来**，于是「定义在使用点之后」这类错误在夹具里**永远重现不了**——夹具里它总是先定义后使用。

当天三次同类错误全部源于此。⚠️ 这不是夹具写得糙，是**这种测法在原理上看不见顺序**。

**解法**：顺序是静态属性 → 用静态检查（`bin/test/lint-order.py`，check-scripts 第 7 项），⛔ 不要指望动态测试。

### 盲区② 只测「坏输入会红」，不测「好输入不红」

给 `q_render` 加多传检测时，我塞了违规样本确认变红就收工。而它对**正常设计**（通用包装固定传一整套占位符）也报——当轮跑批就给使用方发了误报告警卡。

⚠️ 一个乱红的检查比没有检查更危险：**它训练人忽略告警**。

**解法**：每加一项检查做**双向测试** ①违规样本变红 ②**当前全量代码不红**。已写进 `check-scripts.sh` 文件头。

### 盲区③ 夹具的 shell 设置与生产不同

| | 生产（`crash-*.sh` 头部） | 我的典型夹具 |
|---|---|---|
| `set -e` | ✅ | ❌ |
| `set -u` | ✅ | ✅ |
| `pipefail` | ✅ | ✅ |
| `errtrace` + ERR trap | ✅ 发告警 | ❌ |

F31 就死在这里：`grep -o` 无匹配返回 1，**在夹具里只是个被忽略的退出码，在生产里是一张告警卡**。
我测了 `rc=0`（函数返回值确实是 0），但没测「过程中有没有命令返回非零踩到 ERR trap」。

**解法**：`bin/test/harness.sh`——让函数级测试跑在**与生产相同的 shell 设置**下，ERR trap 触发即判失败。

### 盲区④ 卡片的**列宽**只有真发一张才验得出

DRY RUN 与日报 markdown 预览渲染的是同一批数据、同一套列，看上去完全正常——但 CardKit 表格
**总宽固定、按列数比例分配**，截断只发生在飞书客户端的真实渲染里。

**发生**：2026-08-27 把卡片从每端 2 列改成 3 列（7 列表），DRY RUN 一切正常，实发第一张就被截。

**怎么验**（不必重跑整条链路）：dry-run 已经把卡片写到 `$STATE/publish/card.json`，直接单发一张：

```bash
. "$STATE/local.env"   # 开发机 CRASH_REPORT_CHAT_ID 已是 ou_ 私聊，不是日报群
lark-cli --profile crash-triage im +messages-send \
  --user-id "$CRASH_REPORT_CHAT_ID" --msg-type interactive \
  --content "$(cat "$STATE/publish/card.json")" \
  --idempotency-key <每次换> --as bot --format json
```

不写 state、不建文档、不碰归档。⚠️ 返回的 `chat_id` 是 p2p 会话（**也是 `oc_` 开头**），
与日报群 `oc_655033f1…` 不同，别看到 `oc_` 就以为发错了。

⛔ **这张卡的三个按钮是死的，发之前先说一声**：`__DETAIL_URL__` / `__INDEX_URL__` / `__FOLDER_URL__`
由 `deliver.sh` 在**飞书文档建好之后**才回填（`deliver.sh:381-388`），dry-run 产出的 `card.json` 里还是占位符原文。
验列宽不受影响（版面与文案照常渲染），但收卡的人点「详情」会打不开。
⚠️ 要连按钮一起验，只能走真实投递——那会建文档、写归档，是另一件事。

⛔ 压缩文案时**只压卡片、文档保持完整**，且⛔ **不得为了省宽度砍掉有记录的口径标注**
（样本量括注、两端窗口标注这类）——那不是排版问题，是口径问题。

### 盲区⑤ 查了数据也会错——**聚合结果里的「缺席」不是证据**

2026-09-15。这一轮不是「没测」，是**测了、还错了四次**，而且四次是同一个形状。

起点是一句结论：「iOS 1.7.0 / 1.8.0 在性能表里 30 天零行」。它来自一条
`GROUP BY app_display_version` 的输出——**1.7.0 不在结果里**。
⛔ 但 GROUP BY 的结果里「某个值不出现」**至少有三种成因，输出长得一模一样**：

1. 真的零行
2. 那些行的 `app_display_version` 是 **NULL / 空串**（不进 GROUP BY 的可见结果）
3. 版本字符串是**别的格式**（`1.7.0 (18)`、写进了 `app_build_version`…）

我读成了第 1 种——**因为第 1 种正好符合我已经从代码推出来的故事**（`#if DEBUG` 关采集）。
⚠️ 这一步没有「推断」的自觉：我当时认为自己在读数据。

**同一轮里同一形状的四次**：

| 结论 | 缺的那一步 | 代价 |
| --- | --- | --- |
| 「Android 也被 debug manifest 关掉」 | 没查 Android 的数据 | 实测 Android 内部包**有**性能数据 |
| 「有 git tag 就有数据」 | 没找反例 | 同一个有 tag 的 1.6.0，12 个内部 build 全零 |
| 「Android 1.7.0 已发版却零性能」 | **没查那张表的 max 时间戳** | 拿还没导出的时段下结论（F49） |
| 「第 4 态没问题」 | 没拿卡片的断言去对表 | 误报已发进群（F49） |

**共同点**：每次都有一个讲得通的解释，然后**停在「讲得通」，而不是「我试着推翻过它」**。
而推翻它往往只要多一条查询——事后补的那条查询是：
`COUNT(*) / COUNTIF(ver IS NULL) / COUNT(DISTINCT ver) / STRING_AGG(DISTINCT ver)`，**一行**。

⚠️ **最难堪的一条**：`measure-before-inferring` 这条教训**早就写下来了**，这一轮我还引用过它。
它没在该触发的时候触发，因为**触发条件被我判错了**——我不觉得自己在推断。
⛔ 所以「记住要实测」这种自律型规矩是靠不住的，得换成**对查询形状的机械检查**。

**三条硬规矩**（声称任何「零 / 缺失 / 没有」之前必须过）：

1. ⛔ **字段本身干不干净**——NULL、空串、格式变体各查一遍。**GROUP BY 里的缺席不是证据。**
   实测样板：iOS 性能表 2,576,589 行、NULL 0、空串 0、distinct 版本恰好 7 个，**这才叫零行**。
2. ⛔ **找对照组**——另一端 / 另一版本 / 另一张表，证明**链路本身是通的**。
   实测样板：同一套导出链路下 **Android 性能表里 1.7.0 / 1.8.0 都在** ⇒ 「iOS 那两版不在」
   不可能是导出对新版本的结构性缺陷。⚠️ 没有对照组时，「A 没有」什么都证明不了。
3. ⛔ **窗口内的结论，先查表的 `MAX(event_timestamp)`**——否则就是拿还没到的数据下结论（F49）。

**与既有条目的关系**：F3 是「按字段存在推断可用」，讲**字段**；这条讲**查询形状**——
聚合会把三种不同的世界压成同一行输出。⚠️ 和盲区①同构：那条是抽函数把「顺序」测没了，
这条是聚合把「为什么没有」压没了。**都是所用工具的分辨率低于所下结论的分辨率。**

### 盲区⑥ 流水线说「全绿」≠ 读的人拿到的东西变好了

2026-09-21。`crash-fact-cache-model-free-events` 上线后连核四轮，我报的是「全绿，置信度 9/10」：
退出码 0 · 产物断言 0 ❌ · 待补 0 · 事实层从 194 条长到 247 条 · 台账三处同步成功。
⛔ **每一项都是流水线在评价它自己。**

真相是同一批改动把 L2 周报的证据等级打没了：

| 周报 | ✅钻取确认 | ⚠️聚合推断 |
| --- | --- | --- |
| 09-14（改动前） | 4 处 | 0 |
| 09-21（改动后） | **0 处** | **6 处** |

原因是 prompt 里「不许写事实层」被我写成了「不要读它、不要写它」（F52 的回归段）。
⚠️ **事实层数据变多了，读者拿到的证据反而归零**——这个方向相反的结果，
恰恰藏在「事实层从 194 长到 247」这句漂亮的健康指标后面。

**为什么既有的检查一条都没红**：断言问的是「文件在不在 / 时刻新不新 / 有没有真事件」，
夹具问的是「prompt 里有没有那句话」。⛔ **没有任何一条在问「模型还拿不拿得到证据」**，
也没有任何一条在比较**本期产物与上期产物**。

**判据**：改动碰到模型 prompt、取数范围或权限边界时，验收必须包含一次
**本期产物 vs 上期产物的内容对比**，而且比的是**读者会读的那几个字段**
（证据等级 / 根因 / 结论），不是字节数、行数、章节数。
⚠️ 字节数会骗人——这次改动后的周报**更长了**（27027 → 30303 字节）、
「堆栈」一词还从 0 次涨到 3 次，而它多出来的篇幅正是在解释自己读不到东西。

⛔ 与盲区⑤ 的区别：那条是「查数据的姿势错了」，这条是「**根本没去查下游**」。

**⚠️ 补一句同样重要的**：发现后我本想「等下周一的 L2 再看修没修好」。
⛔ 那是拿下一次生产跑批当实验。实际做法是把分析步骤（`fetch-snapshot.sh full`）
单独跑一次——STATE 指向副本、事实层拷真数据、它自己不投递也不提升基线——
当场得到 ✅钻取确认 **5 处**（改动前 4 处、带 bug 时 0 处）。
⇒ **「只能等下一轮」多半是没去找单跑那一段的办法**（memory: measure-before-inferring）。

**⚠️ 这条已经有检测了**（2026-09-21）：夹具静默跳过的那一半——`check-scripts.sh`
第 8 项现在禁止夹具里出现 `exit 0`（唯一合法结尾是 `h_summary`，缺依赖用 `exit 77`），
并把跳过数打在「✅ 全部通过」之前。⛔ 但**「没去比下游产物」那一半仍然无工具可抓**，
它靠的是上面第 7 条判据和人。

### 盲区⑦ 「本地全绿」与「发出去的东西对」是两件事——2026-09-22 三比零

盲区④说的是卡片列宽；这一条是它的**一般形式**，而且有了硬数据：

当天 `check-scripts.sh` 十项全过、55 条函数级夹具 0 失败、两次整跑 `NO_DELIVER` rc=0、
产物自检 4 通过。**在这个状态下实发，仍然挖出三个真缺陷**：

| 缺陷 | 本地为什么看不见 |
| --- | --- |
| ANR 判据长版与「本次运行」被粘成同一个 callout（F58） | markdown 里只是少一个空行 |
| `sync_ledger` bootstrap 打 ✅ 而文档一字未写（F57） | 退出码 0，输出被 `>/dev/null` 丢了 |
| `overwrite_doc` 同一个洞（F57） | 同上，而且它每天在生产跑 |

同一天还顺手发现索引页「今日日报」入口**每天都是秃的**（F59）——跑批天天打 ✅。

⛔ **判据**：凡是「渲染 / 写入 / 排版」类的改动，本地全绿**不构成任何证据**。
必须实发一次并 `docs +fetch` **把产物读回来**。
⚠️ 把这类风险判成「非阻塞」时，如果理由是推理而不是实测——2026-09-22 这个推理三次全错。

## 三、判据（动手前问自己）

1. 这个改动的错误**会以什么形式表现**？值不对（动态测试能抓）/ 顺序不对（只有静态检查能抓）/ 退出码不对（要 harness）/ 文案与实况不符（只有人读产物能抓，见 F29）
2. 我的夹具**有没有生产的 shell 设置**？
3. 我有没有测**正常路径不报错**，而不只是**异常路径报错**？
4. 我的断言是**正向**的吗（必须出现 X）还是只是「没崩」？⚠️ 空输出常常被当成合法。
5. 我新加的断言**真的在 gating 吗**？⚠️ 追加到 `h_summary` 之后会照常打印 ✅ 却不进统计（F36）。判据：故意植入一个违规样本，看退出码变不变。
6. 我这次验收**看到的东西，是不是就是要发出去的东西**？⚠️ 同一份数据有两个渲染点时，预览可能来自没被改的那个（F35）；卡片列宽则连正确的预览也验不出（盲区④）。
7. 我核的是**流水线的健康**还是**读者拿到的东西**？⚠️ 退出码、断言、条数增长全是流水线
   在评价自己。碰 prompt / 取数范围 / 权限边界的改动，必须比一次**本期 vs 上期的产物内容**
   （证据等级、根因、结论这些读者真会读的字段），⛔ 比字节数与章节数会得出相反结论（盲区⑥）。
8. 我说「没有 / 零 / 缺失」时，**用的查询分辨得出「真没有」和「查错地方」吗**？
   ⛔ 聚合里的缺席不是证据（盲区⑤）：先查 NULL / 空串 / 格式变体，再找一个**对照组**证明链路是通的。

## 四、仍然抓不到的（诚实登记）

- **F29 类**：文案与实况自相矛盾（原因写"显式跳过"、建议写"等额度恢复"）。两行各自都对，错的是组合。⛔ **没有工具能抓**，只有人读产物。
- **F18 类**：模型路径产物的非确定性——冻结缓存冻得住 bq，冻不住模型。
- **跨轮潜伏**：`WOW_CUT` 那种"首轮不进分支、第二轮才炸"。静态检查能抓这一个，但同类未必都能。
