# 失效模式登记

> 记录**已经发生过**的失效，以及它们各自「能不能被工具抓住」。
> ⛔ 本文不是坑的流水账——每条必须回答一个问题：**下次重犯时，谁会发现？**
> 没有答案的那几条（标 🔇）是本仓库真正的风险面，改动碰到它们时要人肉过一遍。

## 怎么用

- 动 `bin/` 之前扫一眼「🔇 无工具可抓」一节。
- 新发现一类失效，按同样格式补进来，并**明确写出检测手段或承认没有**。
- 单点 bug 不进本文——只收**会重复发生的模式**。单点修复记在对应 openspec change 里。

## 一、🔇 无工具可抓（最高风险）

### F37 · `[ -s ]` 判的是「有没有字节」，不是「有没有内容」

```bash
printf '%s\n' "$(cat "$f")" > "$f".t && mv "$f".t "$f"   # 去尾随空行
if [ -s "$f" ]; then 追加; else echo "跳过（幂等）"; fi
```

`$f` 内容为空时，`printf '%s\n' ""` **仍然写出一个换行**——文件 1 字节，`[ -s ]` 判非空，
于是「跳过（幂等）」那条分支**永远走不到**，每次都追加一个空行。

**发生**：2026-08-27 跑 change `crash-report-correctness-fixes` 的 2.4 负向测试（连跑两轮验时间线不增长）。
⚠️ **条目数确实零增长（23 → 23），只数条目会判它通过**——但空行 6 → 7，
每一轮「无新增条目」的跑批都在往台账时间线里塞一个空行。周跑一年就是 50 多个。

**与 F21 / F31 同一类**：那两条是把 grep 的**退出码**当成错误信号，这一条是把**文件字节数**当成内容判据。
共同点是**用一个近似量代替真正想判的东西**，而近似在边界上失真。

**防复发**：⚠️ 想判「有没有内容」就写 `[ -n "$(cat "$f")" ]`——`$(…)` 会剥掉全部尾随换行，
只剩空白时正好判空。⛔ 负向测试**不能只数条目数**：要比对完整产物（逐字节 diff），
否则「形状对了、内容在漂」这类泄漏一律看不见。

### F33 · 窗口「容忍滞后」≠ 窗口内数据完整

`crash-perf-data-staleness-guard` 把性能窗口放宽到 3 天以容忍批量导出约 2 天的滞后。窗口是宽了，
**但没人问过尾部那一天只有 7 小时怎么办**——滞后被容忍了，不完整没有被处理。

**发生**：2026-08-27。firebase_performance 每天只灌到 06:59 UTC，表里**最后一个日历日恒为 7 小时的残日**
（实测 iOS：08-25 有 24 小时 44420 行，08-26 只有 7 小时 3988 行）。后果有两层，第二层严重得多：

1. 残日掺进滚动窗口，把样本稀释掉一截；
2. **DoD 的「今日」正好取中它**——`perf_day_offset()` 取 `MAX(DATE(event_timestamp))`，那恰恰是残日。
   实测 iOS 1.5.4：残日 08-26 只有 29 个样本 P95 **548ms**，完整日 08-25 是 192 个样本 P95 **1044ms**。
   照旧口径会渲染出「启动 P95 −496ms ↓」的**假改善**。⚠️ 环比两边口径不同，差值无意义。

**为什么一直没被发现**：生产 07:00(+08) = 23:00 UTC 跑，那时残日还没落地（分区约 23:54 UTC 落），
`MAX(DATE(...))` **侥幸取中完整日**。⛔ 这意味着「把 cron 挪晚一点拿更新的数据」这个看似无害的改动
**会单独把这个 bug 激活**——挪到 08:30(=00:30 UTC) 残日已落地，旧口径当场翻车。

**防复发**：⚠️ 判据是**「窗口里每一天都灌完了吗」**，不是「窗口够不够宽」。
⛔ 完整性判据用「表中存在 D+1 的事件 ⇒ D 已完整」，**不要查 `INFORMATION_SCHEMA.PARTITIONS`**——
性能表按**摄取时间**分区，实测存在「无该日分区、按事件日却有数千行」的情况，用分区元数据会得出错误结论。

### F34 · 缺「本轮未取到」这一态，会把故障读成常态

「该版本无数据」一句话压着两种处置完全不同的情况：**这版从来没有过数据**（正常滞后，明天就有）
与**历史有值、这轮没取到**（取数故障或导出退化，要查）。渲染完全一样，于是后者永远不会有人去查。

**发生**：2026-08-27 补 change `crash-data-completeness` C 组时登记。判定所需的历史值一直存在
（`metrics-history.jsonl` / `perf-history.jsonl`），只是没被用来区分。

**这一类的两个连带坑**：

- ⛔ **判据必须显式判 `null`，不得用真值性判断**。慢帧率 / 冻结率 / 接口错误率的 `0` 是合法且常见的值
  （实测 Android 1.5.4 冻结 0.0%），当成缺失会把「今天确实取到了 0」渲染成故障——把好消息读成坏消息。
- ⛔ **「沿用历史值」听起来贴心，但多数时候口径对不上**。五个性能格子没有一个能搬：
  启动 P50/P95 格子是 3 天滚动窗、历史是单日；慢帧最差页与冻结是「最差页单页」、历史是「平台级聚合」；
  接口错误率格子是窗口 top10 端点、历史是全量。⚠️ **判据可以读历史（那只是个布尔），呈现不能搬数值**。

**防复发**：⚠️ 「未取到」文案**必须带日期**——不带日期时连续多轮失败会一直显示同一句话，
看不出已经僵住（`latest_event` 冻结在历史峰值那天就是这么来的，见 F26 一类的同源问题）。

### F35 · 同一张表的列集合有两个定义点，改一个预览就骗过你了

**发生**：2026-08-27 把卡片从每端 2 列改成 3 列。`build_card_table()` 出 CardKit JSON、
`md_table()` 出 DRY RUN 预览与日报 markdown，**两者各写一遍列循环**。只改了前者，
于是 **DRY RUN 预览显示 4 列、真发出去 6 列**。

**为什么危险**：预览是唯一的验收手段，而它给出的正是「没问题」。与 F1 同类（一个目的两份实现），
但更阴——**两份实现的其中一份就是验收工具本身**。

**防复发**：⚠️ 改任何「一份数据两种渲染」的结构前先 `grep -n` 数清渲染点；
⛔ 两处都要留「改一处必须改两处」的注释。⚠️ 判据：**我这次验收看到的东西，是不是就是要发出去的东西？**

### F36 · 断言写在汇总函数之后：会跑、会打印 ✅、但不 gating

**发生**：2026-08-27 给 `bin/test/fn-regression.sh` 追加 12 条断言，直接 `cat >>` 到文件末尾——
而 `h_summary` 在第 64 行。新断言在它**之后**执行：照常打印 ✅，但**不进统计、不影响退出码**。
`check-scripts.sh` 一直报「夹具：17 通过」（新加的 12 条一条没算），一眼扫过去全是绿的。

**同类**：F30（新加的检查自己成了噪音源）说的是「检查响错了」，这一条是「**检查根本没接线**」。
⚠️ 两者都属于「加了检查却没有真的在检查」，而后者更难发现——它没有任何异常输出。

**防复发**：⛔ 新增断言后必须**双向验证**：故意植入一个违规样本，确认退出码变 1、失败计数 +1；
再还原，确认恢复 0。⚠️ 光看「跑出来是绿的」证明不了它在 gating。

顺带：`bin/test/harness.sh` 的 `h_extract` 靠「列 0 的 `}`」找函数结尾，被抽的函数若以 `; }` 收尾，
它会**一路吞掉后面的顶层代码并连同 eval**（实测吞进 `HISTORY="$STATE/…"`，报的是 `STATE: unbound variable`
——错误信息与真正的原因毫无关系）。已加守卫：函数体里出现列 0 的顶层赋值即当场失败。

### F1 · 同一目的两份实现，修了一份就以为修完了

**发生**：bq CSV 解析在仓库里有两套——`md_csv_table` 的 Python `csv.reader`（对）与 7 处 `awk -F,` / `cut -d,`（错）。2026-08-24 修了 L2 的那份，**L1 的 7 处原样留着**，当时还得出过「L1 解析正确、不受影响」的错误论断。

**为什么没被抓**：`check-scripts.sh` 第 4 项只检测**同名**函数跨文件。这类重复**名字都不一样**——`qdim` vs `ver_dim`、`md_csv_table` vs `csv2tsv`、`dim_csv` vs `dims_md`。

**防复发**：加取数包装或解析函数前，先 `grep -n '<sql文件名|目的关键词>' bin/*.sh` 看另一条链路有没有等价物。⚠️ 这是**纪律不是工具**，登记在此就是承认它抓不住。

### F2 · 下游正确 ≠ 上游正确

**发生**：L1 的 `dim_csv()` 先用 `awk -F,` 把原始 CSV 切坏、再重新加引号输出，下游 `md_csv_table` 用 Python 正确解析——**解析的已经是坏数据**。看到「下游用了正确的解析器」就下结论，漏掉了上游。

**防复发**：追数据要从**产生点**追到**消费点**，中间每一次重写都是一个可疑点。判据：这一步的输出还是不是原始格式？

### F3 · 按「字段存在」推断可用

**发生（两次）**：
- `remote_config_feature_rollouts` 字段存在但恒空 → 灰度关联做不了（历史）。
- 2026-08-24 我把 `sessions.session_index` 当成「第几次会话」写进建议——实测 **96% 的值是 0**，`first_session_id` 96.4% 自指，两个字段都在会话组内重置，做不了新老用户拆分。

**防复发**：任何字段进设计前跑覆盖率与**分布**（不只是非空率）。**双端分别验**——实测 `user.id` iOS 96.6% / Android 0%，只验一端会得出完全相反的结论。方法写在 `.claude/agents/crash-report-analyst.md`。

### F4 · 优先级覆盖导致历史数据被冲掉

**发生**：新增生命周期基准时，播种阶段给所有 issue 写了 `first=今天`；而渲染时基准的 `first` 优先级高于上一版表格，**下一轮把台账里真实的历史首次纳入日期全覆盖成了当天**。跑批退出码 0，卡片正常，无任何告警。

**为什么危险**：这是**数据丢失**不是显示错误——历史日期没有别处备份。

**防复发**：同一个值有多个来源时，**取值优先级只允许实现一次**，放在最靠近数据的那一层（此处是 `render-ledger.sh`）。调用方另算一遍必然漂移。

### F5 · append 型产物不幂等

**发生**：台账变更时间线用 awk 无条件追加增量。同周重跑会重算出同一批增量——实测 08-22 那 6 条**各重复 5 遍**，36 条里只有 12 条是真的。

⚠️ CLAUDE.md 曾写「台账同步不需要幂等键（`block_replace` 本身幂等）」——**那句只对现状表成立**，时间线是 append。一句正确的话覆盖了半个场景，比写错更难发现。

**防复发**：任何 append 型写入，追加前查重；查重键要**剔除每轮都会变的部分**（此处是周报链接：未投递是占位符、投递后是真 URL，整行比对查不出重复）。

### F6 · 规格要求了但从未实现，且没人发现

**发生**：spec `crash-perf-issue-lifecycle` 明确要求三态（新增/回归/长期），`render-ledger.sh` 只有两态，「回归」从未被渲染过。台账 14 行全是 🔁遗留。

**防复发**：spec 的 Requirement 与代码之间**没有任何自动映射**。开 change 时逐条对照该 capability 的既有 spec，⛔ 不要只看本次 change 的 delta。

### F7 · 机制在，但依赖的人工约定没人执行

**发生**：修复状态反扫依赖 commit message 的 `crash:` 约定。实测两个业务仓库**近 120 天 0 条**命中，台账「处置状态」14/14 恒为「未处理」——这一列不携带任何信息，但看起来像正常工作。

**防复发**：依赖人工约定的指标，**必须有「约定命中率」这个元指标**，并在命中率为 0 时显式标注「该列当前无效」，而不是渲染成「未处理」。

### F18 · 冻结缓存只冻得住 bq，冻不住模型

**发生**：2026-08-24 做 CSV 收口的等价性验收，`diff -r A B` 里除了预期的那一行，还多出 `$STATE/issues/*.json` 与 `snapshot.json` 的差异——一度以为是改动引入的回归。

**真因**：L1 的事实层由**模型**写（`fetch-snapshot.sh light` → `claude -p` + MCP）。实测同一 issue 在 A 有 69 条事件、B 有 70 条（真实增量抓取），且模型的引号风格与文件末尾换行不稳定（写出过 `"eventId": "'2255524737785064267'"` 这种带字面单引号的值）。

**防复发**：等价性比对时，`issues/` 与 `snapshot.json` **不能做逐字节 diff**——它们不在冻结面内。要么用 `CRASH_REPORT_SKIP_ANALYSIS=1` / 让事实层缓存全命中，要么在 diff 时显式排除并单独人工看。⚠️ 排除后要说出来，不能默默跳过。

**顺带发现（未修）**：模型写进事实层的 `eventId` 带字面单引号，是数据质量问题，不是格式问题。

## 三、验证纪律（本会话实测翻过车）

### F19 · `${var:+（…）}` 绕过了多字节 lint

CLAUDE.md 硬约束写着「⛔ 全角括号一律先条件赋值再拼接，禁 `${var:+（...）}`」，但 `check-scripts.sh` 第 2 项的 lint 只匹配 `$VAR` 紧邻多字节字符（`\$([A-Za-z_]\w*)(?=[^\x00-\x7F])`）——**`${VAR:+（…）}` 这个带花括号的形式它抓不到**。

**发生**：2026-08-24 写前后台摘要行时原样写成了 `${_unk:+（未知 ${_unk}）}`，lint 通过、运行也没炸（这次侥幸），但它正是硬约束点名禁止的写法。

**防复发**：⚠️ 硬约束里被 lint 覆盖的部分只是一半。写全角括号拼接时**先条件赋值再拼**，不要指望 lint 拦。

### F20 · 「取最新版」在事件维度上几乎总是错的

**发生**：前后台摘要行首版写 `$IOS_V1`（最新版）。实测 iOS 1.5.4 非致命只有 14 条（低于阈值直接跳过），真正的 981 条在上一版 1.5.3——**整行渲染不出来**，跑批退出码 0、无告警。

⚠️ 讽刺的是同一个函数（`card_focus_line`）上方几行的既有注释就写着这条：「取**事件最多的那个版本**，不是固定取最新版：新版刚放量时事件常是个位数」。**读过注释仍然写错了。**

**防复发**：凡是「挑一个版本来展示某个事件量」的地方，判据是**事件量最大**而非版本号最新。新版刚放量时样本必然小，这不是例外是常态。

### F14 · 改成 stdin 后忘了去掉尾部文件参数

`awk ... '<脚本>' "$f"` 改成 `csv2tsv < "$f" | awk ...` 时，若尾部 `"$f"` 没删，awk 会**读文件而忽略 stdin**——修复静默失效，输出与改前一模一样。

**防复发**：管道化改造后，故意破坏输入（`< /dev/null`）确认输出真的变了。

### F15 · 测试夹具本身错了，却去怀疑被测代码

zsh 数组**下标从 1 开始**，`${IDS[0]}` 是空串。据此构造的基准让我一度以为渲染器把「遗留」判成了「回归」。

**防复发**：断言失败时先打印夹具内容，确认输入是你以为的那个。

### F16 · 断言判定写反，diff 相同却报「失败」

`diff A B && echo "❌"` —— 相同才是期望，却写成了失败分支。

**防复发**：负向测试——先让断言在**已知应该失败**的输入上真的失败，再信任它的通过。

### F22 · 文案里的字面 `%` 放进 printf 格式串会在运行时炸

`printf '…覆盖 96.6%、**Android 0%**…\n'` —— printf 把 `%、` 与 `%*` 当成格式符，报
`invalid format character`，⚠️ **触发 ERR trap 发出告警卡片**。

**发生**：2026-08-24 加「受影响用户」标注时踩到。代价不只是一个错误——它在**取数跑完 5 分钟之后**的渲染阶段才炸，整轮跑批作废。

**已补上工具**：`check-scripts.sh` 第 8 项（2026-08-24 新增，带负向测试）。⚠️ 此前无任何静态检查覆盖它——`bash -n` 只查语法，格式串内容是合法的。

**防复发**：含字面 `%` 的文案一律走 `printf '%s\n' "…"`，⛔ 不放进格式串。⚠️ 中文报告文案里百分比极常见，这条几乎必然复发——加了新文案行就单独跑一次那行验证（`bash -c "$(sed -n 'N p' file)"`）。

一次性排查全仓的命令：

```bash
grep -n "printf '" bin/*.sh | python3 -c "
import sys,re
for l in sys.stdin:
    loc,_,r=l.partition(':'); n,_,c=r.partition(':')
    m=re.search(r\"printf '([^']*)'\", c)
    if m and '%' in re.sub(r'%%|%[-+ #0-9.]*[sdfxX]','',m.group(1)): print(loc,n)
"
```

### F24 · 🔇→✅ `set -u` 失败会被 EXIT trap 吞成退出码 0（生产级静默）

**发生**：2026-08-24 排查 L2 时发现——脚本因 unbound variable 中途死亡，`baseline.sh` 却报 rc=0。

**根因**（bash 3.2 实测，非本仓库代码写错）：

| 失败方式 | 进 EXIT trap 时的 `$?` |
|---|---|
| **`set -u` 未定义变量** | **0** ← 状态在 trap 运行前就已丢失 |
| 普通命令失败 / 127 / 显式 exit | 正常 |

而 `trap 'rm -f "$X"' EXIT` 的最后一条命令是 `rm -f`（恒返回 0），于是整脚本退出码 = 0。
⚠️ **保留 `$?` 的写法（`_rc=$?; …; exit $_rc`）修不好**——`$?` 本来就是 0。

**为什么严重**：unbound variable 恰是本仓库最常见的失败模式（bash 3.2 把多字节首字节并进变量名，CLAUDE.md 记着「一天内连踩五次」）。实测三重静默：

- 退出码 0 → cron 看到成功
- ERR trap **不触发** → 无告警（shell 错误不算命令失败）
- `health.json` 停在**上一轮**的 `ok:true` → 健康检查显示正常

结果是「群里收不到报告，而所有监控信号都说没事」。

**已修**：四个脚本（crash-daily / crash-weekly / deliver / fetch-snapshot-bq）改用**完成哨兵**——
`trap 'rm -f "$X"; [ "${RUN_COMPLETED:-0}" = 1 ] || exit 1' EXIT`，脚本末尾置 `RUN_COMPLETED=1`。
⚠️ 任何合法的提前 `exit 0`（DRY_RUN / 仅重发卡片）都必须先置位——已处理 2 处。
端到端负向验证：注入 unbound variable → rc=1（修复前 0）。

### F25 · 跑批失败时 baseline.sh 会收走**上一次**的投递产物

`$STATE/publish` 不在 `artifacts_baseline_files` 的还原清单里。脚本死在写 publish 之前时，那里留着上一轮（甚至另一条链路）的产物，`baseline.sh` 原样收走。

**发生**：2026-08-24 L2 失败那轮，收到的「投递产物 6 个」全是 **L1 日报**的 `daily.md` / `daily.xml` / `index.xml`。⚠️ 若不是恰好去看文件名，会以为周报产物正常。

**防复发**：验收脚本断言产物时**先断言文件名对不对**（周报要有 `weekly.md`），⛔ 不要只看「收集了 N 个文件」。本条与 F24 叠加时格外危险：退出码 0 + 产物看似齐全 = 完全看不出失败。

### F23 · ⛔ 编辑正在运行的 bash 脚本

bash **按字节偏移边读边执行**。跑批途中改脚本会让正在运行的进程从错位的偏移继续读，产生完全无关的错误。

**发生**：2026-08-24，L1 跑批途中给 `qc()` 加了一行 sed 参数，文件变长，运行中的进程随即报
`line 870: $1: unbound variable` 与 `line 1121: Crash-free: command not found`——**两处都与改动无关**，
而且触发 ERR trap 发了告警。排查方向一度被引向 ROW_DEFS 与变量作用域。

⚠️ 更隐蔽的情况是它**不报错**：偏移恰好落在另一条合法语句上，跑批「成功」但执行的是拼接出来的逻辑。

**防复发**：跑批期间 ⛔ 一律不碰 `bin/**`。要并行推进就改 `openspec/` / `docs/` / scratchpad，或**新增**文件（新文件不在任何运行中脚本的读取路径上）。⚠️ 判断依据是「有没有进程在跑」而不是「我改的是不是那个文件」——`bin/lib/*.sh` 被 source，同样会咬。

```bash
ps aux | grep -cE '[c]rash-(daily|weekly)\.sh'   # 非 0 就别动 bin/
```

### F32 · 「常见原因」写进产物就成了断言

失败分支原本写死：`模型不可用（退出码 1，**常见原因：额度耗尽 429**）`。
2026-08-24 实测真实是 **API 529 Overloaded**（服务端过载）——⚠️ 读者按「等额度恢复」处理，
而正确动作是「立刻重试」。

⚠️ 这是 F29 的**升级版**：F29 修好了「补救建议跟着原因走」，但**「原因」本身还是猜的**。
「常见原因」这种措辞在代码注释里是合理的推测，**印进产物就变成了对本次失败的断言**。

**已修**：从分析日志里提取 `API Error: NNN` 按码分类（429 额度 / 529 过载 / 5xx 服务端 /
4xx 请求 / 无码则明说「未能识别，需看日志」）。⛔ 识别不出时必须**明说识别不出**，
不得回落到任何「常见原因」。

⚠️ 实施中两个坑：①只扫最新日志会把重试中的空文件当成「无错误码」——要扫全部重试日志；
②`grep` 无匹配返回 1 需 `|| true`（F31）。

### F30 · 新加的「检查」自己成了告警噪音源

2026-08-24 给 `q_render` 加「多传占位符」检测，当轮跑批就给使用方发了一张**误报告警卡**。两个错误叠加：

**① 判据本身错了。** `qc()` 是**通用包装**——一个函数喂多份 SQL，固定传一整套占位符，某份 SQL 用不到其中几个是**设计如此**。我把正常设计当成了异常，于是 `crash-issues.sql` 每次取数都警告一次。

⚠️ 教训：给既有代码加检查前，先问「现有代码为什么这么写」。这个检查如果在写之前跑一遍全量，立刻就能看到它对正常路径也报。

**② 检查自己触发了 ERR trap。**

```bash
[ -n "$extra" ] && echo "⚠️ …" >&2      # extra 为空时整句返回 1
```

作为函数最后一条语句，`set -e` 下返回 1 → ERR trap → **发告警**。⛔ `[ cond ] && cmd` 放在函数末尾（或 `set -e` 下的任意非条件位置）是已知陷阱，要写成 `if … fi` 或补 `|| true`。

**防复发**：⛔ 新增的检查/警告**不得走会触发 ERR trap 的路径**；⚠️ 且加完必须先在**正常数据**上跑一遍确认不报——只测「违规样本会红」是不够的，还要测「合规样本不红」。这与 CLAUDE.md 的告警红线同源：**告警必须只在有事实依据时触发**。

### F29 · 写死的「补救建议」会与它上一行的原因自相矛盾

产物里连着两行：

```
> 分析层：⚠️ **本周无深度分析** — 按 CRASH_REPORT_SKIP_ANALYSIS=1 跳过。
> 缺的只是根因与修复方案。额度恢复后重跑本周即可补齐。
```

原因是**显式跳过**，建议却是**等额度恢复**。跳过分析有三种原因（显式跳过 / 超时 / 模型不可用），只有第三种与额度有关，而补救文案对三种一律写死同一句。

**发生**：2026-08-24 由使用方读产物时发现（「没有额度问题呀」）——⚠️ **不是任何测试或 lint 发现的**，因为两行各自都"正确"，错的是它们的组合。

**防复发**：⛔ 凡是「原因」与「怎么办」成对出现的地方，**「怎么办」必须由产生「原因」的那个分支一并赋值**，不能在渲染处写死。判据：把原因换成另一种取值，那句建议还成立吗？

⚠️ 与 CLAUDE.md 记的 NON_FATAL「线上仍为零上报」是同一类——**静态文案与实况相反**。那次是文案过期，这次是文案只覆盖了三分之一的分支。

### F26 · 一个数字的「同名不同义」比它算错更难发现

同一份周报里两个都叫「崩溃率」：二段 `0.42%`（FATAL / 全部会话）、三段 `2.83%`（FATAL+ANR / 该系统版本会话）——**差 6.7 倍，都对，但读者会当成同一个率**。

**发生**：2026-08-24 audit。唯一的口径提示离数字 19 行，且措辞只说「崩溃**列**不可相加对照」，没说「崩溃**率**不是同一个率」。

**防复发**：⛔ 同名指标在同一份产物里出现两次时，**列名本身必须带口径**（`FATAL率` / `FATAL+ANR率`），⚠️ 不能靠段落注释区分——读者是扫表格的，不是逐段读注释的。同类还有：`—` 在同一份文档里出现三种含义（无此概念 / 样本不足不可算 / 缺数），每种都要有紧邻的图例。

### F27 · 必要标注离数字太远等于没有标注

crash-free 与 ANR 的「下界估计」「不可对照 Play 门槛」两条硬约束写在六段口径区，而数字在二段——**相隔 155 行**。

⚠️ 这不是「重复写了两遍」可以删掉的那种冗余，恰恰相反：**该写两遍的地方只写了一遍，还写在了远处**。

**防复发**：判据是「读者看到数字时，标注在不在同一屏」。⛔ 别把「六段已经写了」当成二段可以不写的理由。⚠️ 反向陷阱：六段那份是卡片共用的 `NOTE_MD`，删它会连带改卡片——**去重要按渲染点分开处理**。

### F28 · awk 字符串拼接里的 `%%` 不会被折成 `%`

`printf` 格式串里 `%%` 表示一个字面 `%`；但 awk 的**字符串拼接**（`s = s "..." "%%" "..."`）里它就是两个字符。

**发生**：2026-08-24 下钻脚注渲染出 `88%%；共 2 种机型`。⚠️ 与 F22（格式串里的字面 `%`）是**方向相反的同一类错**——一个该转义没转，一个不该转义却转了。判据：**这段字符串是喂给 printf 的格式串，还是纯拼接？**

### F31 · grep 的退出码表达「有没有匹配」，不是「有没有出错」

`left="$(… | grep -o '{{[A-Z_]*}}' | sort -u | tr '\n' ' ')"` —— **无匹配时 grep 返回 1**，
而「无匹配」恰恰是**成功路径**（没有漏传的占位符）。`set -e` + `pipefail` 下赋值状态为 1
→ ERR trap → **每次成功渲染都发一张告警卡**。

**发生**：2026-08-24 `q_render` 的缺项检查。⚠️ 由使用方发现（「L1、L2 都报错？」）——
跑批本身 rc=0、产物正常，只是**多了一张告警卡**，日志里那行 `📣` 夹在正常输出中间毫不显眼。

**与 F21 是同一类**（`grep -c … || echo 0` 得到 `"0\n0"`），但表现相反：
F21 是**有匹配才对**、F31 是**无匹配才对**。共同点是把 grep 的退出码当成了错误信号。

**防复发**：⛔ 任何把 grep 放进命令替换或 `set -e` 路径的地方都要 `|| true`；
⚠️ 判据：**这条 grep 找不到东西时，是正常还是异常？** 是正常就必须兜。
同类命令还有 `diff`（有差异返回 1）、`test`/`[`（假返回 1）。

### F21 · `grep -c … || echo 0` 会得到两个 0

`grep -c` 零匹配时**既输出 `0` 又返回退出码 1**。于是 `$(grep -c … || echo 0)` 里两边都执行，值变成 `"0\n0"`，后续 `[ "$n" -gt 0 ]` 直接报 `integer expression expected`。

**发生**：2026-08-24 写复发率计数时踩到。⚠️ 危险之处在于它**只在零匹配那条路径上炸**——有匹配时一切正常，测试若只跑「有数据」的用例就发现不了。

**防复发**：写 `$(grep -c … || true)`（保留 grep 自己输出的 `0`），再 `${n:-0}` 兜住文件不存在的情况。⚠️ 计数类断言必须**同时测有匹配与零匹配两条路径**。

### F17 · 管道吞掉退出码

`cmd | tail -30; echo "rc=$?"` 拿到的是 `tail` 的退出码。

**防复发**：要退出码就别接管道，`cmd > file 2>&1; echo $?`。

## 四、跑批与验收的既有陷阱

- ⚠️ **活数据上 diff 永远不为空**（滚动窗口锚在跑批时刻，实测 6 分钟内 sessions 就变）——等价性验收必须用 `CRASH_REPORT_BQ_CACHE` 冻结，**生产禁用**。
- ⚠️ **L2 的基线提升在 NO_DELIVER 闸门之前**——「跑两次对比产物」在 L2 不成立。`bin/test/baseline.sh` 的快照回滚协议就是为此存在，⛔ 新增基准文件必须登记进 `bin/test/artifacts.sh`，否则回滚不还原它、两次跑批走不同分支。
- ⚠️ **整跑 5 分钟以上，别设短超时**——进程被信号杀掉会触发 ERR trap，把「被杀」当故障告警**发进群**。
- ⚠️ `BASELINE_KEEP_STATE=1` 的那一轮**不还原状态**，下一轮的还原点是它跑完之后——连跑结束时 `$STATE` 停在第一轮之后，不是跑批前。要回到跑批前得自己备份。

## F36 · issue 开关状态不可得，别按「字段应该有」去找

BigQuery Crashlytics 导出的 schema 里与 issue 相关的字段**只有** `issue_id` / `issue_title` /
`issue_subtitle`（2026-09-01 `bq show --schema` 实测），**没有任何 state / closed / regressed 字段**。
唯一能给出 OPEN/CLOSED 的通路是 MCP `topIssues`，而它只返回 OPEN issue——关闭即从列表消失，
正是 `crash-source-bigquery-migration` 当初迁走的原因，且 2026-08-06 有过误关线上 issue 的事故。

⛔ 台账图例不得把「消失」与「关闭」并列：**消失 = 滚动窗口内无事件**，不等于已修复，更不等于已关闭。
与 `remote_config_feature_rollouts` 恒空那条同源——**先查有没有值，别按「字段存在」推断可用**。

## F37 · 共享变量的消费点不数清就改，改完还长得挺对

`CHANGES_MD`（周报段一）有**三个**消费点：群消息 `message.md`、飞书卡片、周报文档。
2026-09-01 实施 `crash-report-issue-identity` 时按「只有两个」去改，结果把控制台链接加进了群消息、
**周报文档反而一条都没有**——静态看不出来，是跑完 E2E 比对三份产物才发现的。

与 F35（卡片表格的列集合有两个定义点）同族。⛔ 拆分或改共享渲染变量前先 `grep -n` 数清全部消费点，
并把清单写进代码注释里，别让下一个人再数一遍。

## F38 · 「报告太啰嗦」多半不是排版问题，是口径复杂度的代价

2026-09-01 实测周报：提示块占 28.8%，看起来像典型的「免责声明比数据多」。但逐条按
「这条信息的读者是谁」归类后，39 行里**能移走的只有 1 行**（run_id 与审计路径）、
**能去重的只有 1 处**（段四重复了段三的 owner 读法）；其余全是判读须知——
「`—` 表示该桶会话数不足」「crash-free 是下界估计」「ANR 率不可对照 Play 门槛」
「页面维度没有分母」——不知道就会读错数字。实施后降幅 **0.1 个百分点**。

⛔ **不要把「注解多」直接当成排版冗余去砍**。先做四层归类，看能移走的到底有几条。
真正的杠杆在**降低口径复杂度本身**（统一版本集与 error_type 集），那是重新设计口径，不是排版。

⚠️ 同期还证伪了一个想当然的前提：「把下钻交给 Firebase 控制台」——实测投递群 15 人中
只有 5 人能在项目 IAM 里匹配到，**约三分之二读者点不开链接**。
⛔ 提出「交给上游系统」这类方案前，先查读者有没有那个系统的权限。

## F39 · 「对方没遵守约定」先证伪一次，可能是我们只认一种没人用的写法

台账「处置状态」列两个月来两端全空，文档里记的原因是「Android 未采用提交带 issue ID 的约定
（2026-08-07 核实：全仓 0 处 32 位 hex 引用）」。2026-09-01 重查：

```
[crash:<8位>]              iOS 0 条 · Android 0 条    ← 我们唯一认的写法，没人用
Crashlytics[ issue]:<32位>  iOS 1 条 · Android 4 条    ← 大家实际在用的写法
```

4 个 Android id 经 BigQuery 复核全是真 issue。改扫描器后反扫从 **0 条变 6 条**——
其中 `470ed3ef` 正是 08-31 周报报「✅消失」的那条 iOS issue，它其实是被代码修好的。

⛔ **「自动对账恒为空」不要直接归因成「对方不配合」**，先看我们的匹配条件是不是太窄。
⚠️ 两个仓库的落点还不同（Android 在 subject、iOS 在 body），只扫 `%s` 会漏掉一半——
**扫整条 message**。

## F40 · 累计量当版本判据，在版本交替期必然滞后

周报「主力版本 = 近 7 天会话量 top2」是一个**滞后积分量**：新版放量再快，也要若干天才能在累计值上
超过旧版；等它超过时，放量期已经过去了。

实测 2026-08-31（跑批当天）：

```
Android 当日会话   1.5.6 855（93%） · 1.5.5 46 · 1.5.4 20
Android 7 天累计   1.5.4 3666 · 1.5.5 2064 · 1.5.6 1819   ← 1.5.6 差 245 落榜
```

于是周报第二/三/四段整段在描述当天合计仅 66 个会话的两个版本，而 1.5.6 上的 3 条 FATAL issue
一条都没呈现。⛔ **这个 bug 只在放量窗口内可见**——滚动窗口几天后自己就追上了，事后再查什么都看不到，
这正是它一直没被发现的原因。

处置（change `crash-report-version-alignment`）：判据改为「窗口 top2 ∪ **当日** top1」，上限 3，逐行标注入选理由。
⛔ 不换判据只补一列——窗口累计答「盘子里的大头」，当日答「现在线上跑什么」，**分歧本身就是要看见的信息**。

⚠️ **验证这类 bug 不必等下一次发版**：把窗口调长即可在活数据上复现病症形态。
实测 `CRASH_REPORT_WEEK_DAYS=14` 时 14 天 top2 是 1.5.3(6062)/1.5.4(4448)、当日 top1 是 1.5.6 → 补列路径激活。

## F41 · `ok:true` 不等于操作生效——飞书写指令会「调用成功、文档没改」

2026-09-01 实测：`docs +update --command block_replace` 返回

```json
{ "ok": true, "data": { "result": "failed",
  "warnings": ["degrade_code=1011,msg=Instruction produced no document changes."] } }
```

而 `deliver.sh` 此前**只判进程退出码**，于是跑批日志打「✅ 台账已同步」、文档一个字没变、无人知晓。
与既有纪律同源：**「成功」判据必须两端一致**——CLI 说调用成功、飞书说没改，就是不一致。

实测两条触发路径：
1. **profile 未配置**（开发机上 `--profile crash-triage` 的 appId 为 null）→ 写操作降级空转
2. **block id 已被消费**——⚠️ `block_replace` **同一 block 仅限一次**，替换后旧 id 立即失效；
   拿旧 id 再替换就是 1011。排查时我用死 id 连试三次全失败，差点误判成「新加的链接把表格搞坏了」。

⛔ **修法不能只判 `result`**：内容与线上一致时飞书同样返回 1011，而那是**平稳周的常态**
（「L2 平稳周照常投递」是既有硬约束）。第一版补丁就踩了这个假阳性。
正确做法是**替换前先比对**：一致则跳过替换、压根不产生降级；不一致才写，并要求 `result=success`。

⚠️ 比对**不能逐字**：取回的 markdown 带 `<fragment>` 包裹，链接与转义还有往返差异——
实测同一份内容两边差 386 字符。改用扛得住往返的**指纹**（数据行数 + 表内 8 位 id 集合）。

⚠️ `_lark_write_ok` 是谓词函数，⛔ 必须用在条件位——裸调会在 `set -e` + ERR trap 下触发假告警
（夹具 `fn-lark-write-result.sh` 第一版就是这么写的，被 harness 当场抓出）。

## F42 · 卡片能力靠类推会推错——「裸 URL」和「markdown 链接」不是一回事

`crash-report-issue-identity` 给卡片下了「MUST NOT 附外部链接」的禁令，理由是
「卡片单元格宽度有限，链接会挤占并触发截断」。2026-09-01 实发一张测试卡片，结论是**一半对一半错**：

| 卡片里的载体 | 链接可点 | 列宽影响 |
|---|---|---|
| `{tag:"markdown"}` 块（**周报段一就在这里**） | ✅ | **无变化** |
| `{tag:"table"}` 单元格（`lark_md`） | ❌ | 会显示字面 markdown 并撑宽 |

`[2a800b33](url)` 只显示锚文本，与纯文本一样宽——⛔ 会撑宽的是**裸 URL**，不是 markdown 链接。
代价：卡片是群里多数人唯一会看的产物，最该能下钻的地方被自己禁掉了两天。

⛔ **卡片能力的结论只能来自真实发送一张卡片**（已写进 spec 作为硬要求）——
DRY RUN、markdown 预览、以及「同类推断」都不算。与既有的「卡片列宽只有真发一张才验得出」同源，
但那条只说了列宽；**可点性是另一个维度，上一轮实发时只验了列宽、没顺手验链接，等于白发一次**。

## F43 · 两条链路的平台键不是同一套——`ios/android` vs `ios/and`

2026-09-02 用户发现：日报里 **Android 的 issue 全都点不开，iOS 正常**。

根因是 `issue_url` / `issue_url_prefix` 只认 `android`，而 **L1 日报内部一路用 `and`**
（`AND_CRASH_TBL` / `mv_ and` / `xml_issues and "$v"` …）；L2 周报用 snapshot 的 `android`，所以周报没事。
键落到 `(*)` 兜底 → 返回空串 → 那一段一条链接都不出，**静态看不出、退出码也正常**。

⛔ **三道防线同时漏掉，全都是「只验了有没有、没验每个平台都有」**：

1. 夹具只测 `ios` 一个键——单平台通过就以为覆盖了
2. E2E 数的是**总链接数**（daily.xml 5 个、index.xml 6 个），总数非零就放过
3. 实发卡片验的是周报段一（用 `android`，本来就对）；日报卡片是表格没有链接，看不出

⚠️ 凡是「按平台分支」的东西——渲染、取数、告警——**验收必须按平台分组核对**，
⛔ 数总数等于没验。已在 `fn-xml-link.sh` 补齐逐键断言（`ios/and/android/iOS/Android` + 两条负向）。
